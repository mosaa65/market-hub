# قانون الترحيلات الرسمي — Market Hub ERP

> **الملف:** `supabase/MIGRATIONS_RULES.md`
> **الحالة:** قانون ملزم. يُقرأ **قبل** أي عمل على قاعدة البيانات.
> **النطاق:** كل من يضيف أو يعدّل migration أو seed أو دالة أو سياسة.

---

## 0. القاعدة الحاكمة

**الترحيلات تمثّل الحالة النهائية للنظام، لا تاريخ الوصول إليها.**

أي ملف ترحيل يُقرأ كأنه التصميم الرسمي المعتمد اليوم. إذا كان يحتوي سلسلة `ALTER` تُصلح خطأً سابقًا في نفس الملف، فهو مرفوض.

**الهدف ليس "أقل عدد ملفات".** الهدف:

```
أبسط بنية صحيحة + أقل تعقيد + وضوح + قابلية النقل + عدم تكرار + سهولة تطوير
```

عدد الملفات نتيجة، لا هدف. افصل مجالين إذا كانت الاعتماديات تسمح. ادمجهما إذا كانت الاعتماديات تفرض.

---

## 1. الفصل الإلزامي بين الأنواع الأربعة

لا يجوز خلط هذه الأنواع في ملف واحد. كل نوع له مكانه:

| النوع                            | التعريف                                                                                                                                   | المكان                       | يُنفَّذ تلقائيًا؟                   |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ----------------------------------- |
| **Schema**                       | جداول، أعمدة، علاقات، قيود، فهارس، enums، دوال، triggers، RLS                                                                             | `supabase/migrations/`       | نعم                                 |
| **Essential Reference** (النظام) | بيانات لا يعمل النظام بدونها: الوحدات، الباقات، دليل الحسابات، وحدات القياس، تصنيفات المصروفات، مسؤولو المنصة، ترقيم المستندات، طرق الدفع | `supabase/seeds/01_system/`  | نعم (مربوط في `config.toml`)        |
| **Customer** (العميل)            | بيانات عميل حقيقي: هويته، منتجاته، أرصدته الافتتاحية                                                                                      | `supabase/seeds/02_company/` | **لا — يدويًا، ولا تُرفع للمستودع** |
| **Demo** (العيّنات)              | بيانات عرض لعرض المنتج: منتجات، عملاء، فواتير وهمية                                                                                       | `supabase/seeds/03_samples/` | **لا — يدويًا فقط**                 |
| **Test** (الاختبارات)            | بيانات لاختبارات آلية، ثابتة وقابلة للتكرار                                                                                               | `supabase/seeds/04_tests/`   | **لا**                              |

> **مطابقة المجلدات:** أسماء المجلدات مرقّمة بترتيب التنفيذ (`01_system` → `04_tests`)،
> لأن الرقم يمنع الالتباس ويرتّب التشغيل. هي نفسها الأنواع الأربعة أعلاه بالترتيب.

### 1.1 اختبار الحدّ الفاصل

اسأل: **"هل يستطيع أي عميل جديد تشغيل النظام بدون هذا السطر؟"**

- نعم، والكود يحلّه بمفتاح ثابت → `seeds/01_system/`
- لا، لكنه مفيد للعرض → `seeds/03_samples/`
- لا، وهو خاص بعميل → `seeds/02_company/` أو خارج المستودع
- لا، وهو مثبّت لاختبار آلي → `seeds/04_tests/`

### 1.2 أمثلة صريحة

**مسموح في `seeds/01_system/`:**

```
أدوار النظام:      owner · manager · accountant · cashier · warehouse
حالات الفاتورة:    draft · confirmed · paid · partial · unpaid · cancelled · returned
طرق الدفع:         cash · card · bank_transfer · mobile_money · credit · split · cheque
                 + الكتالوج الموسّع اليمني (بنك الكريمي، جيب، جوالي، ...) في seeds/01_system/08
وحدات القياس:      Piece · Dozen · Kilogram · Gram · Ton · Litre · Metre · Box · Pack
تصنيفات المصروف:   Rent · Salaries · Transport · Utilities
حسابات دليل الحسابات: 1101 · 1211 · 1311 · 2111 · 4111 · 5111 ...
ترقيم المستندات:   seeds/01_system/07 (محرّك الترقيم 14 يقرأ منه)
```

**ممنوع تمامًا في أي migration:**

```
❌ قمح بلدي / قمح صلب مستورد / دقيق نمرة 1 / ذرة صفراء
❌ عميل أحمد / مورد الشركة الفلانية
❌ مخزون 999999 / منتجات بأسعار بيع وتكلفة
❌ فاتورة تجريبية / سند قبض تجريبي
❌ Main Warehouse / المحل الرئيسي / مستودع فرع تعز
❌ أصناف متجر معين / منتجات المطحنة / مستلزمات تعبئة
❌ company_settings (اسم الشركة، العملة، الشعار، الرقم الضريبي)
❌ auth.users / profiles / user_roles لأشخاص حقيقيين
❌ أي TRUNCATE / DELETE جماعي على بيانات تشغيلية
```

**سبب منع `company_settings`:** هوية الشركة **إعداد** يحرّره العميل في التطبيق. وصولها من migration أو seed يعني أن كل عميل جديد يبدأ باسم وعملة وشعار عميل آخر. هذه هي القاعدة R-6 في `docs/database/migration-safety-notes.md`.

## 2. قواعد كتابة الترحيل

### R-01 — لا بيانات أعمال أو تجريبية أو اختبارية

لا `INSERT` لمنتجات أو عملاء أو موردين أو فواتير أو مخزون أو مستودعات أو أسعار داخل `migrations/`. تُنقل إلى ملف seed مناسب.

### R-02 — لا بيانات عميل معيّن

لا اسم شركة، لا منتج عميل، لا رصيد افتتاحي لعميل، لا تصنيف خاص بمجال عمل معيّن.

### R-03 — الترحيل يمثّل Schema نهائيًا، لا تاريخ تعديلات

ممنوع:

```sql
CREATE TABLE products (...);
ALTER TABLE products ADD COLUMN sku text;
ALTER TABLE products RENAME COLUMN code TO sku;
ALTER TABLE products DROP COLUMN legacy_code;
ALTER TABLE products ADD CONSTRAINT ...;
```

مطلوب: تعريف واحد مباشر بالشكل النهائي.

```sql
CREATE TABLE public.products (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  sku text NOT NULL UNIQUE,
  category_id uuid REFERENCES public.categories(id),
  ...
);
```

### R-04 — لا سلسلة `ALTER` للوصول إلى تصميم كان يمكن كتابته مباشرة

إذا كان الجدول جديدًا، اكتبه كاملًا مرة واحدة. `ALTER` مسموح فقط لتغيير **حقيقي لاحق** على جدول موجود في الإنتاج.

### R-05 — الجدول الجديد يُكتب في ترحيل مجاله، بترتيب الاعتماد

لا يُنشأ جدول في ملف لا يخص مجاله. ولا يُنشأ جدول يشير إلى جدول غير موجود بعد.

### R-06 — التعديل المستقبلي = ترحيل جديد، عند الحاجة الفعلية فقط

لا يُنشأ ترحيل لمجرد تحسين شكلي أو إعادة تنظيم. التعديل يستحق ترحيلًا عندما يكون **مطلوبًا فعليًا** ويغيّر السلوك أو البنية.

### R-07 — لا ترحيل لتحديث بيانات Seed

تغيير صف في `seeds/01_system/` يُعدَّل في ملف الـ seed نفسه. لا يُنشأ `2026xxxx_update_units.sql`.

### R-08 — فصل صارم: Schema / Reference / Demo / Test / Customer

كما في القسم 1. لا استثناءات.

### R-09 — يُمنع إنشاء بيانات تجريبية في ترحيل إنتاجي

أي `INSERT` لا يعمل النظام بدونه = بيانات تجريبية. انقلها.

### R-10 — يُمنع استخدام هذه الأسماء

```
fix · final · final2 · fix2 · cleanup · temp · update_again · misc · patch
```

اسم الملف يصف **محتواه**. أمثلة صحيحة (من البنية الفعلية):

```
02_core_identity_and_settings.sql
05_products_and_inventory.sql
07_purchasing_and_returns.sql
16_payment_methods.sql
```

### R-11 — أسماء الملفات واضحة وتصف المحتوى

الصيغة المعتمدة:

```
<رقم_تسلسلي>_<المجال>_<الوصف>.sql
```

- الرقم التسلسلي يحدد الترتيب التنفيذي.
- المجال يحدد الحدود المعمارية.
- الوصف يصف ما يُنشأ، لا ما يُصلَح.

### R-12 — قبل إضافة ترحيل، تحقق أنه غير موجود

ابحث عن الجدول/الدالة/السياسة/الفهرس. إن وُجد، عدّل تعريفه في مكانه بدل إضافة ملف جديد.

### R-13 — لا تكرار لإنشاء نفس الكائن

ممنوع `CREATE TABLE` لنفس الجدول مرتين، أو تعريف نفس الدالة في عدة ملفات بنسخ متضاربة. آخر تعريف فقط هو الساري — وهذا هش. كل كائن يُعرَّف **مرة واحدة** في ملفه المعتمد.

### R-14 — أي تغيير على Function/RPC ينتج نسخة نهائية واضحة

ممنوع تراكم `CREATE OR REPLACE FUNCTION` لنفس الدالة في خمسة ملفات. التعريف المعتمد واحد. التعديل الجوهري لاحقًا = ترحيل جديد يُعيد تعريف الدالة كاملة بشكل مقروء.

### R-15 — كل Agent يقرأ هذا الملف أولًا

لا يُسمح بتعديل `supabase/` قبل قراءة `MIGRATIONS_RULES.md` و`MIGRATIONS_REFACTOR_PLAN.md`.

### R-16 — تحديث التوثيق عند تغيير البنية

إضافة جدول أو عمود أو دالة أو سياسة تُتبَع بتحديث `MIGRATIONS_REFACTOR_PLAN.md` و`SCHEMA_REFERENCE.md` (مرجع البنية الفعلي).

### R-17 — لا Secrets أو كلمات مرور ثابتة في الترحيل

ممنوع أي `password`, `secret`, `api_key`, `token`, `service_role_key` مكتوب صراحةً.

### R-18 — إنشاء Super Admin عبر Bootstrap آمن منفصل

إنشاء مسؤول النظام لا يتم من migration. يستخدم:

- متغيرات بيئة، أو
- سكربت bootstrap مستقل يُشغَّل يدويًا، أو
- دعوة/تسجيل عبر Supabase Auth في التطبيق.

### R-19 — الـ Seed يجب أن يكون Idempotent

كل `INSERT` ينتهي بـ `ON CONFLICT` على **مفتاح أعمال حقيقي** (اسم، كود، SKU) — لا على UUID عشوائي. `DO UPDATE` ممنوع على هوية الشركة.

### R-20 — قاعدة بيانات جديدة تُبنى من الصفر بلا أخطاء

معيار إلزامي: `supabase db reset` على مشروع فارغ ينجح دون خطأ واحد، وينتج مخططًا كاملًا صالحًا.

## 3. قواعد الأمان

### R-21 — ممنوع DML مدمّر في الترحيل

```
❌ TRUNCATE
❌ DELETE FROM <جدول تشغيلي>
❌ DELETE FROM auth.users / profiles / user_roles
❌ UPDATE جماعي على بيانات العميل
❌ DROP TABLE على جدول قائم
```

هذه العمليات تُنفَّذ يدويًا عبر سكربت مستقل موثّق، لا عبر migration يعمل تلقائيًا على كل بيئة.

### R-22 — RLS إلزامي على كل جدول

كل جدول في `public` يُفعَّل عليه `ENABLE ROW LEVEL SECURITY` ويُمنح سياسات صريحة. الجدول بلا سياسة = جدول مقفل أو مكشوف، وكلاهما خطأ.

### R-23 — الكتابة عبر RPC فقط للجداول المالية

الجداول التي تحمل أثرًا ماليًا (`sales_invoices`, `purchase_invoices`, `customer_ledger`, `journal_entries`, `journal_lines`, `stock_movements`, `inventory`) يُمنع الكتابة المباشرة عليها من العميل:

```sql
REVOKE INSERT, UPDATE, DELETE ON <table> FROM authenticated;
```

الكتابة عبر دالة `SECURITY DEFINER` داخل معاملة واحدة.

### R-24 — كل دالة `SECURITY DEFINER` تضبط `search_path`

```sql
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public
```

بدونها تتعرض الدالة لاختطاف المسار.

### R-25 — فحص الصلاحية داخل الدالة لا في الواجهة فقط

الواجهة تخفي الزر، والقاعدة ترفض العملية. كل دالة تعدّل بيانات مالية تفحص `has_role` أو `is_staff`.

## 4. قواعد إدارة التغيير

### R-26 — لا تغيير سلوك بدون سبب موثّق

كل ترحيل يغيّر منطقًا تشغيليًا يشرح في ترويسته: ما كان، ما صار، ولماذا.

### R-27 — كل ترحيل له ROLLBACK موثّق

في نهاية الملف، تعليق يوضح كيف يُلغى.

### R-28 — الترحيل الإضافي (Additive) هو الافتراضي

الأعمدة الجديدة `NULL`-able أو لها `DEFAULT`. لا `NOT NULL` على جدول فيه بيانات بلا قيمة افتراضية.

### R-29 — لا حذف عمود أو جدول بلا تحقق من الاستخدام

قبل أي حذف:

1. ابحث عن كل استخدام في `src/`
2. تحقق من كل دالة وview وreport
3. وثّق سبب اعتباره قديمًا
4. احذفه في ترحيل مستقل واضح

### R-30 — الـ Reference Data تُكتب مرة واحدة

الوحدات، الباقات، طرق الدفع، تصنيفات المصروفات، دليل الحسابات، ترقيم المستندات — تُعرَّف في `seeds/01_system/` مرة واحدة. لا تُكرَّر في الترحيل ولا في العيّنات.

## 5. قائمة تحقق قبل أي PR يمسّ قاعدة البيانات

```
[ ] قرأت MIGRATIONS_RULES.md و MIGRATIONS_REFACTOR_PLAN.md
[ ] لا بيانات أعمال/تجريبية/اختبارية في migration
[ ] لا TRUNCATE / DELETE جماعي / DROP TABLE
[ ] لا Secrets أو كلمات مرور
[ ] الجداول الجديدة في ملف مجالها الصحيح، بترتيب الاعتماد
[ ] لا ALTER متسلسل للوصول إلى تصميم كان يمكن كتابته مباشرة
[ ] كل جدول جديد له ENABLE ROW LEVEL SECURITY + سياسات
[ ] الجداول المالية ممنوعة الكتابة المباشرة، والكتابة عبر RPC
[ ] كل دالة SECURITY DEFINER تضبط search_path
[ ] لا تكرار لإنشاء نفس الكائن
[ ] أسماء الملفات وصفية بلا fix/final/cleanup
[ ] الـ seed idempotent على مفتاح أعمال حقيقي
[ ] ROLLBACK موثّق
[ ] supabase db reset على قاعدة فارغة ينجح بلا أخطاء
[ ] التوثيق محدَّث
```

## 6. عواقب المخالفة

مخالفة هذه القواعد ليست مسألة أسلوب. النتائج الفعلية المرصودة في هذا المستودع:

| المخالفة                                           | النتيجة الفعلية                                                         |
| -------------------------------------------------- | ----------------------------------------------------------------------- |
| بيانات أعمال في migration                          | `duplicate key` على `company_settings` عطّل `supabase db reset` بالكامل |
| `TRUNCATE` + `DELETE FROM auth.users` في migration | ملف واحد يمسح كل المستخدمين والأدوار وسجل التدقيق على أي بيئة جديدة     |
| `INSERT INTO inventory ... 999999` في migration    | مخزون وهمي يلوّث تقييم المخزون لأي عميل جديد                            |
| تعريف نفس الدالة في 6 ملفات                        | النسخة السارية غير واضحة، وتغييرها عرضة للخطأ                           |
| `ALTER` متسلسل على نفس الجدول                      | استحالة معرفة الشكل النهائي من قراءة الملفات                            |

هذا الملف وُجد لمنع تكرار هذه النتائج.
