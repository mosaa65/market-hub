## 1. الحكم في سطر واحد

**التصميم ممتاز، والتنفيذ فيه خلل واحد خطير يُفسد الغرض كله:** الجدول يقول
"بنك الكريمي"، والعمود يقول "نقداً" — فالمستند يُسجَّل نقداً والدفتر يقيده في
البنك.

الملف **صحيح بنيوياً** (الجداول، السياسات، الدوال، المنح كلها سليمة)، لكن **بيانات العمود `legacy_id` خاطئة في كل الصفوف الـ 13**.

## 2. الخلل الأول — `legacy_id` (خطر عالٍ)

### 2.1 الأعراض المقيسة فعلياً

استعلام على قاعدة مبنية من الملف نفسه:

| الصف             | `legacy_id` المخزَّن | الصحيح          | الحكم |
| ---------------- | -------------------- | --------------- | ----- |
| `cash`           | `cash`               | `cash`          | ✅    |
| `bank_transfer`  | **`cash`**           | `bank_transfer` | ❌    |
| `card`           | **`cash`**           | `card`          | ❌    |
| `mobile_money`   | **`cash`**           | `mobile_money`  | ❌    |
| `credit`         | **`cash`**           | `credit`        | ❌    |
| `split`          | **`cash`**           | `split`         | ❌    |
| `cheque`         | **`cash`**           | `cheque`        | ❌    |
| `kuraimi_bank`   | **`cash`**           | `bank_transfer` | ❌    |
| `jaib` و 4 محافظ | **`cash`**           | حسب نوعها       | ❌    |

**13 صفاً، 12 منها خاطئة.**

### 2.2 الأثر الحقيقي — ليس نظرياً

```
resolve_writable_payment_method('kuraimi_bank', 'pos')  →  'cash'
```

عند بيع بـ**بنك الكريمي**:

|                                           | القيمة               |
| ----------------------------------------- | -------------------- |
| المستند (`sales_invoices.payment_method`) | `cash` ← **"نقداً"** |
| الدفتر (`post_sales_invoice`)             | `1111` ← **البنك**   |

**النتيجة:** تقارير الصندوق تتضخم بأموال لم تدخله، وتقارير البنك تنقص. **والمستند يخالف الدفتر** — وهذا أسوأ من خطأ في أي منهما منفرداً، لأنه يجعل التسوية مستحيلة.

وينطبق على `credit` (الآجل): يُسجَّل "نقداً" مع أن شيئاً لم يُحصَّل.

### 2.3 السبب الجذري — ثلاثة أخطاء متراكبة

**الخطأ (أ) — `coalesce` يتوقف عند أول قيمة موجودة**

السطر 1197:

```sql
legacy_id = coalesce(
  legacy_id,              -- ← يجد 'cash' هنا فيتوقف
  nullif(legacy_ids[1], ''),   -- ← لا يصل إليه أبداً
  CASE ledger_kind ...         -- ← ولا إلى هذا
)
```

النية كانت "املأ إن كان فارغاً"، لكن `legacy_id` **ليس فارغاً** — فيه `'cash'` من `DEFAULT` أو تشغيل سابق. فالدالة تعيد `'cash'` وتتجاهل كل البدائل.

**الخطأ (ب) — فحص 8.1 لا يطابق الحالة المعطوبة**

السطر ~2081:

```sql
WHERE ... AND coalesce(legacy_id,'') NOT IN ('cash','card','bank_transfer',...)
```

يقول: "أصلح الصفوف التي قيمتها **غير صالحة**". لكن `'cash'` **قيمة صالحة** — فالشرط لا يطابقها، **والإصلاح لا يعمل أبداً**.

وهذا أسوأ أنواع الخلل: كُتب إصلاح، ولم يُنفَّذ، وطُبعت رسالة نجاح.

**الخطأ (ج) — العمود يُقرأ قبل أن يُملأ**

القسم 5 يُعيد تعريف `payment_method_legacy_id` لتقرأ `legacy_id` **أولاً** ثم `legacy_ids[1]`. لكن العمود مملوء بـ `'cash'` في كل الصفوف، فالدالة تُعيد `'cash'` وتتجاهل `legacy_ids` الصحيحة تماماً.

### 2.4 الإصلاح المقترح

في القسم 1.1، استبدال `coalesce` بـ `CASE` يقارن بالحالة الفعلية:

```sql
UPDATE public.payment_methods
   SET is_system = true,
       legacy_id = CASE
         -- القيمة الصريحة في الكتالوج أولاً
         WHEN nullif(legacy_ids[1], '') IS NOT NULL THEN legacy_ids[1]
         -- ثم عائلة الحساب — وهي المرجع الذي يثق به محرّك الترحيل
         WHEN ledger_kind = 'BANK'   THEN 'bank_transfer'
         WHEN ledger_kind = 'WALLET' THEN 'mobile_money'
         WHEN ledger_kind = 'CARD'   THEN 'card'
         WHEN ledger_kind = 'CREDIT' THEN 'credit'
         WHEN ledger_kind = 'CASH'   THEN 'cash'
         ELSE 'cash'
       END
 WHERE legacy_id IS NULL
    OR legacy_id = 'cash' AND ledger_kind <> 'CASH'   -- ← الحالة المعطوبة
    OR is_system IS DISTINCT FROM true;
```

**النقطة الجوهرية:** `WHERE` يجب أن يطابق **القيمة الخاطئة** لا **القيمة غير الصالحة**. وهذا الفرق بين إصلاح يعمل وإصلاح يبدو أنه يعمل.

وفي القسم 8.1، تصحيح الشرط بالمثل.

### 2.5 التحقق بعد الإصلاح

```sql
SELECT id, legacy_id, public.payment_method_legacy_id(id) AS resolved
FROM public.payment_methods
WHERE legacy_id <> public.payment_method_legacy_id(id);
-- يجب أن يكون صفر صفوف

SELECT public.payment_method_legacy_id('kuraimi_bank');  -- bank_transfer
SELECT public.payment_method_legacy_id('credit');        -- credit
SELECT public.payment_method_ledger_account('credit');   -- NULL
```

## 3. الخلل الثاني — `is_renamed` مُعطَّلة

### 3.1 العَرَض

دالة `payment_method_catalog_view()` تُرجع `is_renamed = false` **دائماً**، حتى بعد تعديل الاسم فعلاً.

### 3.2 السبب

```sql
m.is_system AND EXISTS (
  SELECT 1 FROM public.payment_methods d
  WHERE d.id = m.id AND d.is_system AND d.name_ar <> m.name_ar
)
```

الاستعلام يبحث في **نفس الجدول عن الصف نفسه** (`d.id = m.id`)، ثم يقارن `d.name_ar <> m.name_ar` — أي **يقارن الصف بنفسه**، والشرط يكون `false` دائماً.

المقصود: المقارنة بـ **الاسم الأصلي المشحون** — وهو غير مخزَّن في أي مكان، فالمقارنة مستحيلة كما كُتبت.

### 3.3 الأثر

شاشة الإعدادات لا تستطيع أن تُظهر "معدّلة" ولا أن تقدّم زر "إرجاع للاسم الأصلي" — وهي الميزة التي وُعد بها تعليق الملف نفسه.

**أثر منخفض** — لا يمسّ مالاً. لكنه **وعد لم يُنفَّذ**.

### 3.4 الإصلاح المقترح

عمود `shipped_name_ar` يُملأ عند الزرع ولا يُعدَّل أبداً، ثم `is_renamed = (m.name_ar <> m.shipped_name_ar)`.

أو — إن أردت أبسط حل — **حذف `is_renamed`** من العرض وتوثيق أن الميزة مؤجَّلة. **الأفضل: لا تُعلن ميزة لا تعمل.**

## 4. الخلل الثالث — ترتيب البذرة

### 4.1 العَرَض

`payment_method_settings` = **صفر صفوف**، والمتوقع 6 (القسم 4.1 يُدرج إعدادات الطرق القديمة).

### 4.2 السبب

الترتيب الفعلي:

```
1. migrations/16  ← القسم 4.1 يحاول إدراج 6 صفوف إعدادات
                     لكن payment_methods فارغ! (البذرة لم تُشغَّل)
                     → يُدرج صفراً، بلا خطأ

2. seeds/08_payment_methods  ← يزرع 13 طريقة
```

القسم 4.1 **يُدرج من الكتالوج**، والكتالوج يُزرع **لاحقاً**. فالـ `SELECT ... FROM payment_methods` يُرجع صفر صفوف، والـ `INSERT` ينجح بصمت.

### 4.3 الأثر

الطرق الـ 13 تعمل (لأن غياب صف في `settings` يعني "ورّث الافتراضي"). لكن **الـ backfill الذي كُتب لحماية الطرق القديمة لم يحدث** — وهو الغرض المعلن من القسم.

**أثر منخفض عملياً، لكنه يعتمد على ترتيب هشّ:** لو شغّل أحدهم البذرة قبل الترحيل، لاختلف السلوك.

### 4.4 الإصلاح المقترح

نقل إدراج الإعدادات إلى **البذرة** `08_payment_methods.sql` — فهي بيانات لا بنية، وهذا ما يقوله `MIGRATIONS_RULES.md`.

## 5. الخلل الرابع — فحص ذاتي لا يفحص

القسم 8.2 يفحص:

```sql
IF EXISTS (SELECT 1 FROM payment_methods WHERE id = 'kuraimi_bank')
   AND public.payment_method_legacy_id('kuraimi_bank') <> 'bank_transfer' THEN
  RAISE EXCEPTION 'FAIL: ...';
END IF;
```

**هذا الفحص سليم ومكتوب جيداً — ومع ذلك لم يُطلق!**

لأنه يعتمد على `payment_method_legacy_id` التي تقرأ `legacy_id` أولاً... لكن انتظر — كانت تُرجع `'cash'` في اختباري، والفحص كان يجب أن يفشل.

**السبب:** القسم 8.2 يقع **قبل** القسم 5 من الملف الثاني، حيث `payment_method_legacy_id` **لم تُعرَّف بعد** بالنسخة الجديدة — فكانت النسخة القديمة (التي تقرأ `legacy_ids` وتتجاهل العمود) هي الفعّالة وقت الفحص. **فمرّ الفحص، ثم تغيّر سلوك الدالة بعده.**

**الدرس:** فحص ذاتي **يسبق** تغيير السلوك لا يفحص شيئاً. يجب أن يكون **خاتمة الملف**، بعد كل التعريفات.

## 9. التعليقات الإنجليزية التي تحتاج ترجمة

رأس الملف يحوي **~120 سطراً إنجليزياً** من الأصل. المقترح ترجمتها **ترجمة ذكية** لا حرفية — أي بنقل المعنى باختصار لا بلفظه.

### 9.1 نموذج للترجمة الذكية

**الأصل (45 سطراً):**

> Before this migration, the set of usable payment methods was scattered across
> eight files with no single owner... The consequence was concrete, not
> theoretical: adding a Yemeni method such as بنك الكريمي required editing five
> files, and if you only edited the ENUM the new method posted to the CASH
> account — silently overstating the till and understating the bank, with no
> error anywhere.

**الترجمة الذكية (4 أسطر):**

> قبل هذا الملف كانت طرق الدفع موزّعة على ثمانية ملفات بلا مالك واحد. وإضافة
> طريقة يمنية مثل بنك الكريمي كانت تتطلب تعديل خمسة ملفات؛ ومن يعدّل الـEnum
> فقط تُرحَّل طريقته إلى **الصندوق** بدل البنك — بصمت وبلا خطأ ظاهر، فيتضخم
> الصندوق وينقص البنك.

**القاعدة:** تُحذف المقدمات البلاغية ("The consequence was concrete, not theoretical")، ويُبقى **السبب والنتيجة**. الجدول الزمني للملفات القديمة (`20260706120000`...) يُبقى كما هو لأنه مرجع تقني.

### 9.2 الأقسام التي تُترجم

| القسم                                | السطور     | الأولوية                   |
| ------------------------------------ | ---------- | -------------------------- |
| رأس الملف                            | 1–135      | **عالية** — تُقرأ أولاً    |
| §10 "WHERE THE OLD DEFINITIONS WENT" | ~1120–1150 | متوسطة                     |
| تعليقات `COMMENT ON`                 | متفرقة     | ✅ **معرّبة أصلاً**        |
| تعليقات داخل الدوال بالإنجليزية      | متفرقة     | منخفضة — رسائل أخطاء تقنية |

### 9.3 ما يُترك إنجليزياً

- أسماء الملفات القديمة (`20260706120000`)
- رسائل `RAISE EXCEPTION` بالإنجليزية — لأنها تُلتقط في السجلات وتُترجم في الواجهة
- أسماء الأعمدة والدوال

## 10. الإصلاحات المنفَّذة

طُبِّقت الإصلاحات الستة على الملفات، وبقيت الترجمة وحدها مؤجّلة (لا أثر وظيفي لها).

| #   | الملف                                    | ما تغيّر بالضبط                                                                                                                              |
| --- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `16_payment_methods.sql` §1.1            | `coalesce(legacy_id, …)` → `CASE` يشتقّ القيمة من `legacy_ids[1]` ثم من `ledger_kind`، وشرط `WHERE` صار يطابق الصفوف **المخالفة** لا الصالحة |
| 2   | `16_payment_methods.sql` §1.2            | حُذف `DEFAULT 'cash'` عن العمود — كان هو السبب الجذري: يجعل `coalesce` يجد قيمة غير NULL فيتوقف                                              |
| 3   | `16_payment_methods.sql` §8.1            | شرط الإصلاح صار يقارن القيمة المخزّنة بالقيمة المشتقة — كانت `'cash'` قيمة **صالحة** فلا يطابقها الشرط القديم أبدًا                          |
| 4   | `16_payment_methods.sql` §1 + §6         | عمود جديد `shipped_name_ar` يُكتب عند الزرع فقط، و`is_renamed` تقارن به بدل مقارنة الصف بنفسه                                                |
| 5   | `16_payment_methods.sql` §4.1            | حُذف إدراج `payment_method_settings` (كان يجد الكتالوج فارغًا) ونُقل إلى البذرة `08`                                                         |
| 6   | `seeds/01_system/08_payment_methods.sql` | أُضيف `shipped_name_ar` إلى كل صف، وإدراج إعدادات المنشأة، وفحوص ذاتية ثلاث                                                                  |

### 10.1 الفحص الذاتي الآن يكشف الخلل لا يمرّ عليه

البذرة `08` صارت تفحص ثلاثة ثوابت تفشل بصوت عالٍ:

1. كل صف نظامي يحمل `shipped_name_ar` — وإلا عادت `is_renamed` معطّلة.
2. الطرق الست التاريخية لها صف إعداد للمنشأة — وإلا فشل نقل §4.1 بصمت.
3. كل كود حساب في الكتالوج موجود في دليل الحسابات (كان موجودًا).

### 10.2 التحقق

-- يجب أن يكون صفرًا: لا صف يخالف القيمة التي تُرجعها الدالة
SELECT count(*) FROM public.payment_methods m
 WHERE m.legacy_id <> public.payment_method_legacy_id(m.id);

-- 6 طرق تاريخية لها إعداد
SELECT count(*) FROM public.payment_method_settings;

-- بنك الكريمي → 'bank_transfer'، والدفتر → '1111'
SELECT public.payment_method_legacy_id('kuraimi_bank'),
       public.payment_method_ledger_account('kuraimi_bank');
