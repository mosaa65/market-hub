# دليل موحّد لإعداد Supabase المحلي والسحابي

هذا الدليل هو نقطة البداية لتشغيل المشروع محليًا أو تحديث مشروع Supabase سحابي.
مصدر الحقيقة للترحيلات هو فرع GitHub `main` وملفات `supabase/migrations/` فيه.

## الأوامر اليومية

من جذر المشروع في PowerShell:

| المطلوب | الأمر | أثره |
|---|---|---|
| بدء الخدمات المحلية فقط | `npm run db:local:start` | يشغّل Docker Supabase ولا يمسح البيانات |
| إعادة بناء المحلي مع بيانات المطحنة | `npm run db:local:rebuild` | يطلب تأكيدًا، يمسح قاعدة Docker المحلية فقط، يطبق migrations والبذور النظامية ثم عينة المطحنة ويتحقق من النتيجة |
| معرفة حالة الخدمات المحلية | `npm run db:local:status` | يعرض عناوين API وStudio وقاعدة البيانات |
| دفع migrations إلى المشروع السحابي المرتبط | `npm run db:cloud:push` | يطلب تأكيد معرف المشروع، يطبق migrations الجديدة فقط ويعيد البذور المرجعية الآمنة؛ لا يعمل reset |

لفتح البيانات التجريبية على مشروع سحابي اختباري قابل للمسح فقط:

```powershell
npm run db:cloud:push -- -IncludeDemoData
```

يتطلب هذا الخيار تأكيدًا إضافيًا بكتابة معرف المشروع، ثم يضيف حسابات المنصة التجريبية ذات كلمة المرور `Super#2004` وبيانات مطحنة وهمية. لا تستخدمه على مشروع عميل أو إنتاج.

## أول تشغيل محلي

1. شغّل Docker Desktop وانتظر جاهزية المحرك:

   ```powershell
   docker info --format "{{.ServerVersion}}"
   ```

2. أعد بناء قاعدة Docker من المصدر المعتمد:

   ```powershell
   npm run db:local:rebuild
   ```

3. اكتب عبارة التأكيد `RESET LOCAL kwzqvgdyadylwnvjghqn` عند الطلب.

4. بعد اكتمال التحقق، افتح:

   - API: `http://127.0.0.1:54321`
   - Studio: `http://127.0.0.1:54323`
   - Mailpit: `http://127.0.0.1:54324`
   - PostgreSQL: `postgresql://postgres:postgres@127.0.0.1:5432/postgres`

يتحقق الأمر من وصول الترحيلات إلى 55، ومن وجود أنواع الحبوب وعينة المطحنة وحسابات التطوير. عينة المطحنة وحسابات التطوير بيانات محلية فقط؛ لا تعني أن سجل الأعمال في السحابة يجب أن يطابق المحلي.

### تسجيل الدخول محليًا

بعد إعادة البناء، حسابات التطوير الأربعة موجودة. بيانات الدخول المشتركة للتطوير
هي كلمة المرور `Super#2004`؛ يمكن تسجيل الدخول بالبريد أو بالهاتف للرقم
`+967772217218`. هذا رقم اختبار محدد في `[auth.sms.test_otp]` مع الرمز `123456`
لـOTP المحلي فقط؛ لا يرسل SMS، ولا يعمل على السحابة، ولا تستخدمه لحساب حقيقي.
قد يطبع Supabase CLI تحذير عدم وجود مزود SMS خارجي؛ هذا متوقع ما دام اختبار
OTP المحلي مفعّلاً.

## ربط مشروع سحابي جديد

تحتاج Supabase CLI وتسجيل الدخول إليه مرة واحدة. لا تضع كلمات المرور أو مفاتيح الخدمة في الأوامر أو Git.

أضف اتصال PostgreSQL المباشر للمشروع في `.env` غير المتعقّب، بهذه الصيغة:

```text
SUPABASE_DB_URL=postgresql://postgres:<db-password>@db.<project-ref>.supabase.co:5432/postgres
```

لا تضع قيمة حقيقية في مستودع أو ملف متعقّب. السكربت يتحقق أن host يطابق
معرف المشروع المرتبط، ولا يطبع الرابط أو كلمة المرور. يلزم أن يكون `node_modules`
مثبتًا (`npm install`) لاستخدام عميل PostgreSQL المرفق بالمشروع.

إذا كانت شبكتك لا تدعم IPv6 للاتصال المباشر، استخدم عنوان الـ Pooler المعروض
في لوحة المشروع، واجعل اسم المستخدم `postgres.<project-ref>`؛ السكربت يتحقق من
المعرف في اسم المستخدم قبل الاتصال.

أعد تدوير كلمة مرور قاعدة البيانات من لوحة Supabase إذا ظهرت في سجل أو رسالة؛
لا تحتفظ بكلمة مرور منشورة في سجل الطرفية. كتلة السحابة الحالية في `.env`
معلّقة وتحتوي placeholder؛ لن يعمل cloud push حتى تدوّر كلمة المرور وتضع
`SUPABASE_DB_URL` الجديدة محليًا.

```powershell
supabase login
npm run db:cloud:push -- -ProjectRef <project-ref>
```

يحاول الأمر ربط المشروع، ثم يطلب كتابة `CLOUD <project-ref>` للتحقق من الهدف. بعد ذلك:

1. `supabase db push --linked` يطبق migrations غير المطبقة بالترتيب.
2. يطبق سكربت Node ملفات SQL المرجعية متعددة العبارات باتصال PostgreSQL مباشر، دون حسابات تطوير أو بيانات مطحنة تجريبية.
3. يُنشأ حساب المالك الأول عبر مسار إدارة المستخدمين المعتمد للمشروع.

إذا كان تاريخ migrations في السحابة لا يطابق الملفات، يتوقف `db push`. لا تستخدم `--include-all` أو `migration repair` أو حذف schema لإجباره؛ أصلح اختلاف المصدر أولاً.

## قواعد تمنع اختلاف السلسلة

- المحلي والسحابي يبنيان البنية من نفس migrations المرقمة؛ لا تُعدّل migration مطبقة، بل أضف migration جديدة.
- `supabase db reset --local` محلي فقط، وهو ماسح لبيانات Docker. السكربت يضيف تأكيدًا قبل تنفيذه.
- لا تستخدم `supabase db reset --linked`، ولا تسقط `public`، ولا تفرغ `supabase_migrations.schema_migrations`.
- `supabase db push --linked` هو مسار السحابة الطبيعي، وهو غير هدّام ولا يزرع بيانات العرض.
- ملفات `03_samples/` و`06_platform_admins.sql` لا تُرسل إلى السحابة إلا بخيار demo الصريح وعلى مشروع قابل للمسح.
- ملف `supabase/config.toml` يشغّل بذور النظام عند reset. عينة المطحنة تُضاف صراحةً من أمر المحلي أو من خيار demo السحابي.
- أبقِ `supabase/.temp/` و`supabase/config.local` و`.env` محلية؛ لا ترفع مفاتيحها أو تغييرات الربط.

## التحقق اليدوي

```powershell
supabase status
supabase migration list --local
supabase db push --linked --dry-run
```

`migration list --local` يقرأ سجل Docker المحلي. أما أوامر `--linked` فتتصل بالسحابة؛ لا تخلط النتائج أو تستخدمها لاستنتاج أن قاعدة المحلي قد حُدّثت.
