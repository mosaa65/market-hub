## 1. الملخص التنفيذي

الترتيب العام للترحيلات والبذور **سليم**، والبنية `01`–`16` تُطبَّق بتسلسل
اعتماديات صحيح. لكن ترحيل طرق الدفع (`16`) حمل **خلل بيانات خطير** يُفسد الغرض
منه: العمود `legacy_id` كان يبقى `'cash'` في كل الصفوف، فيُسجَّل المستند «نقداً»
بينما الدفتر يقيده في البنك — وهذا أسوأ من خطأ في أحدهما، لأنه يجعل التسوية
مستحيلة.

كذلك وُجد خطأ ثالث في تصنيف البيانات: صفوف إعداد المنشأة (`payment_method_settings`)
كانت تُدرج **قبل** وجود الكتالوج، فتُدرج صفراً بصمت.

**النتيجة:** أُصلحت خمسة أخطاء، ونُقلت بيانات إلى مكانها القانوني (البذور)،
وأُضيفت فحوص ذاتية تكشف الخلل بدل أن تمرّ عليه.

## 3. الأخطاء المكتشفة في الترحيل 16

### 3.1 الخلل الأول — `legacy_id = 'cash'` في 12 صفًا (خطر عالٍ)

**العَرَض المقيس:** الجدول يقول «بنك الكريمي»، والعمود يقول «نقداً».

| الصف            | `legacy_id` المخزَّن | الصحيح             |
| --------------- | -------------------- | ------------------ |
| `cash`          | `cash`               | `cash` ✅          |
| `bank_transfer` | **`cash`**           | `bank_transfer` ❌ |
| `card`          | **`cash`**           | `card` ❌          |
| `mobile_money`  | **`cash`**           | `mobile_money` ❌  |
| `credit`        | **`cash`**           | `credit` ❌        |
| `split`         | **`cash`**           | `split` ❌         |
| `cheque`        | **`cash`**           | `cheque` ❌        |
| `kuraimi_bank`  | **`cash`**           | `bank_transfer` ❌ |
| `jaib` و4 محافظ | **`cash`**           | حسب نوعها ❌       |

**الأثر:** عند بيع بـ«بنك الكريمي»: المستند يُخزَّن `cash`، والدفتر يُقيَّد في
`1111` البنك. فتقارير الصندوق تتضخم، وتقارير البنك تنقص، **والمستند يخالف الدفتر**.

**السبب الجذري — ثلاثة أخطاء متراكبة:**

1. `coalesce(legacy_id, …)` يتوقف عند أول قيمة موجودة. ولأن العمود لم يكن `NULL`
   (بسبب `DEFAULT 'cash'` أدناه)، فالدالة تُعيد `'cash'` وتتجاهل `legacy_ids`
   و`ledger_kind` معًا.
2. `ALTER COLUMN legacy_id SET DEFAULT 'cash'` هو ما جعل العمود غير `NULL` أصلاً.
3. فحص الإصلاح في §8.1 كان يطابق «القيمة **غير الصالحة**»، و`'cash'` قيمة صالحة —
   فلم يطابقها قط، وطبع نجاحًا كاذبًا.

### 3.2 الخلل الثاني — `is_renamed` لا تعمل أبدًا (خطر منخفض)

`payment_method_catalog_view()` كانت تحسب `is_renamed` بمقارنة الصف **بنفسه**:

```sql
EXISTS (SELECT 1 FROM payment_methods d
        WHERE d.id = m.id AND d.name_ar <> m.name_ar)   -- d هو m نفسه
```

فالشرط `false` دائمًا. المقصود كان المقارنة بالاسم الأصلي المشحون — وهو غير مخزَّن.

### 3.3 الخلل الثالث — إعدادات المنشأة لا تُزرع (خطر منخفض)

`payment_method_settings = 0` صفًا والمتوقع 6. السبب: الترحيل 16 §4.1 كان يُدرج
`SELECT … FROM payment_methods` **قبل** تشغيل البذرة، فيجد الجدول فارغًا ويُدرج
صفرًا بلا خطأ. الترتيب هشّ: لو شغّل أحدهم البذرة أولًا لاختلف السلوك.

## 4. ما أُصلح في كل ملف

### 4.1 `migrations/16_payment_methods.sql`

| #   | الموضع    | ما تغيّر                                                                                                                                                                                                 |
| --- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | §1.1      | `coalesce(legacy_id, …)` → `CASE` يشتقّ القيمة من `legacy_ids[1]` ثم من `ledger_kind`، وشرط `WHERE` صار يطابق الصفوف **المخالفة** لا الصالحة. فإعادة التشغيل تتقارب إلى القيمة الصحيحة بدل أن تحفظ الخلل |
| 2   | §1.2      | حُذف `DEFAULT 'cash'` — كان السبب الجذري                                                                                                                                                                 |
| 3   | §8.1      | شرط الإصلاح صار يقارن القيمة المخزّنة بالقيمة المشتقة، فصار يطابق `'cash'` الخاطئة                                                                                                                       |
| 4   | §1 + §6   | عمود جديد `shipped_name_ar` يكتبه الـseed فقط، و`is_renamed` صارت تقارن به                                                                                                                               |
| 5   | §4.1      | حُذف إدراج `payment_method_settings` ونُقل إلى البذرة `08` (بيانات لا بنية — R-30)                                                                                                                       |
| 6   | رأس الملف | توثيق الأخطاء الثلاثة وسبب الإصلاح                                                                                                                                                                       |

### 4.2 `seeds/01_system/08_payment_methods.sql`

- أُضيف `shipped_name_ar` لكل صف، ويُحدَّث في `ON CONFLICT DO UPDATE`.
- أُضيف إدراج `payment_method_settings` للطرق الست القديمة (نُقل من الترحيل).
- أُضيفت **ثلاثة فحوص ذاتية** تفشل بصوت عالٍ:
  1. كل صف نظامي يحمل `shipped_name_ar` — وإلا عادت `is_renamed` معطّلة.
  2. الطرق الست التاريخية لها صف إعداد — وإلا فشل نقل §4.1 بصمت.
  3. كل كود حساب في الكتالوج موجود في دليل الحسابات.

## 7. التحقق

بعد إصلاح `config.toml`، شغّل محليًا:

```powershell
npx supabase db reset
npx supabase db query "SELECT id, legacy_id, public.payment_method_legacy_id(id) AS resolved FROM public.payment_methods WHERE legacy_id <> public.payment_method_legacy_id(id);"
npx supabase db query "SELECT count(*) FROM public.payment_method_settings;"
npx supabase db query "SELECT public.payment_method_legacy_id('kuraimi_bank'), public.payment_method_ledger_account('kuraimi_bank');"
```

**المتوقع:**

| الفحص                        | المتوقع                             |
| ---------------------------- | ----------------------------------- |
| `db reset`                   | ينتهي بلا خطأ — 16 ترحيلًا + 8 بذور |
| صفوف `legacy_id <> resolved` | **صفر**                             |
| `payment_method_settings`    | **6**                               |
| `kuraimi_bank`               | `bank_transfer` · `1111`            |
| `credit`                     | `credit` · `NULL`                   |

## 8. خطأ التشغيل: `enable_phone`

ظهر في الطرفية:

```
failed to parse config: decoding failed due to the following error(s):
'auth' has invalid keys: enable_phone
```

**السبب:** ملف `config.toml` يحتوي مفاتيح لا يعرفها CLI 2.120. مخططه مُحكم
الإغلاق، فأي مفتاح غير معروف في قسم يُرفض ويمنع `db reset` و`start` كليهما.

**ما حُذف من `config.toml`:**

1. `enable_phone = true` داخل `[auth]` — غير موجود في هذا الإصدار.
2. قسم `[auth.sms.twilio]` بمفاتيح `placeholder` — لا يقبل CLI مفاتيح وهمية،
   وGoTrue تحاول الاتصال بـTwilio فتفشل.
3. `template` داخل `[auth.sms]` — **غير موثق** في CLI 2.120 أيضًا؛ المفتاحان
   المعترف بهما هناك هما `enable_signup` و`enable_confirmations` فقط.

**البديل الصحيح:** تفعيل الهاتف محليًا يتم عبر `[auth.sms]` مع
`enable_signup = true`، وبلا مزوّد SMS تُطبع الرموز في سجلّ حاوية `auth` بدل
إرسالها — وهو المطلوب في التطوير. ونص رسالة OTP يُضبط من لوحة Supabase لا من
الملف. (المصدر: [Supabase CLI config](https://supabase.com/docs/guides/cli/config))

**كيف تربط القاعدة المحلية من الطرفية؟** راجع
`LOCAL_DATABASE_DOCKER_GUIDE.md` — القسم 9 (دليل سريع للتشغيل والربط).

**دليل الإصلاح (تحقق فعلي):** شُغّل CLI بعد الإصلاح فأصبح يطبع
`Resetting local database...` — أي أن قراءة الإعداد **نجحت**، ولم يتوقف إلا
لأن Docker غير موجود في بيئة التشغيل هذه:

```
Resetting local database...
failed to remove container: docker: command not found ...
```

أي أن خطأ `failed to parse config` الذي كان يمنع `db reset` **زال**، وتتابع
العملية على جهازك حيث Docker مثبّت.
