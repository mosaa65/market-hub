# 03_samples — بيانات عرض لكل نشاط

هذا المجلد يحتوي **بيانات مثال جاهزة** ليرى من يجرّب النظام بيانات واقعية بدل
قاعدة فارغة. يُشغَّل **يدويًا**، و**لا يُشغَّل على قاعدة عميل حقيقي أبدًا**.

---

## الملفات

| الملف | النشاط | المحتوى |
| --- | --- | --- |
| `sample-mill.sql` | مطحنة دقيق | 28 صنفًا تجريبيًا، 14 تصنيفًا، بيانات موردين وعملاء عرض؛ وتوفر migrations أربعة أنواع حبوب |

### عيّنتان موروثتان — حُذفتا

كان في المجلد ملفان لبقالة وقرطاسية (`supermarket-inherited.sql` و
`stationery-inherited.sql`). حُذفا نهائيًا لأنهما **لا يعملان على قاعدة
جديدة**: الأول يكتب هوية الشركة ويُنشئ مستخدمين، والثاني يحمل **489
معرّفًا ثابتًا** من قاعدة المطوّر. إن احتجت المحتوى (أسماء المنتجات
والأسعار) فأعد كتابته على نمط `sample-mill.sql`.

---

## لماذا كل نشاط في ملف واحد؟

كانت بيانات المطحنة موزّعة على **ستة ملفات**:
`mill-catalog` + `mill-products` + `mill-reference` + `warehouses` +
`customers` + `suppliers`.

فكان المالك يفتح ستة ملفات ليعدّل سعر منتج أو يضيف عميلًا، ويعرف ترتيب تشغيلها
ولا ينسى أحدها. وإن أضاف منتجًا في ملف المنتجات احتاج تصنيفًا في ملف آخر —
ملفان يجب أن يُشغَّلا بالترتيب.

**اليوم:** ملف واحد لكل نشاط، مقسّم إلى أقسام مرقّمة يعمل كل قسم بعد الذي قبله.
لتعديل سعر، ابحث عن «القسم 4». لإضافة عميل، اذهب إلى «القسم 6».

---

## لماذا لا تُشغَّل تلقائيًا؟

لأنها **بيانات منشأة واحدة** لا تصلح لغيرها. لو شُغّلت تلقائيًا لاستلم متجر
القرطاسية كتالوج مطحنة، وهو خطأ وقع فعلًا في هذا المشروع:

```sql
-- كان في migration يُطبَّق على كل قاعدة جديدة
INSERT INTO public.inventory (...) VALUES (..., 999999, ...);  -- مخزون وهمي
INSERT INTO public.products ('RM-WHEAT-HARD', 'قمح صلب مستورد', ...);
```

## التشغيل

شغّل `01_system` أولًا (يُشغَّل تلقائيًا في `db reset`)، ثم ملفًا واحدًا:

```bash
# مطحنة
psql "$DATABASE_URL" -f supabase/seeds/03_samples/sample-mill.sql
```

أو الصق الملف في Supabase Studio ← محرر SQL ← تشغيل.

> **لا تُشغّل ملفًا من هنا على قاعدة عميل.** سيُدخل منتجات وعملاء وهميين في
> دفاتره، وسيصعب تمييزها لاحقًا.

### نشاط غير موجود؟

شغّل `01_system` فقط، ثم أدخل منتجاتك من التطبيق. النظام يعمل بلا أي ملف عيّنة.

## قواعد كتابة ملف عيّنة

### 1. بلا معرّفات ثابتة
ممنوع كتابة UUID صريح. كان `mill-products.sql` يحتوي معرّفات مثل
`'ac4a1521-8e10-47ee-8da1-8c4aa7dcc645'` مأخوذة من قاعدة المطوّر — وهي لا وجود
لها في قاعدة جديدة، فيفشل الملف.

**الطريقة الصحيحة:** حلّ المعرّف بالاسم أو الرمز:

```sql
INSERT INTO public.products (sku, category_id, unit_id, ...)
SELECT v.sku,
       (SELECT id FROM public.categories WHERE name = v.category),
       (SELECT id FROM public.units      WHERE name = v.unit),
       ...
FROM (VALUES ('RM-WHEAT-HARD', 'Wheat', 'Kilogram', ...)) AS v(sku, category, unit, ...)
ON CONFLICT (sku) DO NOTHING;
```

### 2. بيانات نظيفة
ممنوع أسماء ضغط لوحة المفاتيح أو أرصدة مختلقة. كان `customers.sql` يحتوي:
```
عميل اسمه ضغط لوحة مفاتيح        ← بيانات اختبار تسرّبت
عميل برصيد 14,500 بلا أي فاتورة   ← رصيد مُختلق
```
الرصيد غير الصفري يجب أن ينشأ من فاتورة حقيقية. في مثال، الرصيد **صفر**.

### 3. ثابت (Idempotent)
`ON CONFLICT` على مفتاح أعمال حقيقي: `sku` للمنتجات، `name` للتصنيفات.

### 4. ترتيب الأقسام
كل قسم يعتمد على ما قبله:

```
1. الوحدات الخاصة بالنشاط     ← لا شيء
2. المستودع                    ← لا شيء
3. التصنيفات                   ← لا شيء
4. المنتجات                    ← 1 و 3
5. المراجع الخاصة (درجات…)     ← 4
6. المورّد والعملاء            ← لا شيء
```

---

## عند إضافة نشاط جديد

1. انسخ أقرب ملف موجود (القرطاسية للمتاجر، البقالة للتجزئة).
2. احذف المحتوى وأبقِ الهيكل والأقسام.
3. املأ الأقسام بالترتيب.
4. اختبر على قاعدة فارغة: `db reset` ثم شغّل الملف.
5. شغّله **مرتين** للتأكد من الثبات.
6. سجّله في الجدول أعلى هذا الملف.
