# 02_company — بيانات المنشأة

هذا المجلد مخصص لـ **هوية العميل وأرصدته الافتتاحية**. يُشغَّل **يدويًا**، مرة
واحدة لكل عميل جديد، و**لا يُشغَّل تلقائيًا أبدًا**.

---

## لماذا مجلد منفصل؟

لأن ما هنا **يخصّ عميلًا بعينه**، لا النظام. ولو وُضع في `01_system/` لاستلمه
كل عميل جديد:

> كل عميل يبدأ باسم شركة أخرى، وبعملة أخرى، وبمستودع لا يخصّه.

هذا ممنوع بنصّ `MIGRATIONS_RULES.md` القاعدة R-02.

---

## الملفات

| الملف                           | الغرض                                     |
| ------------------------------- | ----------------------------------------- |
| `customer-template.sql.example` | قالب لتحميل الأرصدة الافتتاحية لعميل جديد |

القالب يحمل لاحقة `.example` حتى لا يُشغَّل بالخطأ. انسخه باسم جديد، واملأه،
وأبقِ النسخة المعبّأة **خارج المستودع**:

```bash
cp customer-template.sql.example acme-trading-2026.sql
# عبّئه، ثم شغّله
psql "$DATABASE_URL" -f acme-trading-2026.sql
```

> أضف `seeds/02_company/*.sql` إلى `.gitignore`. النسخة `.example` وحدها هي
> التي تُرفع إلى المستودع.

## ما لا يوضع هنا في ملف

### 1. هوية الشركة

اسم الشركة، العملة، الرقم الضريبي، الشعار، بادئة الفواتير — كلها **إعداد**
يحرّره العميل من شاشة الإعدادات. لا تُكتب في ملف.

### 2. المستودع الأول

المستودع موقع فيزيائي يخصّ العميل. يُنشأ من شاشة المستودعات.

### 3. كلمات المرور

لا كلمات مرور ولا مفاتيح. إنشاء المستخدمين عبر التطبيق أو دالة
`admin-create-user`، ثم يُمنح المالك الأول دور `owner` صراحةً.

## الأرصدة الافتتاحية — الطريقة الصحيحة

لا تُدخل الأرصدة بـ `INSERT` مباشر. استخدم دورة الأرصدة الافتتاحية في النظام،
لأنها تتحقق من التوازن وتكتب حركات المخزون وطبقات التكلفة معها.

### الخطوة 1 — إنشاء المستند كمسودة

```sql
SELECT public.create_opening_balance(
  _effective_date => '2026-01-01',
  _lines => '[
    {"section":"STOCK",      "product_id":"...", "warehouse_id":"...",
                             "quantity":1000, "unit_cost":250, "amount":250000,
                             "description":"رصيد افتتاحي - مخزون"},
    {"section":"RECEIVABLE", "customer_id":"...", "amount":50000,
                             "description":"ذمم عملاء"},
    {"section":"CASH",       "amount":100000, "description":"نقدية"},
    {"section":"CAPITAL",    "amount":400000, "description":"رأس المال"}
  ]'::jsonb
);
```

### الخطوة 2 — التحقق من التوازن قبل الترحيل

```sql
SELECT document_number, total_assets, total_liabilities, capital_required, is_balanced
  FROM public.opening_balance_summary
 ORDER BY created_at DESC LIMIT 1;
```

`is_balanced = false` تعني أن الأرقام لا تتوازن، و`post_opening_balance` سيرفضها.

### الخطوة 3 — الترحيل

```sql
SELECT public.post_opening_balance('<معرّف المستند>');
```

## أقسام المستند وأطرافها

| القسم           | الطرف | مثال                        |
| --------------- | ----- | --------------------------- |
| `STOCK`         | مدين  | مخزون أول المدة             |
| `RECEIVABLE`    | مدين  | ما هو مستحق لنا على العملاء |
| `CASH` / `BANK` | مدين  | نقدية وبنوك                 |
| `ASSET`         | مدين  | أصول ثابتة                  |
| `PAYABLE`       | دائن  | ما هو مستحق للموردين        |
| `LIABILITY`     | دائن  | قروض والتزامات              |
| `CAPITAL`       | دائن  | رأس المال                   |

الطرف **يُشتقّ من القسم** ولا يُدخل يدويًا — فخطأ كتابة «أصل على الجانب الدائن»
مستحيل.

> ⚠️ الرصيد الافتتاحي الخطأ **يُبنى عليه كل تقييم لاحق**. تحقق قبل الترحيل،
> واحتفظ بنسخة من الملف المعبّأ.

---

## ⚠️ خطر معروف: أقسام لا تُرحَّل

فحص سابق كشف أن `post_opening_balance()` ترحّل **المخزون والذمم فقط**. أما
`CASH` و`BANK` و`ASSET` و`LIABILITY` و`CAPITAL` فتُسجَّل في المستند **ولا
تُرحَّل إلى دفتر الأستاذ**.

**الأثر العملي:** مستند افتتاحي متوازن (نقدية 50 مليون مقابل رأس مال 50 مليون)
**يُقبل ويُعلَّم `POSTED`** بينما لا تزيد النقدية ولا يُنشأ رأس مال في أي مكان.

**ما يجب فعله:** بعد ترحيل أي مستند افتتاحي فيه أقسام نقدية أو رأس مال، تحقق
يدويًا من أثره على ميزان المراجعة. هذا موثّق في
`ACCOUNTING_GAPS_AUDIT_REPORT.md`.
