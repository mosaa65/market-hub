# توجيه العامل البرمجي: إكمال نظام المطحنة اليمنية

انسخ هذا التوجيه كاملاً إلى العامل البرمجي الذي سيكمل المشروع.

```text
أنت مهندس برمجيات مسؤول عن إكمال نظام إدارة مطحنة يمنية داخل مشروع Market-Hub / Vortex ERP. لا تكتفِ بمراجعة أو تلخيص الخطط: افحص الكود وقاعدة البيانات والواجهات، ثم نفّذ النواقص فعلياً واختبرها وارفَعها في فروع/طلبات دمج صغيرة قابلة للمراجعة.

## مصادر الحقيقة — اقرأها كاملة قبل أي تغيير
رتّب المرجعية عند التعارض بهذا الترتيب:
1) معلومات عن المطحنه.m2.md — المرجع التشغيلي اليمني الأوسع والأحدث.
2) معلومات عن المطحنه.md — يشرح دورة الإنتاج التجاري للمطحنة، القمح، النواتج، الفاقد والتكلفة.
3) plan,mill.md — التصميم والتنفيذ التفصيلي للبيانات والواجهات.
4) MILLING_SYSTEM_IMPROVEMENT_PLAN.md — تحسينات الطحن للغير، العقود، التسعير والتقارير وحالة التنفيذ.
5) Market-Hub_Product_Inventory_Service_Design.md وMarket-Hub_Product_Inventory_Service_Implementation_Status.md — قواعد المنتج والمخزون المشتركة.

لا تفترض أن ما كُتب في "حالة التنفيذ" مكتمل؛ تحقق من الـ migrations المطبقة، تواقيع RPC، RLS، الواجهات، وسيناريو حقيقي في قاعدة بيانات اختبار/البيئة المرتبطة. لا تعدّل أو تعرض أسرار .env.

## قواعد أعمال غير قابلة للكسر
- افصل دائماً بين مخزون الشركة وممتلكات العميل المحتجزة لدى المطحنة. حبوب العميل ونواتج طحنه أمانة وليست شراء أو مخزوناً أو إيراداً للشركة.
- فرّق بين: مادة خام، منتج نهائي، منتج جانبي مثل النخالة، مادة تعبئة، خدمة، فاقد، ومادة عميل. لا تستخدم الاسم أو علامة is_service وحدهما لاستنتاج السلوك.
- المنتج المملوك للمطحنة: GOOD + TRACKED، ولكل حركة مستند ومصدر وتكلفة.
- خدمة طحن الغير: SERVICE + UNTRACKED؛ فاتورة خدمة فقط، ولا تنشئ رصيد مخزون.
- سعر الطحن يُتفق ويُثبت في عقد/سند الاستلام بعد الوزن الصافي وفحص الجودة، ثم تصدر الفاتورة عند إتمام العمل بنفس الأساس المتفق عليه. يمنع احتساب BAG وTON للخدمة نفسها معاً.
- التخزين للغير هو حيازة/أمانة؛ لا يدخل تقييم مخزون الشركة. أي رسم تخزين يكون خدمة وفاتورة مستقلة واضحة.
- لا شراء وهمي للرصيد الافتتاحي، ولا تسوية مخزون تُسجل كمشتريات.
- لا تسليم أكثر من الناتج أو الرصيد المتاح، ولا يختفي فرق الوزن: يُسجل فاقداً/فرق إنتاج بسبب وتصديق.
- لا تخلط إنتاج ملك المطحنة بطحن الغير. لكل منهما مستندات، ملكية، تقارير، وقيود مختلفة.
- استخدم الريال اليمني YER و"ر.ي"، ضريبة صفرية افتراضياً ما لم يقرر المستخدم غير ذلك، ونصوص عربية وبيانات يمنية واقعية قابلة للتعديل. لا تخترع أسعار سوق ملزمة؛ ضعها مرجعية مع تاريخ/مصدر أو اجعلها مدخلة من المستخدم.

## المطلوب تنفيذه، بالترتيب
1. أنشئ مصفوفة فجوات فعلية: كل بند من الخطط مقابل (قاعدة البيانات، RPC/RLS، الواجهة، الاختبار، التقرير) مع حالة دليلية، في docs/plans أو ملف حالة جديد. لا تضع "مكتمل" بلا اختبار.
2. أصلح أساس المنتج والمخزون أولاً:
   - حقول وسياسة الصنف محفوظة فعلياً على products، لا كتفضيل متصفح فقط.
   - واجهة عربية واضحة لإضافة/تعديل: نوع الصنف، الملكية، التتبع، الوحدة، السعر/التكلفة، الحد الأدنى والمستودع.
   - بطاقات المنتجات والمخزون لا تخفي فشل الاستعلام كأنها بيانات فارغة.
   - الرصيد الافتتاحي، الاستلام، التسوية، النقل، والبيع تسجل المصدر والتكلفة ولا تخلط التقارير.
3. أكمل دورة إنتاج ملك المطحنة كمسار مستقل:
   شراء القمح → استلام مخزني → أمر إنتاج → صرف القمح/مواد التعبئة → إدخال النواتج الفعلية (دقيق/نخالة/سميد/غيره) → تسجيل الفاقد وسببه → إضافة النواتج للمخزون → تكلفة الإنتاج → بيع/تحصيل/تقارير.
   يجب أن يدعم أمر الإنتاج المخطط مقابل الفعلي ونسبة الاستخلاص، ولا يفرض نسبة ثابتة.
4. أكمل طحن الغير والأمانات:
   استلام ووزن صافٍ/رطوبة/شوائب → عقد خدمة بسعر واحد → أمر طحن → نواتج وفاقد → فاتورة أجرة وبنود أكياس/حياكة مستقلة عند اختيارها → تسليم جزئي أو كامل → كشف عيني ومالي للعميل.
5. أكمل التقارير القابلة للتشغيل، لا بطاقات شكلية فقط:
   - إنتاج: المدخلات، النواتج، الفاقد، الاستخلاص، المتوقع مقابل الفعلي.
   - مخزون: خام، إنتاج تام، نواتج جانبية، تعبئة، حسب المستودع والحركة.
   - أمانات العملاء: رصيد العميل العيني منفصل عن قيمة الشركة.
   - تجاري/مالي: مبيعات، مشتريات، ديون، دفعات، مصروفات، تكلفة وهامش مع بيان صريح إن كانت التكلفة مرجعية وليست فعلية.
6. راجع الشاشات والتنقل: كل عملية لها نقطة دخول واضحة، صلاحيات مناسبة، حالة فارغة مفهومة، تعليمات قصيرة، ومسار رجوع. حدّث /milling/operations-guide مع أي تدفق جديد.

## متطلبات قاعدة البيانات والأمان
- اجعل كل migration صغيرة، قابلة لإعادة التطبيق، وبترتيب زمني صحيح. لا تعدل migration مطبقة في الإنتاج؛ أضف migration تصحيحية جديدة.
- افحص التواقيع الدقيقة للدوال؛ CREATE OR REPLACE لا يغيّر توقيع الدالة. احذف/استبدل النسخ المتضاربة بطريقة آمنة عند الحاجة.
- فعّل RLS واكتب سياسات صريحة لكل جدول/عرض/RPC جديد. اختبر كمستخدم دور مناسب، لا كمفتاح service_role فقط.
- لا تحذف فواتير أو حركات أو أرصدة موجودة تلقائياً. أي تنظيف بيانات يحتاج كشفاً قبل التنفيذ ومعياراً واضحاً ونسخة قابلة للاستعادة.
- لا تعيد كتابة تاريخ Git ولا تستخدم force push/rebase/amend للمنشور.

## الاختبارات والتسليم
- لكل مرحلة: نفّذ npm run build، فحص TypeScript إن توفر، وgit diff --check.
- نفّذ migrations على قاعدة بيانات اختبار/مرتبطة وتحقق باستعلامات حقيقية من الجداول وRPC، مع تسجيل النتائج دون أسرار.
- أضف اختبارات قبول SQL أو آلية للسيناريوهات: شراء قمح، رصيد افتتاحي، إنتاج مع فاقد، بيع منتج متتبع، طحن للغير، تخزين للغير، تسليم جزئي، منع السعر المزدوج، منع التسليم الزائد، وفصل ملكية العميل.
- لا تقل "النظام جاهز" قبل تمرير قائمة القبول كاملة. عند وجود قرار تجاري غير محسوم، اعرض الخيارات والأثر وتوقف عنده فقط؛ غير ذلك نفّذ باستقلالية.
- في كل طلب دمج: اذكر ما تغير، ما اختبر، ما بقي، وأي ترحيل أو إجراء يدوي مطلوب. حافظ على كل فرع في حالة بناء ناجحة.

ابدأ الآن بالخطوة 1: اقرأ المصادر، افحص الوضع الحالي، وأنشئ فجوة تنفيذية دقيقة؛ ثم نفّذ أعلى فجوة خطورة في فرع صغير دون انتظار موافقة إضافية إذا لم يتطلب الأمر قراراً تجارياً جديداً.
```
