# خطة مرحلية لتوحيد صفحات السجلات

> **استخدم هذا الملف كتعليمات تشغيل مستقلة** كلما طُلب من وكيل تنفيذ توحيد صفحة سجلات مثل الموردين أو العملاء أو المنتجات أو المخزون أو المبيعات. يُطبّق على الواجهة المستهدفة وعلى المكونات المشتركة التي تستخدمها، مع الحفاظ على منطق المجال والصلاحيات. اقرأه كاملًا قبل البدء.
>
> الملف يكمل التدقيق التفصيلي في [UNIFIED_RECORD_LISTS_AUDIT_AND_REPAIR_PLAN_AR.md](UNIFIED_RECORD_LISTS_AUDIT_AND_REPAIR_PLAN_AR.md)، لكنه يحتوي ما يلزم لبدء تنفيذ توحيد صفحة بشكل مستقل.

## 1. المهمة والنتيجة المطلوبة

وحّد بنية عرض السجلات بحيث تدعم الشاشة، بحسب ما يناسبها، أوضاع:

1. **بطاقات:** عرض سريع وملائم للهاتف، للمعلومات الأساسية والإجراءات الأكثر استخدامًا.
2. **قائمة:** صفوف كثيفة للمسح السريع ومقارنة السجلات.
3. **جدول كلاسيكي:** أعمدة قابلة للفرز وعرض تفاصيل أدق، باستخدام `DataTable` المشترك متى كان مناسبًا.

يجب أن تكون واجهة البحث والفلترة والترتيب والإضافة وحالات التحميل والخطأ والفراغ متسقة، وأن تكون سلوكيات التخزين المؤقت وRealtime صحيحة ومختبرة. التوحيد يعني **مشاركة الهيكل والتفاعل والتصميم**، وليس فرض الحقول أو الاستعلامات أو قواعد الأعمال نفسها على كل الكيانات.

## 2. تعليمات بدء الوكيل

قبل التعديل:

1. اقرأ [AGENTS.md](../AGENTS.md) وهذا الملف. إذا كان هناك ملف تدقيق تفصيلي، اقرأ [خطة التدقيق والإصلاح](UNIFIED_RECORD_LISTS_AUDIT_AND_REPAIR_PLAN_AR.md) أيضًا.
2. افحص الصفحة المطلوبة وكل المكونات والـhooks والـquery keys التي تستخدمها فعليًا. تحقق من الشيفرة الحالية ولا تعتمد على أسماء أو أرقام أسطر من وثائق قديمة.
3. اكتب ملخصًا قصيرًا لخط الأساس: طرق العرض الحالية، query ومصدر البيانات، الفلاتر والفرز والعدد، الصلاحيات، عمليات الصف، مفاتيح Query، Realtime، واستخدام كل مكوّن مشترك.
4. حدّد لكل ملاحظة تصنيفها: **مشترك**، **خاص بالصفحة**، **سلوك مجال متعمد**، أو **يحتاج تحققًا/قياسًا**. لا تغيّر سلوك المجال لتجميل الواجهة.
5. شغّل أو سجّل حالة typecheck وlint والاختبارات قبل التعديل حتى يمكن فصل العيوب السابقة عن الجديدة.

### قيود لا يجوز تجاوزها

- لا تغيّر schema أو migrations أو RLS أو RPC أو سياسة حذف/ترحيل سجلات إلا إذا كانت المشكلة تتطلب ذلك بوضوح، وكان التغيير مطلوبًا ومختبرًا ضمن نطاق المهمة.
- لا تضع منطق قاعدة البيانات أو Supabase أو Realtime داخل مكوّن العرض العام.
- لا تعرض بيانات حساسة، مثل التكلفة أو الأرصدة أو بيانات العملاء، لمستخدم لا يملك الصلاحية. إخفاء العنصر في الواجهة ليس بديلًا عن التحقق الخادمي وRLS.
- لا تضف قناة Realtime ثانية أو hook cache موازيًا إذا كان هناك اشتراك قائم على المفتاح نفسه.
- لا تسمّ ذاكرة Query أو localStorage «Offline معاملاتية». لا تغيّر عمليات الكتابة لتصبح محلية/غير متصلة دون تصميم منفصل.
- لا تحذف مكوّنًا لأنه يبدو غير مستعمل قبل البحث عن كل الاستخدامات والـimports الديناميكية وفحوص build.
- لا تنفذ ترحيلًا جماعيًا لكل الشاشات في خطوة واحدة. ابدأ بالصفحة المطلوبة ثم اختبر صفحة مختلفة المجال عند تعديل مشترك.

## 4. الخطة المرحلية

### المرحلة 0 — خط أساس واكتشاف

1. احصر ملفات الصفحة ومصادر البيانات والـquery keys واستعمالات `TableToolbar` و`DataTable` وRealtime.
2. احصر الفلاتر والفرز والعدادات وما إذا كانت محلية أو خادمية، وحدد نطاق النتائج الذي يراه المستخدم.
3. احصر حالات الصلاحيات: تكلفة/رصيد/حذف/إضافة/تعديل، وأي اختلاف حسب الدور أو المنشأة أو المستودع.
4. شغّل baseline للفحوص، ثم قِس إذا أمكن: طلبات التحميل الأولى، طلبات الإثراء، عدد الصفوف المرئية، وأي تكرار طلبات عند التمرير أو Realtime.
5. سجّل عيوبًا مؤكدة منفصلة عن فرضيات تتطلب قياسًا أو بيانات إنتاج. لا تعرض تقديرات الأداء كقياسات.

**بوابة الانتقال:** لا تبدأ ترحيل markup حتى يتضح من يملك بيانات الصفحة، وما هي العقود المشتركة التي ستستخدمها، وأي السلوكيات مجالّية يجب أن تبقى كما هي.

### المرحلة 1 — تخزين Query والأمان

1. أنشئ/حدّث Query key factory typed للكيان، مع مفاتيح واضحة مثل `all`, `list`, `detail`, `count`, و`lookups` حسب الحاجة الفعلية.
2. أدرج في key كل قيمة تغير النتيجة: الشركة/المستأجر إذا كان متعددًا، الفرع/المستودع، البحث، الفلاتر، sort، cursor، أو نطاق التاريخ. لا تضع بيانات سرية في المفتاح.
3. عالج logout وتبديل المستخدم/الشركة: امسح أو افصل cache للبيانات الحساسة قبل عرض الشاشة التالية. تحقّق من lifecycle الفعلي لـAuth وQueryClient في التطبيق واختبر تبديل الهوية.
4. بعد كل mutation، أبطل المفاتيح المتأثرة فقط؛ لا تعِد تحميل metadata الثابتة أو كل صفحات التطبيق دون سبب.
5. لا تُضف persisted cache دون تصميم عزل المستخدم/الشركة والإصدارات والتنظيف وحماية البيانات وبيان حداثة البيانات. لا تعتبر Query cache وحدها Offline.

**اختبارات المرحلة:** مستخدم A يسجل خروجًا، ثم مستخدم B يدخل في نفس التطبيق؛ لا تظهر بيانات A حتى مع `staleTime` أو placeholder data. تغيير أي filter أو warehouse لا يعيد بيانات query مختلفة من cache خاطئة.

### المرحلة 2 — Realtime موثوق وقابل للتشخيص

1. استخدم مسارًا واحدًا متفقًا عليه، غالبًا `useRealtimeTable` أو مدير اشتراك مركزي. افحص كل مستهلكي الجدول قبل تغيير hook.
2. عرّف lifecycle: إنشاء القناة، حالة الاشتراك، أخطاء القناة، reconnect، cleanup على unmount، والنطاق/الفلتر المناسب للمنشأة عند الحاجة.
3. عرّف سياسة تحديث cache لكل شكل: array، infinite pages، joins، والصفوف المفلترة. لا تدمج payload خامًا في شكل cache غني من دون mapper typed.
4. اختر بين patch موثوق وinvalidation/re-fetch. إذا استُخدما معًا، وضّح لماذا ومتى وكيف لا يتضاعف العمل. لا تعتمد على إعادة جلب كل الصفحات لكل حدث قبل قياس ذلك.
5. إذا دُمجت الأحداث/debounce، اعتبر الحدث إشارة للمصالحة مع مصدر الحقيقة لا سجلًا مضمونًا لكل تغيير. أعد التوفيق بعد عودة الاتصال حتى لا تضيع تغييرات أثناء الانقطاع.
6. امنع الاشتراكات المكررة للـ(schema, table, scope) نفسه إن كان هناك تكرار مثبت، مع تنظيف مرجعي يمنع إغلاق اشتراك ما زال مستخدمًا.

**اختبارات المرحلة:** INSERT/UPDATE/DELETE، دفعة أحداث سريعة، update لصف خارج filter، تغيير فرز أو صفحة، payload ناقص للعلاقات، انقطاع/عودة WebSocket، وفك الصفحة أثناء انتظار debounce. افحص عدد refetchات والشبكة وcache النهائي.

### المرحلة 3 — مكونات العرض المشتركة

1. اعتمد مكوّنًا مركبًا واحدًا لهيكل السجلات، مثل تطوير `ListPage` أو إنشاء `RecordsPage`؛ تجنب بناء ثالث بجانب `DataTable` و`TableToolbar`.
2. اجعل الشريط المشترك مسؤولًا عن العرض والتفاعل العام فقط: search input، filter panel/chips، sort preset، action slots، view toggle، عدد النتائج، refresh عند الحاجة. النصوص العامة يجب أن تتبع i18n.
3. اجعل `RecordsView` يدير `cards | list | table` وحالات skeleton/refreshing/error/empty/load-more. لا يظهر اختيار لوضع غير مدعوم في الصفحة.
4. مرر renderers/slots typed لبطاقات وصفوف كل كيان؛ اترك أسماء الحقول وترتيبها ومحتواها للصفحة. اجعل أفعال الصف والصلاحيات واضحة، واستخدم `stopPropagation` عند وجود clickable row.
5. أعد استخدام `DataTable` للوضع الجدولي. اختر مالكًا واحدًا للفرز: لا تجعل parent و`DataTable` يرتبان البيانات نفسها مرتين، ووحّد حالة header مع sort preset.
6. ثبّت `onLoadMore` أو استخدم ref داخليًا لتجنب إعادة إنشاء `IntersectionObserver` كل render. امنع duplicate fetch إذا ظل sentinel ظاهرًا.
7. استخدم tokens/مكونات النظام للحاويات والمدخلات والأزرار والحالات؛ لا تنقل markup صفحة كاملة إلى ملف جديد من دون إزالة الاقتران بمنطق الأعمال.
8. قيّم virtualization بالقياس إن كانت الصفحات قد تراكم فيها عدد كبير من DOM rows. لا تضف مكتبة أو تغيّر دلالات الجدول دون اختبار sticky/RTL/keyboard/print.

**بوابة الانتقال:** اختبر مكوّن العرض الجديد أولًا في الشاشة المطلوبة ثم في شاشة مختلفة المجال قبل إعلان أن تغييره آمن لكل المستخدمين.

### المرحلة 4 — البحث والفلترة والفرز والصفحات

1. قرر محلي أم خادمي بالاستناد لحجم البيانات واحتياج الشاشة. المحلي مقبول لمجموعة صغيرة معروفة؛ ليس صحيحًا أن يعلن اكتمال النتائج عند تحميل 50 سجلًا فقط.
2. إذا كانت محلية: سمّ نطاق البحث والعداد بوضوح، واحمِ الأداء عند تراكم الصفحات. لا تخلط total database count مع matches أو loaded count.
3. إذا كانت خادمية: كل criteria المؤثرة في Query key؛ debounce للطلبات وليس للكتابة المرئية، تجاهل النتائج القديمة، ابدأ cursor جديدًا عند تغير المعايير، وأعد count بنفس صلاحيات وفلاتر النتيجة.
4. اجعل sort stable بعمود tie-breaker فريد مثل id. اختبر nulls والقيم الرقمية والنصوص العربية وlocale.
5. عالج مخاطر offset pagination عند إدراج/حذف صفوف أثناء التصفح؛ قيّم cursor/keyset إذا كانت البيانات كبيرة أو تتغير بكثرة.
6. عرّف معنى كل filter/quick chip من بيانات المجال الفعلية. لا تسمِّ “له حد أدنى” بأنه “منخفض المخزون” إذا لم تقارن الكمية بالحد.

### المرحلة 5 — ترحيل صفحة السجلات المستهدفة

نفّذ بالتسلسل:

1. احفظ query والـmutations الحالية واختبر سلوكها قبل تغيير العرض.
2. عرّف type للسجل، أعمدة الجدول، card/list renderers، حالات البيانات، actions، الصلاحيات، empty state، وسياسة الفلترة/الفرز.
3. مرر هذه التعريفات للمكونات المشتركة دون إدخال منطق Supabase أو أسماء حقول الكيان إلى `RecordsView` أو `TableToolbar`.
4. حافظ على كل عمليات CRUD والـRPC والتحقق والحذف الآمن. إذا نقلتها إلى hook، احفظ signature وسلوك الخطأ وأضف اختبارات لها.
5. أزل markup المكرر بعد التأكد من نقل كل action والحالة، لا قبل ذلك. أزل imports غير المستخدمة حسب ESLint/TypeScript، لا بالانطباع.
6. افحص accessibility وRTL/mobile وpermission gating في كل وضع، لا في الجدول فقط.

#### عند تنفيذ صفحة الموردين تحديدًا

- اقرأ [suppliers route](../src/routes/_app.suppliers.tsx) واستخرج query والمفاتيح والـpermissions ومصدر الأرصدة وعمليات الإضافة/التعديل والحذف.
- استخدم toolbar/records shell العام بعد تثبيت عقده؛ لا تنشئ `SupplierToolbar` و`SupplierTable` يعيدان نفس الواجهة.
- عرّف renderer خاصًا بالمورد، ولا تعرض رصيدًا أو تفاصيل مالية إلا للمصرح لهم. تحقق إن كان الرصيد لكل منشأة/عملة/تاريخ أو نطاق آخر.
- تأكد أن الفلترة والعدادات تحترم RLS ومعايير query نفسها، وأن عمليات CRUD لم تتغير بسبب إعادة الهيكلة.

#### عند تنفيذ صفحة المنتجات تحديدًا

- وحّد كل مداخل الإضافة، بما فيها الإضافة السريعة وفتح النموذج من barcode، على تحقق quota/access واحد.
- تحقق من أن `low_stock` يقارن quantity حقيقيًا مع الحد، وإلا غيّر التسمية لتصف ما يُحسب فعليًا.
- اجعل إجمالي المنتجات والنتائج المطابقة والصفوف المحمّلة مفاهيم منفصلة. عالج محلية البحث على الدفعات أو انقلها للخادم حسب المتطلب والحجم.
- عالج ترتيب الصفحات بإضافة tie-breaker ثابت، وقيّم cursor pagination إذا كان مناسبًا.
- عالج submit بحيث ينتهي saving حتى عند رفض الوعد أو انقطاع الشبكة (`try/finally` أو mutation typed).
- افحص جدوى تحميل product compatibility مع كل دفعة؛ حمّله lazy/detail-only إذا ثبت عدم حاجة الأسطح الأساسية إليه.

## 5. معايير القبول النهائية

لا تعتبر المهمة منجزة إلا بعد تحقق ما ينطبق من البنود التالية:

### التوحيد والتصميم

- تستخدم الشاشة المستهدفة مكوّن toolbar وعرض سجلات مرجعيين، ولا تكرر مكوّنًا عامًا موجودًا باسم جديد.
- لا تعرض الشاشة وضع cards/list/table غير منفذ؛ إذا كان وضع ما مدعومًا، يشارك نفس الصفوف والصلاحيات والأفعال وحالات التحميل.
- وجود معلومات كل كيان في renderers/slots الخاصة به، بينما layout العام والسلوك العام في shared components.
- التصميم يعمل على هاتف وtablet وdesktop، في RTL وLTR، ولا يسبب قص الأزرار أو أعمدة وهمية أو تراكب sticky controls.
- الأزرار قابلة للاستخدام بلوحة المفاتيح ولها `aria-label` عند كونها أيقونات، والضغط على إجراء الصف لا يفتح تفاصيل الصف بطريق الخطأ.

### الدقة والبيانات

- كل عداد يوضح هل هو إجمالي خادمي، نتائج مطابقة، أم صفوف محملة؛ لا توجد تسميات مضللة.
- search/filter/sort يعمل على النطاق المعلن، ومفتاح cache يضم كل المعايير المتغيرة.
- لا تكرار أو فقد سجلات عند التنقل بين الصفحات أو عند وصول event أثناء تحميل الصفحة التالية.
- أي filter متعلق بمخزون/رصيد/حالة يستخدم المعنى الصحيح من مصدر موثوق، لا حقلًا قريب الاسم فقط.
- الصلاحيات نفسها قبل وبعد في البطاقة والقائمة والجدول والتفاصيل والـactions.

### الأداء والكاش وRealtime

- طلب أول صفحة محدود بالأعمدة والصفوف المطلوبة؛ لا توجد N+1 غير مبررة ولا enrichment لا يستخدمه السطح.
- لا يعاد إنشاء observer/channel عند كل render بلا حاجة، ولا تتكرر طلبات fetch next page.
- Realtime يؤدي إلى cache نهائي صحيح، وإلى عدد requests مقصود ومختبر؛ توجد reconciliation بعد reconnect.
- logout/switch لا يكشف بيانات user/tenant سابق من cache؛ اختبار التبديل يمر.
- لا توجد وعود Offline غير مدعومة من التطبيق أو من هذه الشاشة.
- عند تراكم سجلات كثيرة، توجد نتيجة قياس وقرار صريح حول virtualization/server paging؛ لا يعتمد القرار على التخمين.

### التحقق البرمجي

- typecheck وESLint والاختبارات ذات الصلة ناجحة؛ لا توجد أخطاء جديدة ذات صلة في Problems/build.
- الاختبار اليدوي/Browser covers: loading أولي، refresh، خطأ وإعادة محاولة، empty، فلتر بلا نتائج، load-more، كل وضع عرض، actions، RTL، صلاحيات مختلفة.
- بعد تعديل shared components، تُراجع شاشة ثانية على الأقل تستخدمها لاكتشاف regression.
- التقرير الختامي يسرد الملفات المشتركة والملفات الخاصة بالصفحة وسبب كل تغيير ونتائج الاختبارات والقيود غير المحلولة.

## 6. مصفوفة الاختبارات المطلوبة

| المجال | السيناريوهات الدنيا | النتيجة المتوقعة |
|---|---|---|
| Toolbar | بحث فارغ/موجود، clear، filter apply/reset/remove chip، sort preset، add action، toggle view | حالة التحكم والـbadge والنتيجة متزامنة؛ لا نصوص لغة مختلطة أو عناصر غير عاملة. |
| صفحات البيانات | صفر/صفحة واحدة/أكثر من صفحة؛ filter/sort يتغير أثناء fetch | لا duplicate/missing rows؛ الفلاتر والفرز على النطاق المعلن؛ sentinel لا يطلق طلبات مكررة. |
| Realtime | insert/update/delete، أحداث سريعة، صف يخرج من filter، update joins، reconnect | cache يتطابق مع المصدر الرسمي بعد reconcile؛ لا صف خام ناقص يستقر، وعدد fetches محدود ومقصود. |
| الهوية | logout ثم login بمستخدم آخر؛ تبديل tenant/company/warehouse إن كان مدعومًا | لا بيانات/عدادات من نطاق قديم؛ keys وreset صحيحة. |
| الصلاحيات | أدوار لها/ليس لها رؤية التكلفة أو الرصيد أو الحذف | لا تسرب في أي عرض أو detail أو query؛ action ممنوع لا ينفذ backend operation. |
| حالات الواجهة | initial loading، background refresh، error/retry، empty dataset، empty filtered result | الحالات مميزة ومتسقة، والبيانات القديمة لا تُعرض على أنها نتائج جديدة دون توضيح. |
| Responsive/Accessibility | 320–390px، tablet، desktop، RTL/LTR، keyboard فقط | لا قص/تراكب؛ focus مرئي، labels مفهومة، modal focus/escape صحيح. |
| نموذج الكتابة | نجاح، validation، تعارض unique، Promise rejection/timeout، النقر المكرر | saving يكتمل/يتحرر دائمًا؛ لا تكرار كتابة؛ رسالة خطأ آمنة؛ invalidate keys المناسبة فقط. |

## 7. شكل التقرير النهائي للوكيل

في الرد بعد التنفيذ استخدم هذا الترتيب:

1. **الملخص:** ما الذي توحّد وما بقي خاصًا بالكيان.
2. **المكونات المشتركة المعدلة:** السلوك السابق/الجديد والصفحات التي قد تتأثر.
3. **الصفحة المستهدفة:** query/عدادات/بحث/فلترة/فرز/عروض/أفعال جرى تغييرها.
4. **الكاش وRealtime:** سياسة keys/invalidation/patch/reconnect والتنظيف، وما اختُبر منها.
5. **الاختبارات:** أوامر/اختبارات فعلية ونتيجتها؛ صرّح إذا لم يمكن تشغيل قياس أو اختبار إنتاج.
6. **المتبقي:** مخاطر، قيود، مكونات بديلة لم تُحذف، أو متابعة تحتاج تغييرًا خادميًا.

لا تقل «أصلحت الأداء» دون مقارنة قابلة للتكرار أو على الأقل ذكر إصلاح محدد مثل تقليل عدد الاستعلامات أو منع observer re-creation. لا تقل «Realtime مضمون» إذا لم يُختبر reconnect والمصالحة مع الخادم.
