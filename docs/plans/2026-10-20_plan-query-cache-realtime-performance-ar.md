# خطة مراجعة وتحسين الكاش وRealtime وسرعة الصفحات

## 1. ملخص مبسط للحالة الحالية

### أين تحفظ نتائج الاستعلامات؟

- النتائج التي تجلبها صفحات النظام عبر TanStack Query موجودة في **ذاكرة التطبيق أثناء الجلسة**، وليست في `localStorage` أو قاعدة بيانات محلية دائمة.
- إعداد `QueryClient` المركزي موجود في `src/router.tsx`، ويقدمه جذر التطبيق عبر `QueryClientProvider` في `src/routes/__root.tsx`.
- القيم العامة الحالية: `staleTime = 2 minutes`، و`gcTime = 15 minutes`، وإعادة المحاولة للأخطاء العابرة حتى 3 مرات، وإعادة الجلب عند عودة الاتصال، وعدم إعادة الجلب عند التركيز على النافذة.
- يوجد `localStorage` لأشياء منفصلة، مثل إعدادات الطباعة واللغة وبعض الكاشات/التفضيلات وبيانات المصادقة. **هذا لا يعني أن قوائم المنتجات والعملاء والفواتير محفوظة كلها محلياً.**
- مفاتيح الاستعلام في `src/lib/query-keys.ts`: بعضها قديم ومسطح مثل `QUERY_KEYS.customers` وبعضها factories منظمة مثل `productKeys.list()` و`customerKeys.list()`.

### ماذا يحدث عند مغادرة الصفحة والعودة؟

- عند مغادرة صفحة، غالباً يخرج مكوّن الصفحة من العرض وينفك اشتراك realtime الذي أنشأه ذلك المكوّن. تبقى نتيجة React Query في الذاكرة إلى أن تُزال أو تمر مدة `gcTime` (15 دقيقة من عدم الاستخدام).
- إذا رجع المستخدم قبل أن تصبح البيانات stale، تعرض الصفحة الكاش فوراً غالباً من دون طلب جديد.
- إذا كانت البيانات stale (بعد دقيقتين افتراضياً)، يمكن أن تظهر البيانات المحفوظة أولاً ثم يجري تحديث بالخلفية عند تفعيل observer الصفحة.
- إذا لم تعد الصفحة مستخدمة مدة `gcTime` وانتهت بياناتها من الكاش، يجلبها التطبيق من جديد.
- بما أن subscription مرتبط بصفحة نشطة، قد تفوت تلك الصفحة تغييرات قاعدة البيانات أثناء غيابها. عند العودة قد تبقى نسخة الكاش القديمة حتى تصبح stale أو يحصل invalidation آخر. هذه فجوة يجب اختبارها وإغلاقها بسياسة عودة/reconcile واضحة.

### أين ينفذ التحديث اللحظي؟

| الطبقة               | مسؤوليتها                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Supabase/Postgres    | تفعيل بث تغييرات الجداول في Realtime publication، تطبيق صلاحيات الوصول/RLS، وإرسال أحداث INSERT/UPDATE/DELETE للمشتركين المصرح لهم.  |
| كود React في المتصفح | فتح قناة Supabase على جدول/نطاق، استقبال الحدث، تحديد cache key المتأثر، تحديث الكاش أو إبطاله، ثم إعادة جلب البيانات عند الحاجة.    |
| React Query          | الاحتفاظ بنتيجة الاستعلام في ذاكرة الجلسة، عرضها، تحديد freshness، إعادة الجلب، ودمج invalidation التي تطلبها mutations أو Realtime. |

Realtime ليس «ميزة تضغطها في Supabase فتحدث كل صفحات التطبيق وحدها». يجب إعداد الجدول في جهة Supabase، ويجب أن يشترك كود العميل في القناة الصحيحة ويحدث المفتاح الصحيح.

## 2. ما وجدناه في الكود

- يوجد hook مشترك `useRealtimeTable` في `src/lib/realtime.ts`. يعالج الأشكال المدعومة من cache، ويستطيع patch للصف أو invalidation حسب الإعداد، ثم يعيد المصالحة مع بيانات الخادم.
- الصفحات التي تستخدم `useRealtimeTable` حالياً تشمل المنتجات، العملاء، الموردين، المخزون، الفواتير، التحويلات، المستودعات والدفعات؛ الاستخدام مؤكد في 8 routes.
- المصروفات لها hook خاص `useExpenseRealtime` في `src/hooks/use-expenses.ts` ويعمل بنمط invalidation مجمّع.
- نقطة البيع لديها قناة يدوية متعددة الجداول في `src/routes/_app.pos.tsx` وتحدّث state محلية مباشرة، منفصلة عن QueryClient المشترك.
- صفحات مثل لوحة التحكم والتنبيهات وبعض صفحات المشتريات لا يظهر أنها تستخدم hook Realtime مشتركاً لكل البيانات المعروضة؛ بعضها يعتمد على staleTime، عودة الاتصال، أو invalidation محلي بعد mutations.
- `ConnectionBanner` في `src/components/ui/connection.tsx` يعيد جلب الاستعلامات النشطة عند عودة الاتصال أو بطلب المستخدم؛ هذا لا يعيد تشغيل كل الاستعلامات غير النشطة، ولا يعوض إعداد الاشتراك أو المزامنة لكل route.
- `useRealtimeTable` ينشئ قناة ضمن عمر المكوّن، ويزيلها عند unmount. لا يوجد حالياً دليل على مدير قنوات عام يملك اشتراكاً واحداً للتطبيق بأكمله.
- hook المشترك يحدث الكاش ثم يطلب reconciliation/invalidation. هذا يساعد على إبقاء الشاشة سريعة وصحيحة، لكنه قد يسبب طلبات إضافية؛ يجب قياسه وتحديد متى يكفي patch آمن ومتى يلزم refetch.
- query cache يمسح مفاتيح بيانات الأعمال عند تبديل الهوية/الخروج عبر `clearSessionQueryCache` في `src/lib/query-keys.ts` وربطه في `src/lib/auth.tsx`. هذه حماية مهمة لأن كثيراً من المفاتيح ليست scoped بهوية المستخدم.
- لم يظهر في البحث ضمن SQL migrations تعريف واضح لإضافة الجداول إلى `supabase_realtime` publication. يجب التحقق من إعداد Supabase المنشور ومقارنته بالمستودع؛ لا نفترض أن كل جدول مضاف أو أن التغيير يحتاج migration قبل هذا التحقق.
- توجد خطة إصلاح سجلات أسبق في `docs/plans/2026-10-08_plan_unified-record-lists-repair.md` تحذر من الاعتماد على payload خام للصفوف الغنية، التكرار بين subscriptions، وأن Query cache ليس مخزناً Offline. هذه الخطة تُكملها ولا تنشئ hook منافساً.

## 3. الجواب المباشر عن أسئلتك

### هل كل شيء تمام حالياً؟

ليس بالكامل. إعداد الكاش الأساسي موجود ومنظم نسبياً، وهناك hook realtime مشترك جيد كبداية، لكن التغطية ليست لكل الصفحات، والاشتراك غالباً ينتهي عند مغادرة صفحة القائمة. لذلك التحديث اللحظي مضمون فقط في الصفحات التي تشترك وهي نشطة، وليس لكل التطبيق في كل وقت.

### هل الكاش محلي؟

نعم، نتائج React Query محفوظة في ذاكرة JavaScript أثناء تشغيل التطبيق. الإعدادات أعلاه تحدد متى تعتبر قديمة ومتى تُحذف. لا يوجد persisted query cache عام، ولذلك إعادة تحميل التطبيق أو إغلاقه لا تعني استرجاع كل قوائم الأعمال من localStorage.

### إذا خرجت من واجهة ورجعت، هل يرجع من الكاش؟

غالباً نعم إذا بقي الاستعلام في ذاكرة الجلسة ولم تنتهِ مدة الاحتفاظ به. إذا ما زال fresh يعرضه دون انتظار طلب؛ إذا أصبح stale يعرضه ثم يحدّثه بالخلفية؛ وإذا انتهت مدة الاحتفاظ أو مسح الكاش يجلبه من قاعدة البيانات. أي realtime فات أثناء غياب الصفحة يحتاج reconcile عند الرجوع؛ لا يجوز افتراض أن Supabase يعيد الأحداث القديمة تلقائياً.

### هل Realtime من Supabase أم من الكود أم مكوّن موحد؟

هو تعاون بينهما: Supabase يجهز publication ويرسل الحدث، والعميل يفتح subscription، و`src/lib/realtime.ts` يوفر hook مشتركاً لبعض الصفحات، ثم React Query يحدّث cache/refetch. **ليس مفعلاً مرة واحدة لكل النظام حالياً.** كما توجد استثناءات مثل POS والمصروفات، وصفحات لا تشترك مباشرة.

## 4. الأهداف والقرارات المعمارية

1. مصدر البيانات الرسمي يبقى Supabase/Postgres. Cache وRealtime وسائل لسرعة وتحديث العرض، وليسا قاعدة البيانات الأصلية ولا ضماناً لتسليم كل حدث.
2. إنشاء طبقة Realtime مشتركة واحدة لإدارة عمر القنوات وتوثيق حالتها، لكن الاشتراكات تبقى حسب المجال والجدول والصفحات/الاستعلامات المستخدمة؛ **لا نشترك عشوائياً في جميع الجداول لكل مستخدم**.
3. تظل hooks المجال مالكة لتعريف الاستعلام والمفتاح وشكل البيانات، بينما مدير Realtime المشترك يتولى القناة والتنظيف وإعادة الاتصال والتجميع. لا يوضع Supabase داخل مكوّن الجدول المرئي.
4. لكل query key عقد typed يضم محددات النتائج المؤثرة: الشركة/النطاق، المستودع، الفلاتر، البحث، sort، والصفحة/cursor حسب الحاجة.
5. قرارات patch/refetch تكون لكل شكل cache:
   - patch مباشر فقط عندما تكون payload كاملة ويمكن تحديث الصف والترتيب والعداد بأمان.
   - invalidation/refetch عند صفوف joins/aggregates أو إدخال لا يمكن تحويله إلى شكل العرض.
   - تجميع bursts في نافذة قصيرة، ثم طلب reconcile واحد لكل مفتاح متأثر؛ لا إعادة جلب شامل لكل QueryClient عند كل event.
6. قنوات جميع المسارات ذات البيانات الخاصة تراعي الصلاحيات ونطاق الشركة/المستأجر. RLS وقاعدة البيانات تبقيان خط الدفاع النهائي؛ إخفاء الصف في React لا يكفي.
7. تبديل مستخدم/شركة يمسح البيانات الحساسة ويوقف الاشتراكات السابقة قبل تحميل النطاق الجديد.
8. أي Persisted Cache مستقبلي قرار مستقل، وليس جزءاً تلقائياً من Realtime. يلزمه tenant/auth/version scoping، إبطال آمن، بيان عمر البيانات، ومعالجة حذف/تعارض؛ لا يستخدم لبيانات مالية حساسة قبل اعتماد ذلك.

## 5. خطة التحسين المرحلية

### المرحلة 0: تدقيق قابل للقياس

- جرد queries ومفاتيحها ومالكها ومصدر Supabase والjoins ومحددات الشركة/المستودع ووقت stale.
- جرد الاشتراكات الحالية مع جدول Supabase والقناة والصفحة وعمرها وآلية cleanup والـquery key أو state التي تعدلها.
- فحص Supabase Dashboard/CLI للـRealtime publication المنشور ومقارنته بالمigrations، مع التأكد من RLS وReplica Identity حيث يلزم DELETE payload. لا تُجرى تغييرات قاعدة قبل إثبات النقص.
- قياس تحميل بارد/دافئ، عدد requests عند التنقل، عدد subscriptions المفتوحة، events/refetches لكل burst، وحجم الصفحات.
- عدم تغيير production data أو migrations في مرحلة التدقيق.

**مخرج المرحلة:** جدول تغطية لكل مجال: query، cache key، realtime، reconnect، permissions، ونتيجة اختبار العودة للصفحة.

### المرحلة 1: توحيد المفاتيح ودورة الجلسة

- اعتماد key factories الموجودة (`productKeys`, `customerKeys`, إلخ) تدريجياً وتوثيق المفاتيح القديمة التي يجب التوافق معها.
- فصل keys للـlist/detail/lookups/summary/count؛ لا تُبطل بيانات lookup ثابتة عند كل تحديث سجل إذا لم تتأثر.
- تضمين نطاق الشركة والمستودع/الفلاتر المؤثرة، أو إثبات أن التطبيق single-tenant في كل session. إبقاء `clearSessionQueryCache` واختبار المستخدم A → logout → المستخدم B.
- اختبار تغيّر filter/sort/search/cursor حتى لا تعرض query key نتيجة محددات قديمة.

### المرحلة 2: مدير Realtime مشترك

- تطوير `src/lib/realtime.ts` ليعلن status موحداً: connecting/subscribed/error/closed/reconnecting، مع callbacks قابلة للاختبار وcleanup موثوق.
- إضافة registry/config typed يحدد الجداول والkeys والمجالات المسموح الاشتراك بها، ومحول payload لكل query enriched.
- استبدال/احتواء الاشتراك اليدوي في POS وhook المصروفات عند اعتماد parity وظيفي؛ لا تحذف أي implementation قبل اختباره ومقارنة سلوكه.
- منع subscriptions المكررة لنفس `(schema, table, scope)` عبر reference counting فقط إذا أكد الجرد وجود تكرار فعلي. تجنب topic عشوائي لكل rerender ومراعاة قيود Supabase على أسماء القنوات.
- التحقق من إعداد publication على Supabase؛ الجداول اللازمة فقط تضاف، وبآلية versioned/migration معتمدة إن كان ذلك مطلوباً.

### المرحلة 3: سياسة أحداث صحيحة وخفيفة

- لكل جدول: تحديد هل الحدث يعمل patch أم invalidate. اختبر INSERT لا يطابق الفلتر أو يقع خارج الصفحة الأولى، UPDATE يغيّر sort/filter field، DELETE/old payload، والعدادات.
- للـinfinite lists: لا يُضاف raw row إلى صفحة غنية بالjoins. إذا لم يوجد mapper آمن، أجّل العرض الدقيق إلى refetch مع إبقاء snapshot القديمة مرئية.
- تجميع عدة أحداث إلى reconcile واحد لكل key؛ الاستماع لا يعني طلباً لكل حدث ولا refetch لكل الصفحة إن أمكن patch صحيح.
- عند انقطاع الاتصال: عرض حالة اتصال واحدة واضحة؛ عند استعادة القناة وبعد mount/visibility، نفذ reconcile محدوداً للمجال النشط لتعويض الأحداث المفقودة. لا تفترض replay تلقائياً.
- mutation محلية: optimistic update فقط مع rollback واضح، ثم تأكيد الخادم وتوحيد query cache؛ عند نجاح mutation لا تكرر refetch إذا mutation ردت الشكل المعتمد بشكل كامل.

### المرحلة 4: نشر التغطية حسب الأولوية

1. المخزون والمنتجات، مع مستودع/فلتر tenant ومجاميع/count منفصلة.
2. المبيعات والمشتريات والتحصيلات، مع الأحداث التي تغير الأرصدة وملخصات dashboard.
3. العملاء والموردون والتحويلات والدفعات.
4. المصروفات والصفحات المالية والتقارير: invalidate عند الحاجة لمجاميع/دفاتر مشتقة بدلاً من patch صف غير كافٍ.
5. Dashboard والتنبيهات: اعتماد keys لمصادر المقاييس، وتحديد refresh contract. لا تشترك الصفحة في كل الجداول إذا كان invalidation عبر domain events أقل تكلفة.
6. POS: ترحيل القناة اليدوية تدريجياً بعد إثبات تطابق سلوك المخزون/المنتجات/العملاء الحالي.

### المرحلة 5: قياس الأداء واعتماد سياسة الكاش

- إعداد مستويات staleTime حسب نوع البيانات: lookups الثابتة، قوائم العمل النشطة، الرصيد/المؤشرات، وتفاصيل المستندات؛ لا تستخدم قيمة واحدة لكل المجالات.
- مراقبة freshness: عرض وقت آخر تحديث/حالة قديمة للبيانات الحساسة عند فشل reconnect، مع زر إعادة محاولة موجه إلى key/mجال محدد.
- قياس stale refetch عند العودة إلى الصفحة وعدد الطلبات الفعلية. الإعدادات الحالية `refetchOnWindowFocus: false` مقصودة لأجهزة POS؛ أي تغيير لها يكون حسب المجال ولا يُعمم بلا تجربة.
- ضبط `placeholderData` بعناية: إبقاء الصفحة السابقة بصرياً لا يعني أن البيانات الجديدة صحيحة للفلاتر أو المستخدم الحالي؛ أظهر loading/refreshing ولا تخلط نتائج نطاقين.
- لا تضف persisted cache عاماً في هذه المرحلة. إذا ثبتت حاجة offline لبيانات معينة، تُصمم كمستودع offline منفصل محدود ومراجعته الأمنية مستقلة.

## 6. اختبارات ومعايير القبول

### ذاكرة الاستعلام والتنقل

- query cold load ثم الانتقال إلى صفحة أخرى والعودة قبل دقيقتين: تعرض snapshot cached ولا تنفذ request غير لازم.
- العودة بعد staleTime: تبقى الواجهة مستجيبة وتحدث بالخلفية، وتعرض freshness/error بوضوح.
- العودة بعد gcTime أو بعد reload: يجلب الخادم البيانات؛ لا تدّعي وجود persisted cache.
- تبديل المستخدم/الشركة: لا تظهر بيانات النطاق السابق ولو لحظة بعد تبديل الهوية.

### Realtime والاتصال

- كل حدث INSERT/UPDATE/DELETE يحدّث key الصحيح أو يبطله مرة واحدة، ولا يكرر row ولا يترك joined fields فارغة.
- تغيير حقل filter/sort/tenant يؤدي reconcile صحيحاً، والعداد والصفحات تبقى متسقة.
- burst من عدة تغييرات ينتج reconcile مجمّعاً لا storm.
- مغادرة الصفحة تزيل القناة، والعودة تعيد الاشتراك وتعمل reconcile ابتدائياً/عند استعادة القناة لتعويض الأحداث الفائتة.
- offline ثم online، channel error/timeout، logout وتبديل الشركة، وفتح أكثر من مكوّن مشترك لنفس الجدول.
- RLS تمنع وصول مستخدم إلى أحداث بيانات غير نطاقه؛ لا توجد قناة واسعة غير مفلترة دون توثيق قرار أمني.

### الأداء

- قياس requests في انتقال صفحتين، ثم العودة، وبعد mutation، وبعد burst Realtime.
- قياس حجم payload ومدة أول عرض وrender time مع دفعات منتجات متعددة.
- معايير أولية تعتمد baseline المرحلة 0؛ لا تُعتمد أرقام تحسين افتراضية من دون قياس قبل/بعد على نفس البيانات والجهاز.

## 7. المخرجات والقرارات

- مخطط يوضح: Supabase publication/RLS → Realtime client/channel → shared registry/hook → domain query keys → React Query cache → page components.
- جدول تغطية الصفحات والقنوات بعد التنفيذ.
- توثيق stale/gc لكل domain، سياسة patch/invalidate، وحالة reconnect.
- اختبارات regression، ونتائج baseline/after للطلبات وزمن العرض وعدد القنوات.
- توثيق ما بقي غير فوري أو ما يتطلب database publication/RLS changes، وعدم الادعاء بمزامنة durable أو offline معاملية.

**تعريف الإنجاز:** المستخدم يرى snapshot cached بسرعة عند العودة، وتُراجع freshness وفق سياسة المجال؛ التحديث اللحظي يصل للصفحة النشطة عبر قناة مصرح بها ويحدّث cache key الصحيح، والفقد أثناء انقطاع/غياب الصفحة يُعالج بـreconcile من الخادم، مع عدم فتح اشتراك عالمي واسع أو تكرار قنوات بلا حاجة.
