# ملاحظات أمان ترحيلات قاعدة البيانات وحماية البيانات (Database Migration & Safety Notes)

> **المشروع:** Market Hub (Vortex ERP)  
> **حالة قاعدة البيانات:** لا يتم إجراء أي حذف أو تعديل أو تفريغ لجداول أو سجلات الشركة الحقيقية (Strictly Zero Data Loss).

---

## 1. الحالة والجاهزية الفنية

تم إعداد ملفات الترحيل الإضافية لتكون **تراكمية وآمنة تماماً (Additive & Idempotent)**:
- التطبيق يعمل بسلاسة بوجودها أو بدونها، حيث تتولى وحدة الأمان `src/lib/safety.ts` اكتشاف وجود الدوال أو الرجوع التلقائي للاستعلامات المباشرة.
- **لم يتم حذف أو تعديل أي سجلات حقيقية في قاعدة البيانات نهائياً.**

---

## 1.1 ✅ الجلسة الأخيرة — إغلاق أربع ثغرات (2026-09-29)

هذه أربع مشاكل حقيقية اكتُشفت بعد كتابة هذا المستند، وأُصلحت كلها. **لم تُلمس أي
قاعدة بيانات — كل العمل في ملفات SQL.**

### 🔴 أ) أخطر ما وُجد: `20260916000000` كانت تُرقّي **أي** حساب إلى سوبر أدمن

رأس الملف كان يقول إن جمعه «مطابِق لصفر صفوف على مشروع جديد فهو غير ضار». **هذا
خطأ**: عبارة `DELETE ... WHERE email = '...'` لا تطابق شيئاً، لكن **`INSERT INTO
`auth.users` التي بعدها تُنشئ الحساب من الصفر على كل قاعدة جديدة** — ثم تُمنح
superadmin. أي: كل عميل جديد يصبح فيه ذلك البريد سوبر أدمن المنصة.

**الإصلاح:** على قاعدة أنشأها الترحيل نفسه، يعمل كما كان (وهذا مطلوب). على قاعدة
فيها أي حساب حقيقي، يخرج فوراً. الترقية صارت **مشروطة بإثبات أن الحساب من صنع
الترحيل** (`encrypted_password IS NULL` + بلا صف في `auth.identities`).

### 🔴 ب) قائمة منح الدوال ناقصة — تكسر أي نشر جديد

`20260929000200` ختمت التطبيق بـ`REVOKE ... FROM PUBLIC, anon` ثم أعادت المنح
لقائمة أسماء **مكتوبة يدوياً**. القائمة أسقطت:

| الدالة | ما ينكسر |
|---|---|
| `search_products` | قائمة المنتجات (بحث/فرز/صفحات) |
| `customer_ledger_balance` | كشوفات حسابات العملاء |
| `has_role` / `is_staff` | **كل سياسات RLS على جداول المستأجر** |
| `warehouse_reference_counts` | حارس حذف المخازن |

ولا يمكن أن تشمل أي دالة تُضاف لاحقاً من الـDashboard.

**الأثر عندك: لا شيء** — الدوال مُطبَّقة مسبقاً والمنح القديمة باقية. **الأثر على
نشر جديد: التطبيق يعمل ثم يفشل في التشغيل** بـ`permission denied for function`.

**الإصلاح:** `20260929000400` يمنح `authenticated` **ديناميكياً لكل الدوال**،
فلا يمكن أن تصبح القائمة «ناقصة دالة» مرة أخرى.

### 🔴 ج) `ALTER DEFAULT PRIVILEGES` كان يكسر تسجيل الدخول

`20260929000200` كانت تنفّذ `REVOKE EXECUTE ON FUNCTIONS FROM anon` — وهي لا
تنحصر في دوال كاتبها، بل تُعيد كتابة صف الـdefault ACL للمخطط كله، فيسقط `anon`
من المنح الافتراضية ويفشل تسجيل الدخول:

```text
500 {"error_code":"unexpected_failure","msg":"Database error querying schema"}
```

ثم `20260929000300` أصلحت الـdefault فقط، **وتركَت** سحب `has_role`/`is_staff`
الصريح فعّالاً — فبقي مسار التحقق مكسوراً. علاوة على ذلك، سحب `PUBLIC` يُخفي كل
دالة جديدة عن `service_role` (يُعطّل Edge Functions).

**الإصلاح:** حُذفت جملتا `ALTER DEFAULT PRIVILEGES`، والمنح أصبح صريحاً لكل دالة.
**القاعدة المستخلصة:** `ALTER DEFAULT PRIVILEGES` مفتاح على مستوى المخطط كله —
يُمنع أن يُستخدم للتعبير عن «هذه الدالة خاصة». للتخصيص: `REVOKE` صريح.

### 🔴 د) `is_staff` كانت تفشل **مفتوحة** لا مغلقة

`20260918000200` سطر 41 كان: `COALESCE((SELECT is_active ...), true)` — أي أن
مستخدم **بلا صف `profiles`** يُعتبر **نشطاً**. وهذا عكس نية الملف تماماً: حذف
الملف الشخصي كان يزيد الصلاحية. صُحّح إلى `false` في `20260929000400`.

### 🟠 هـ) الترتيب المدمّر — الآن محروس بالكامل

| الترحيل | الحارس المضاف |
|---|---|
| `20260912111000` | `sales_invoices` فارغة **+** لا حساب حقيقي (بمطابقة البريد) |
| `20260916000000` | `user_roles` فارغة + ترقية مشروطة |
| `20260915030000` | `DO UPDATE` ← `DO NOTHING` |
| `20260917200000` | `DO UPDATE` ← `DO NOTHING` (٣ مواضع) |

**لماذا `DO NOTHING`:** الحمولة متطابقة في كل الحالات، فالـ`UPDATE` لم يكن يشتري
شيئاً — إلا **إلغاء سحبٍ متعمّد** (`is_active = false`) عند التشغيل التالي. الآن
سحب صلاحية المنصة **دائم**. تحقّق: لا يوجد أي `DO UPDATE SET role = 'superadmin'`
في المستودع.

### 🟠 و) الـSeed — فُصل فعلياً

| الملف | يُشغَّل تلقائياً؟ | المحتوى |
|---|---|---|
| `seeds/reference.sql` 🆕 | ✅ نعم (في `config.toml`) | تصنيفات مصروفات + وحدات قياس فقط |
| `seeds/demo.sql` (نُقل من `seed.sql`) | ❌ لا | 56 صنفاً + 20 عميلاً + 10 فواتير + حركات مخزون |
| `seeds/demo_users.sql` | ❌ لا | حسابات تجريبية |

**قبل:** `config.toml` كان يوجّه إلى ملف واحد فيه الاثنان معاً — فأي `db reset` على
مشروع عميل يزرع فواتير وهمية و**يستبدل هوية الشركة** (`company_settings`).
**بعد:** المرجعي فقط يعمل تلقائياً.

## 2. تصحيح خطأ بناء جملة سابق في الترحيلات

أثناء محاولة تشغيل `npx supabase db push`، ظهر الخطأ التالي:

```text
syntax error at or near "USING" (SQLSTATE 42601)
```

### السبب الجذري:
في الترحيل `20260917200000_link_superadmin_user_and_permissions.sql`، تم إنشاء سياسة إدخال `INSERT` باستخدام جملة `USING`:

```sql
CREATE POLICY tenant_subscriptions_insert ON public.tenant_subscriptions
  FOR INSERT TO authenticated
  USING (public.is_platform_admin(auth.uid()))   -- غير صالح لعمليات INSERT في PostgreSQL
  WITH CHECK (public.is_platform_admin(auth.uid()));
```

في PostgreSQL، تقبل سياسات `INSERT` فقط جملة `WITH CHECK`، بينما تطبق `USING` على `SELECT` و `UPDATE` و `DELETE`. وجود هذا الخطأ كان يحجب تنفيذ أي ترحيل تالٍ.

**الحل المطبق:** إزالة جملة `USING` غير الصالحة والإبقاء على `WITH CHECK` لضمان تحقق الهدف الأمني الأصلي ("فقط مسؤولو المنصة يمكنهم إضافة اشتراكات") دون التأثير على أي جدول أو سياسة أخرى.

## 4. ما لم يتم لمسه مطلقاً (Explicitly NOT Touched)

- لا تغيير في مخطط أي جدول حالي، ولا حذف لأي جدول أو عمود أو إعادة تسميته.
- لا تعديل على علاقات المفاتيح الأجنبية (Foreign Keys).
- لا مساس بسياسات أمان الصفوف (RLS Policies).
- لم يتم تشغيل أي أمر `seed` أو `reset` أو `truncate` أو `drop` أو حذف جماعي.
- ملفات SQL التجريبية (`docs/seed/yemen_grocery_seed.sql`, `docs/seed/yemen_stationery_seed.sql`) لم يتم تشغيلها مطلقاً.

## 5. ملاحظة هندسية لمرحلة قادمة: الحذف التعاقبي (Cascade Deletion)

يحتوي مخطط قاعدة البيانات الحالي على قيود:
```sql
inventory.product_id REFERENCES products(id) ON DELETE CASCADE
stock_movements.product_id REFERENCES products(id) ON DELETE CASCADE
```

يقوم حارس الحذف في الواجهة (`product_delete_guard` و `src/lib/safety.ts`) بمنع حذف أي صنف له حركات مخزنية أو فواتير، مما يسد الثغرة البرمجية عبر التطبيق.  
ولكن لتحقيق الأمان المؤسسي التام داخل قاعدة البيانات نفسها، يوصى مستقبلاً بتحويل القيد من `ON DELETE CASCADE` إلى `ON DELETE RESTRICT` ضمن مهمة منفصلة ومعتمدة لمنع الحذف العرضي في حال تنفيذ أوامر SQL يدوية مباشرة.

## 6. قواعد إلزامية للترحيلات (Migration Rules — Contract)

Vortex ERP يُنشر على **مشروع Supabase مستقل لكل عميل**. هذا الواقع وحده يفرض
الفصل التالي: أي شيء خاص بعميل واحد، أو بمطوّر واحد، أو بلحظة زمنية واحدة،
**يُمنع** أن يعيش داخل سلسلة الترحيلات التي يعيد تشغيلها كل عميل قادم.

```
┌──────────────────────────────────────────────────────────────────┐
│ 1. SCHEMA           → supabase/migrations/*.sql                  │
│    جداول، أعمدة، مفاتيح أجنبية، فهارس، قيود، enums، دوال،        │
│    triggers، سياسات RLS. يُعاد تشغيلها على كل مشروع جديد.        │
├──────────────────────────────────────────────────────────────────┤
│ 2. REFERENCE DATA   → supabase/seeds/reference.sql               │
│    صفوف يحتاجها التطبيق ليعمل: أدوار، صلاحيات، وحدات،            │
│    تصنيفات مصروفات افتراضية. Idempotent. بلا بيانات تجريبية.     │
├──────────────────────────────────────────────────────────────────┤
│ 3. DEMO / TEST DATA → supabase/seeds/demo.sql  (لا يعمل تلقائياً)│
│    منتجات وعملاء وفواتير وهمية. اختياري صراحةً.                  │
├──────────────────────────────────────────────────────────────────┤
│ 4. AUTH BOOTSTRAP   → خارج الترحيلات تماماً                      │
│    إنشاء أول مستخدم عبر Auth Admin API، ثم منح الأدوار.          │
│    يحتاج مفتاحاً سرياً → يعمل خارج قاعدة البيانات، يدوياً، مرة    │
│    واحدة لكل نشر.                                                │
└──────────────────────────────────────────────────────────────────┘
```

### 6.1 لماذا إنشاء المستخدمين ليس ترحيلاً؟

المستخدمون **ليسوا مخططاً (schema)**. أربعة أسباب ملموسة:

1. الترحيل يعمل بصلاحية كلمة مرور قاعدة البيانات، لا عبر Auth API. الكتابة
   مباشرة في `auth.users` / `auth.identities` تتجاوز دفتر حسابات GoTrue
   الداخلي — وهو أسلوب غير مدعوم رسمياً.
2. يحتاج **كلمة مرور نصية صريحة داخل ملف في Git** → تسريب دائم لكل من ينسخ
   المستودع.
3. يربط النظام **ببريد شخص واحد**. العميل الجديد سيرث حساباً غريباً عنه.
4. لا يمكن أن يكون Idempotent بمعنى مفيد: "أنشئ المستخدم إن لم يوجد" إما
   تُنشئ هويات مكررة أو تتخطى بصمت — وكلاهما غير مرغوب.

### 6.2 القواعد

| # | القاعدة | السبب |
|---|---|---|
| R1 | الترحيل = **مخطط فقط**. | البيانات تُعاد على قاعدة كل عميل. |
| R2 | البيانات المرجعية في `seeds/reference.sql`. | يجب أن تُعاد بأمان وتُراجع منفصلة. |
| R3 | البيانات التجريبية في `seeds/demo.sql` و**لا تُوصَل** بـ`config.toml` لأي عميل. | منع تلوث دفاتر العميل بفواتير وهمية. |
| R4 | **لا أسرار** في أي ملف متتبع: لا كلمة مرور نصية، لا `crypt('...')` بقيمة صريحة، لا مفاتيح. | Git دائم → التسريب دائم. |
| R5 | **لا بريد شخصي ولا UUID شخصي** داخل ترحيل. | قاعدة العميل يجب ألا تعتمد على هوية مطوّر. |
| R6 | كل جملة Seed **Idempotent** (`ON CONFLICT` على مفتاح عمل حقيقي، أو `WHERE NOT EXISTS`). | الـSeed يُعاد تشغيله. التكرار يُفسد البيانات المرجعية. |
| R7 | كل جدول مرجعي يحتاج **مفتاح عمل مستقر** (`code` / `slug` / `key`)، و`ON CONFLICT` يستهدفه **لا** UUID عشوائي. | UUID ثابت هشّ وغير مقروء؛ مفتاح العمل مفهوم وقابل للمراجعة. |
| R8 | لا تُعدّل ترحيلاً مُطبّقاً على Remote إلا لتحييد جملة ضارة **مع الإبقاء على الإصدار**. | تعديل ترحيل مُطبّق يُحدِث Drift. |
| R9 | **يُمنع** `supabase db reset` على مشروع مرتبط. | أمر مُدمّر: يُسقط القاعدة ويعيد بناءها. |
| R10 | ترحيل واحد = غرض واحد، صغير وباسم واضح. | الترحيلات العملاقة هي سبب الفوضى الحالية. |
| R11 | كل ترحيل جديد يُختبر على **قاعدة فارغة** و**قاعدة قائمة** معاً. | الترحيل الذي يعمل على إحداهما فقط قنبلة موقوتة. |
| R12 | أي `DROP` / `TRUNCATE` / `DELETE FROM` يحتاج تبريراً مكتوباً وملاحظة Backup في رأس الملف. | يُجبر الكاتب على التفكير والمراجع على الرؤية. |
| R13 | لا تُجرِّب على مشروع عميل أو Production. | بديهي، ويُخالَف كثيراً. |
| R14 | إعدادات العميل (اسم الشركة، العملة، الضريبة، الشعار) **إعداد تطبيق**، لا ترحيل. | كل عميل له قيم مختلفة. |

### 6.3 قواعد مستخلصة من عطل المصادقة (29 سبتمبر 2026)

> خلفية كاملة مع الأدلة: `docs/database/تقرير-جلسة-إصلاح-المصادقة.md`.

| # | القاعدة | السبب |
|---|---|---|
| R15 | **لا تُدرج في `auth.users` بـ`INSERT` مباشر.** استخدم `auth.admin.createUser()` — أو إن اضطررت، مرّر أعمدة الرموز الخمسة (`confirmation_token`, `recovery_token`, `email_change`, `email_change_token_new`, `email_change_token_current`) صريحة كـ`''`. | هذه الأعمدة `NOT NULL DEFAULT ''` في مخطط Supabase، وGoTrue يقرأها في متغيرات `string` بلغة Go. Go لا تمثّل `NULL` كنصّ، فعمود واحد فارغ يُسقط كل قراءة للمستخدمين: `sql: Scan error ... converting NULL to string is unsupported` — ويفشل تسجيل الدخول واستعادة كلمة المرور وقائمة المستخدمين وحذفهم بـ500. |
| R16 | **`ALTER DEFAULT PRIVILEGES` مفتاح على مستوى المخطط كله، لا على دالة واحدة.** يُمنع استخدامه للتعبير عن «هذه الدالة خاصة». | `REVOKE ... FROM anon` في الـdefault ACL يسحب `anon` من المنح الافتراضية للمخطط كله فيكسر تسجيل الدخول (`Database error querying schema`)، و`REVOKE ... FROM PUBLIC` يُخفي كل دالة جديدة عن `service_role` فيُعطّل Edge Functions. للتخصيص: `REVOKE` صريح على الدالة. |
| R17 | **أي دالة تُستدعى داخل سياسة RLS يجب أن تكون قابلة للتنفيذ من الدور الذي يُقيّمها — بما فيه `anon`.** | السياسة تُقيَّم بدور المستدعي، وقبل وجود جلسة يكون الدور `anon`. سحب EXECUTE عن `has_role`/`is_staff` يجعل GoTrue يفشل بـ`permission denied for function has_role` عند تسجيل الدخول. |
| R18 | **الدوال التي تقرأ جدولاً لا يجوز أن تكون محجوبة بسياسة ذلك الجدول.** استخدم `SECURITY DEFINER` + سياسة self-read لحالة الـbootstrap. | `platform_admins_select USING (is_platform_admin(auth.uid()))` يخلق دائرة: قراءة الصف تتطلب دالة تقرأ نفس الجدول، فيعود الاستعلام فارغاً ويُعطّل الواجهة بصمت. |
| R19 | **`ON CONFLICT DO UPDATE` يُحيي حالة مسحوبة.** إن كانت الحمولة متطابقة استخدم `DO NOTHING`. | تعديل `platform_admins` بـ`DO UPDATE SET is_active = true` يجعل سحب صلاحية سوبر أدمن **غير دائم** — الترحيل التالي يُعيدها. |
| R20 | **القيمة البديلة في `COALESCE` داخل دالة صلاحيات يجب أن تكون `false`.** | `COALESCE((SELECT is_active FROM profiles WHERE id = _user_id), true)` كان يجعل مستخدماً **بلا صف `profiles`** يُعتبر **نشطاً** — أي أن حذف الملف الشخصي يزيد الصلاحية بدل أن ينقصها. |
| R21 | **قائمة منح مكتوبة يدوياً تتقادم بصمت.** المنح تكون ديناميكية أو مُولَّدة من الكتالوج. | `REVOKE ... ALL FUNCTIONS` ثم إعادة منح **قائمة أسماء مكتوبة يدوياً** أسقطت `search_products` و`has_role` و`is_staff` — فالتطبيق يُثبَّت ثم يفشل في التشغيل بـ`permission denied`, ولا يمكن للقائمة أن تشمل دالة تُضاف لاحقاً. |
| R22 | **الحارس البنيوي مقدَّم على التوثيق.** إن كان خطأ فئة ما ممكناً بنيوياً، ضع ضابطاً في قاعدة البيانات (trigger/constraint/policy) لا ملاحظة في ملف. | الترحيلات لا «تتذكّر» شروطاً خارج مسؤوليتها. `normalize_auth_user_token_columns` يمنع تكرار عطل المصادقة بغض النظر عن كاتب الترحيل التالي. |

## 7. نتائج التدقيق (Audit Findings)

### 7.1 🔴 تسريب كلمة مرور داخل الترحيلات — **تم الإصلاح**

`20260916000000_reset_and_recreate_superadmin_user.sql` و
`20260926000000_update_superadmin_password.sql` كانا يقومان بتشفير **كلمة مرور
نصية صريحة** مكتوبة مباشرة في ملف SQL، ويستهدفان **بريداً شخصياً**.

**الأثر:** كلمة المرور مقروءة لأي شخص لديه وصول للمستودع، وتُعاد على أي قاعدة
تصل إليها هذه الترحيلات.

**الإجراء المتخذ:** حُوّل الملفان إلى No-op ولا يُنشئان أي اعتماد. **أُبقيت
أرقام الإصدارات** حتى لا يحدث Drift في
`supabase_migrations.schema_migrations`.

> 🔴 **يجب عليك تنفيذه (يدوي):** إبطال/تغيير كلمة المرور من Supabase
> Dashboard. حذفها من الملف **لا يُبطلها** — فهي ما زالت في تاريخ Git
> للكوميتات المرفوعة مسبقاً.

### 7.2 🔴 الهوية الشخصية داخل سلسلة الترحيلات — **مُحيَّد جزئياً**

الترحيلات `20260911150300`, `20260912111000`, `20260912172000`,
`20260916000000`, `20260926000000` تحتوي بريداً شخصياً ثابتاً. على مشروع عميل
**جديد** هذه الجمل تُطابق صفر صفوف فتكون غير ضارة، لكنها ليست النمط الصحيح
للمستقبل.

**المتخذ:** إزالة الاعتمادات + توثيق النية في رأس كل ملف.
**المتبقي:** الإشارات النصية للبريد باقية للحفاظ على تطابق التاريخ؛ وإنشاء
أول مسؤول انتقل إلى خطوة منفصلة (§9).

### 7.3 🔴 ترحيلات `TRUNCATE` / `DELETE` مُدمّرة داخل السلسلة — **موثّقة، لم تُحذف**

| الترحيل | المحتوى المدمّر |
|---|---|
| `20260706121000_blackbox_reset_and_seed_yemen.sql` | `TRUNCATE` + إدخال بيانات |
| `20260911150300_blackbox_reset_and_seed` | Reset + مستخدم شخصي |
| `20260912111000_reset_for_meters_shop.sql` | `TRUNCATE` لـ25 جدولاً `CASCADE` ثم `DELETE FROM auth.users` |
| `20260912172000_seed_meters_shop_users.sql` | إنشاء مسؤول شخصي |

**أخطر ما في المستودع.** أمر `TRUNCATE ... CASCADE` على 25 جدولاً أعمال
متبوعاً بـ`DELETE FROM auth.users` يعمل تلقائياً على أي بيئة لم يُطبَّق فيها
الإصدار بعد — بما فيها مشروع عميل جديد.

**لماذا لم تُحذف:** مُطبَّقة فعلاً على المشروع المرتبط. حذفها مع بقاء
إصداراتها في `schema_migrations` يُنتج خطأ
*"remote migration versions not found in local migrations directory"* ويحجب
كل `db push` مستقبلي.

**الإجراء الموصى به (يحتاج قرارك):** لا تحذفها. أضف **حارساً (Guard)** في رأس
كل ترحيل مدمّر ليعمل فقط على قاعدة فارغة:

```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM public.sales_invoices LIMIT 1) THEN
    RAISE EXCEPTION
      'Refusing destructive reset: sales_invoices is not empty. '
      'Historical migration. See docs/database/migration-safety-notes.md';
  END IF;
END $$;
```

**لم يُطبَّق تلقائياً** — لأنه يعدّل ترحيلات مُطبَّقة. انظر §11.

### 7.4 🟠 ملف Seed يخلط المرجعي بالتجريبي وبالاعتمادات — **مفتوح**

`supabase/seeds/seed.sql` (موصول بـ`config.toml`) يحتوي في ملف واحد:
صفوف مرجعية + **بيانات تجريبية** + **إدخالات في `auth.users`/`profiles`**.

**الأثر:** كل `db reset` يزرع بيانات أعمال وهمية في قاعدة المطوّر، وملف واحد
يخلط دورة حياة المرجعي بدورة حياة التجريبي.

**الإجراء الموصى به:** فصله إلى `seeds/reference.sql` (Idempotent) و
`seeds/demo.sql` (اختياري)، وتوجيه `config.toml` للأول فقط.
**لم يُطبَّق تلقائياً** — لأنه يغيّر سلوك التطوير المحلي ويجب قراءة الملف
كاملاً أولاً.

### 7.5 🟡 حالة CLI المحلية متتبعة في Git — **تم الإصلاح**

`supabase/.temp/` (11 ملفاً) كان متتبعاً، فيسرّب `project-ref` و
`linked-project.json` و`pooler-url`، ويُنتج فروقات بين الأجهزة.

**المتخذ:** `git rm --cached supabase/.temp` (بقي الملف على القرص) + إضافة
`supabase/.temp/` إلى `.gitignore`.

### 7.6 🟡 Drift في تاريخ الترحيلات — **مكتشف**

`npx supabase migration list --linked` أظهر الإصدار
`20260928000000` **مطبّقاً على Remote**. هذا الترحيل **موجود في المستودع**
ومُدمج. إن أبلغ CLI المحلي أنه Remote-only، فالسبب نسخة عمل قديمة — أعد تشغيل
الأمر بعد `git pull`.

**لا تُصلح هذا بتعديل التاريخ.** الحل الآمن دائماً: تأكد أن الملف موجود محلياً
→ تأكد أن صف الإصدار موجود على Remote → إن صحّ الاثنان فلا شيء يحتاج إصلاحاً.

### 7.7 🟠 قيم الحالات وطرق الدفع مكتوبة نصاً في الواجهة — **مفتوح**

طرق الدفع والحالات تُقارَن كنصوص (`"cash"`, `"split"`, `"paid"`, `"pending"`)
في ملفات كثيرة. هذا يكرّر enum القاعدة في طبقة التطبيق، فأي إضافة قيمة
للـenum تتطلب مسحاً يدوياً، وأي خطأ إملائي يفشل بصمت.

**الإجراء الموصى به:** وحدة مشتركة واحدة (`src/lib/domain/payment.ts`) تُصدّر
اتحاد الأنواع وخرائط التسميات، مع تعليق يقول إن enum القاعدة هو المصدر الوحيد
للحقيقة. **لم يُطبَّق تلقائياً** — لأنه يمس POS والكشوفات والتقارير والفواتير،
ويستحق مراجعة منفصلة.

## 8. متى Enum، ومتى جدول مرجعي، ومتى ثابت في الكود؟

السؤال الحاكم: **هل يمكن للعميل أن يغيّر هذه القيمة أو يضيف إليها بشكل مشروع؟**

### 8.1 PostgreSQL ENUM — فقط لمجموعة مغلقة ونادرة التغيير

يُستخدم فقط عند تحقق الثلاثة معاً: المجموعة صغيرة ومغلقة فعلاً، والتطبيق له
منطق صريح يتفرّع على كل قيمة، وإضافة قيمة تعني تغيير كود أصلاً.

| Enum | الحكم | السبب |
|---|---|---|
| `public.payment_method` | **يبقى enum** | التطبيق يتفرّع لكل وسيلة؛ الإضافة تغيير كود. لاحظ أن `split` أُضيفت لاحقاً بـ`ALTER TYPE ... ADD VALUE` — وهي الطريقة الصحيحة الآمنة. |
| `public.*_status` | **يبقى enum مع الحذر** | القيم مكررة كنصوص في الواجهة (انظر §7.7). الـenum صحيح؛ النصوص هي المشكلة. |

> ⚠️ **تحذير Enum:** `ALTER TYPE ... ADD VALUE` لا يعمل داخل كتلة Transaction
> في إصدارات PostgreSQL الأقدم، والقيمة الجديدة غير قابلة للاستخدام في نفس
> الـTransaction. أضف قيم الـenum في ترحيل **مستقل**، كما يفعل
> `20260928000000`.

### 8.2 جدول Lookup / Reference — للمجموعات القابلة للتوسّع لكل عميل

| المفهوم | الحكم | السبب |
|---|---|---|
| `units` | **جدول مرجعي + صفوف لكل عميل** | محل يبيع بالقطعة/المتر، وآخر بالكيلو/اللتر. يجب أن يكون قابلاً للتوسّع. |
| `categories`, `brands` | **بيانات عميل، لا Seed** | محتوى العميل نفسه؛ تُزرع فقط كمجموعة بداية اختيارية. |
| `expense_categories` | **جدول مرجعي بنطاق العميل** | الافتراضيات مفيدة، وكل نشاط يضيف تصنيفاته. |
| `roles` / `permissions` | **جدول مرجعي (مملوك للنظام)** | يحددها نموذج صلاحيات التطبيق، لكنها مخزّنة في جدول لأن سياسات RLS واستعلامات الأدوار تقرؤها علائقياً. |

### 8.3 ثوابت التطبيق — ما يجب ألا يكون في القاعدة أصلاً

- قائمة الجداول المحمية بـRLS،
- ربط مسار الواجهة بالصلاحية المطلوبة،

هذه تُكتب في الكود **بشرط** أن تُقرأ من **مكان واحد**. انظر §7.7.

## 9. إنشاء أول مسؤول (الطريقة الصحيحة)

### 9.0 الواقع الفعلي في هذا المستودع — كيف يُنشأ المستخدمون؟

هذا القسم يُقرأ أولاً، لأن هناك **ثلاثة مسارات مختلفة** وإنشاء المستخدم لم يكن
موضعاً واحداً — وهذا سبب الالتباس.

| المسار | الكود | يُنشئ `auth.users`؟ | يمنح دوراً؟ |
|---|---|---|---|
| تسجيل دخول | `src/routes/auth.tsx` | ❌ **لا يوجد `signUp` في المشروع** | عبر `bootstrap_first_owner` |
| موظف من داخل النظام | `_app.users.tsx` → Edge Function `admin-create-user/index.ts` | ✅ `auth.admin.createUser` | ✅ `user_roles` |
| حساب المالك على نشر جديد | `20260916000000` (مشروط) | ✅ `INSERT INTO auth.users` | ✅ owner + (superadmin مشروط) |

**النتيجة المهمة:** في التطبيق **لا توجد شاشة تسجيل (sign-up)**. الملف
`src/routes/auth.tsx` فيه `signInWithPassword` فقط. لذلك:

- **الموظفون** يُنشَؤون من شاشة المستخدمين داخل النظام → Edge Function →
  `auth.admin.createUser`. هذا هو **المسار المدعوم رسمياً من Supabase** (كلمة
  المرور لا تمر بالمستودع أبداً، ولا تُخزَّن).
- **حساب المالك** على نشر جديد يُنشأه `20260916000000` مشروطاً (انظر §1.1-أ).

**الفارق العملي:** إنشاء المستخدم في ترحيل ليس «ممنوعاً» مطلقاً، لكنه لا يُدعم
رسمياً (تجاوز دفتر GoTrue) ويتطلب كلمة مرور تُكتب في Git — وهذا ما منعتَه القاعدة
R4. الطريقة الصحيحة تحلّ الشيئين: `auth.admin.createUser` عبر Edge Function.

### 9.1 الطريقة الصحيحة يدوياً (إن أردت حساباً بعينه)

نفّذها مرة واحدة لكل نشر، والمفتاح السري لا يخرج من تلك الجلسة:

1. **أنشئ المستخدم** من Supabase Dashboard → Authentication → Users →
   *Add user*، واكتب كلمة المرور هناك (**لا تمر بالمستودع أبداً**)، وأكّد
   البريد.
2. **امنح دور المنصة.** صف `platform_admins` وصف `user_roles` هما ما يجعل
   الحساب سوبر أدمن:

   ```sql
   -- استبدل <USER_UUID> بالمعرّف الظاهر في Authentication → Users
   INSERT INTO public.platform_admins (user_id, role, is_active, mfa_required)
   VALUES ('<USER_UUID>', 'superadmin', true, false)
   -- DO NOTHING لا DO UPDATE: لا تُحيي سحباً متعمداً.
   ON CONFLICT (user_id) DO NOTHING;

   INSERT INTO public.user_roles (user_id, role)
   VALUES ('<USER_UUID>', 'owner')
   ON CONFLICT (user_id, role) DO NOTHING;
   ```

3. **تحقق** بتسجيل الدخول من التطبيق والتأكد من وصول شاشات السوبر أدمن.

## 11. الأوامر

**فحص (آمن، قراءة فقط):**

```bash
npx supabase migration list --linked      # مقارنة الإصدارات محلياً/عن بُعد
npx supabase db diff --linked             # هل المخطط الحقيقي متقدم عن الترحيلات؟
npx supabase db pull --linked --dry-run   # ماذا سيلتقط الـbaseline؟
```

**تطبيق الترحيلات (آمن، تراكمي — غير مُدمّر بذاته):**

```bash
npx supabase db push
```

**🔴 يُمنع تماماً على مشروع مرتبط:**

```bash
npx supabase db reset     # يُسقط القاعدة ويعيد بناءها. فقدان بيانات.
```

## 12. قائمة تحقق لأي ترحيل جديد

- [ ] مخطط فقط — لا بيانات عميل، لا بيانات تجريبية، لا أسرار.
- [ ] لا بريد شخصي، لا UUID شخصي، لا اسم مستخدم.
- [ ] محمي / Idempotent (`IF NOT EXISTS`، `ON CONFLICT`، أو حارس صريح).
- [ ] غرض واحد، واسم واضح.
- [ ] رأس الملف يشرح ماذا ولماذا.
- [ ] أي `DROP`/`TRUNCATE`/`DELETE` مُبرَّر في الرأس.
- [ ] مُختبر على قاعدة فارغة **و** نسخة من قاعدة قائمة.
- [ ] قيم الـenum في ملف ترحيل مستقل.
- [ ] مُراجع لتحديث هذا المستند إن غيّر سياسة.
