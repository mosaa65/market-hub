المستودع (ملفات SQL) فقط، والتحقق كان بالتحليل الساكن للكود.

### 🔴 المشكلة ١ — تصعيد صلاحيات حيّ داخل Trigger التسجيل

**الملف:** `20260915030000_superadmin_user_and_strict_subscription_rls.sql`
**الموضع:** السطر ٢٤ داخل دالة `handle_new_user()`

```sql
IF LOWER(NEW.email) = 'mousa.mc13@gmail.com' THEN
  INSERT INTO public.user_roles      ... 'owner'
  INSERT INTO public.platform_admins ... 'superadmin'
END IF;
```

**لماذا هذا أخطر مما يبدو — ليس مسألة تجميلية:**

1. **قاعدة تصعيد تعمل على كل تسجيل مستقبلي.** من يملك ذلك البريد يصبح سوبر أدمن
   تلقائياً. على قاعدة عميل، ذلك البريد يخص شخصاً آخر — **شخص ثالث يصبح سوبر أدمن
   لقاعدة العميل لحظة تسجيله.**
2. **لا يمكن إبطالها.** حذف صف `platform_admins` لا يفيد — التسجيل التالي يعيد
   إنشاءه. القاعدة في الـTrigger لا في البيانات.
3. **غير مرئية للتطبيق.** لا توجد شاشة تقول "هذا البريد يرتفع تلقائياً"، فلا
   يستطيع أي مشغّل تدقيقها أو تعطيلها.

**الأثر الإضافي:** `20260915030000` أعاد إنشاء الدالة بـ`CREATE OR REPLACE`، وهذا
**يصفّر صلاحيات التنفيذ (ACL)** التي كان `20260621011959` قد سحبها عمداً — أي أن
الترحيل ألغى تصليباً أمنياً سابقاً بصمت. (تحققت من هذا فعلاً في السجل.)

---

### 🔴 المشكلة ٢ — خلط مفاهيمي: مالك الشركة = سوبر أدمن المنصة

**الملف:** `20260917200000_link_superadmin_user_and_permissions.sql`

الدوال لم تكن تعبّر عن "مدير منصة" بل عن *"مدير منصة **أو** أي مالك شركة"*:

```sql
-- is_platform_admin / is_platform_superadmin — كلا الدالتين
SELECT EXISTS (SELECT 1 FROM platform_admins WHERE ...) 
  OR EXISTS (SELECT 1 FROM user_roles WHERE role = 'owner');   -- ← الخلل هنا
```

**النتائج الفعلية:**

1. **كل مالك شركة هو سوبر أدمن منصة.** على نشر متعدد العملاء، مالك العميل (أ)
   يحقّق سياسات مستوى المنصة. أي سياسة مكتوبة "لمديري المنصة فقط" تشمله.
2. **`platform_admins` توقّف عن كونه مصدر الحقيقة.** منح أو سحب دور منصة **لا أثر
   له** لأي مستخدم يصادف أنه مالك — سحب superadmin من مالك يتركه سوبر أدمن.
3. **والخلط حدث على مستوى البيانات أيضاً** في نفس الترحيل:
   - ربط **كل** صاحب دور `owner` بـ`platform_admins`،
   - ثم طابق بالاسم: `full_name ILIKE '%موسى%' OR '%mousa%'`،
   - ثم طابق بالبريد: `email ILIKE '%mousa%'`.

   **المطابقة بالاسم ليست ضابطاً أمنياً — هي تخمين.**

## هـ. أي الترحيلات المعلَّقة آمنة؟ ✅ آمنة — وإليك الإثبات

فحصت كل جملة في هذا الترحيل تلمس شيئاً موجوداً:

| الجملة | التشخيص | آمنة؟ |
|---|---|---|
| `ALTER TYPE public.payment_method ADD VALUE IF NOT EXISTS 'split'` | إضافة قيمة enum في **ملف مستقل** (تصحيح مهم: `ALTER TYPE ADD VALUE` لا يعمل داخل Transaction) | ✅ آمنة |
| `CREATE TABLE IF NOT EXISTS public.customer_payment_splits` | جدول جديد، محمي بـ`IF NOT EXISTS` | ✅ آمنة |
| `CREATE INDEX IF NOT EXISTS ...` ×2 | فهارس جديدة، محمية | ✅ آمنة |
| `ALTER TABLE stock_movements ADD COLUMN IF NOT EXISTS adjustment_reason text` | **عمود جديد nullable** — لا يمس صفاً موجوداً | ✅ آمنة |
| `ADD CONSTRAINT ... CHECK (...) **NOT VALID**` | ⭐ **النقطة الحاسمة**: `NOT VALID` تعني أن القيد يُطبَّق على الكتابات المستقبلية فقط و**لا يفحص الصفوف الموجودة** — فلا يفشل ولا يوقف الترحيل | ✅ آمنة |
| `CREATE OR REPLACE FUNCTION` ×3 | إضافة دوال / overload جديد | ✅ آمنة |
| `UPDATE public.sales_invoices SET payment_method = ...` | ⚠️ **بدت خطِرة — لكنها آمنة**: هذا `UPDATE` **داخل جسم دالة** `create_sale` الجديدة. يُنفَّذ عند **استدعائها مستقبلاً**، ولا يُنفَّذ أثناء الترحيل نفسه | ✅ آمنة |
| `INSERT INTO customer_payment_splits` | ⚠️ كذلك **داخل جسم الدالة**، لا تنفيذ مباشر | ✅ آمنة |
| `DROP POLICY IF EXISTS` + `CREATE POLICY` | على جدول **جديد** فقط | ✅ آمنة |

**الخلاصة:** الترحيل **إضافي بحت (purely additive)** — لا `DELETE`، لا `TRUNCATE`،
لا `DROP TABLE`، لا تعديل جماعي لصفوف موجودة، ولا قيد يُفحص على البيانات القديمة.
مكتوب بجودة عالية ويصلح كـ**نموذج مرجعي** لبقية السلسلة.

⚠️ **لكن:** *آمن ≠ مُصرَّح بالتنفيذ.* التطبيق يحتاج موافقتك، ويجب أن يتم على
المشروع المرتبط فقط بعد التأكد من أنه ليس مشروع العميل ذا البيانات المهمة.

## ح. معمارية السوبر أدمن (Super Admin Architecture)

### النموذج الهدف (ما تم تطبيقه)

```
                    Supabase Auth
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
  Normal Tenant Users                Platform Super Admin
        │                                   │
   public.user_roles                public.platform_admins
   (owner/manager/                    (superadmin/admin/
    accountant/cashier/                support)
    warehouse)
        │                                   │
   نطاق الشركة — لا يمنح               نطاق المنصة — لا يمنح
   أي صلاحية منصة                      أي صلاحية شركة
```

**الفصل مضمون على مستويين الآن:**

1. **على مستوى الدوال** — `is_platform_admin` و `is_platform_superadmin` لم تعُد
   تقرأ `user_roles` إطلاقاً. (ترحيل `20260929000100`)
2. **على مستوى مسار التسجيل** — `handle_new_user()` لم يعُد يعرف بريداً ولا دوراً.
   (ترحيل `20260929000000`)

### مصفوفة الصلاحيات الناتجة

| الدور | نطاقه | يمنح صلاحية منصة؟ |
|---|---|---|
| `owner` | الشركة | ❌ لا (كان نعم — أُصلح) |
| `manager` / `accountant` / `cashier` / `warehouse` | الشركة | ❌ لا |
| `platform_admins.superadmin` | المنصة | ✅ نعم |
| `platform_admins.admin` | المنصة | ✅ نعم |
| `platform_admins.support` | المنصة (قراءة) | ❌ لا يحقّق `is_platform_superadmin` |
| `service_role` | الخدمة | ✅ (يتجاوز RLS) |

### ⚠️ تغيير سلوكي يجب أن تعرفه

بعد `20260929000100`، **كون المستخدم مالك شركة لم يعُد يمنحه أي صلاحية منصة**
(كان يمنحه سابقاً عبر جملة `OR`).

**لمنع أي مشغّل من فقدان وصوله**، الترحيل يحتوي خطوة تسوية **غير مُدمّرة (Insert
فقط، بلا أي حذف)** تُنشئ صف `platform_admins` صريحاً لكل مالك فعلي **لا يملك
صفاً بعد**. أي: **لا أحد يفقد وصوله يوم التنفيذ**، والصلاحية تتحول من *قاعدة* إلى
*بيانات* — وهي النقطة كلها: يمكنك الآن سحبها بحذف الصف.

## ط. معمارية المستخدم العادي (Normal User Architecture)

| الطبقة | الجدول | آلية الإنشاء |
|---|---|---|
| الهوية | `auth.users` + `auth.identities` | **Supabase Auth فقط** (API / Dashboard) |
| الملف الشخصي | `public.profiles` | trigger `handle_new_user()` — إنشاء صف تلقائي |
| الدور | `public.user_roles` | يُمنح صراحة؛ أول مستخدم فقط يصبح `owner` تلقائياً |

**قاعدة أول مستخدم** ( `bootstrap_first_owner()` ) آمنة بالبناء: تُفعَّل **فقط عندما
يكون `user_roles` فارغاً تماماً** — أي مرة واحدة لكل نشر — وتعتمد على *"لا توجد
أدوار بعد"* لا على *"من أنت"*. ولا تمنح أي صلاحية منصة.

## ي. خطة حماية البيانات الحقيقية

| الضمانة | كيف نُفّذت |
|---|---|
| لا وصول لأي قاعدة بيانات | كل العمل في ملفات SQL + تحليل ساكن |
| لا أمر مُدمّر | صفر `db reset` / `TRUNCATE` / `DROP` / `DELETE` |
| الترحيلات الجديدة إضافية | `CREATE OR REPLACE FUNCTION` + `INSERT ... ON CONFLICT DO NOTHING` |
| تعديل الترحيل المطبَّق | **حارس فقط** — لم أغيّر أي جملة نُفِّذت فعلاً |
| حذف المستخدمين | مُحاط بحارس: يعمل فقط إذا كانت `sales_invoices` فارغة |
| Seed لا يمس الهوية | نُقل بلوك `auth.users` إلى ملف منفصل لا يعمل تلقائياً |
| لا شيء مرفوع | كل التغييرات في مجلد العمل |

**الحارس المضاف على `20260912111000` — قبل كل عملية خطِرة:**

```sql
DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM public.sales_invoices LIMIT 1) THEN
    RAISE EXCEPTION 'Refusing destructive reset (20260912111000): ...';
  END IF;
END $$;
```

**الأثر:** إذا وُجد فاتورة واحدة، **يفشل الترحيل بصوت عالٍ** بدل أن يمسح القاعدة.
ولا يُضعف سلوكه الأصلي على القاعدة التي نُفِّذ عليها (فهي فارغة من الجدول المحروس).

## ك. تهيئة عميل جديد (New Customer Bootstrap)

```
1. أنشئ مشروع Supabase جديد                    ← Dashboard
2. npx supabase link --project-ref <REF>       ← Terminal
3. npx supabase db push                        ← Terminal (الخطوة الوحيدة التي تشغّل ترحيلات)
4. اضبط .env / Vercel                          ← Editor + Vercel
5. سجّل أول مستخدم من داخل التطبيق              ← يصبح owner تلقائياً (قاعدة أول مستخدم)
6. امنحه دور المنصة إن أردت                    ← SQL snippet (يدوي)
7. اضبط إعدادات الشركة                          ← شاشة الإعدادات (لا ترحيل)
8. (اختياري) بيانات تجريبية                     ← psql -f supabase/seeds/demo_users.sql
```

**النتيجة:** `Fresh Supabase → Core Schema → Platform Admin Structure → Tenant Users`
— **بصفر اعتماد على المشروع الأول، وبصفر أسرار في المستودع.**

**التوصية:** أبقِ السلسلة الحالية، وعندما تخلو من أي بيانات/هوية (بعد معالجة §و)،
ادمجها في `baseline.sql` واحد ليكون bootstrap العميل خطوة `db push` واحدة.

## ل. الإجراءات اليدوية المطلوبة (لا يستطيع الـAgent تنفيذها)

### 🔴 عاجل — مرة واحدة

**١) تدوير كلمة مرور السوبر أدمن**
- **ماذا:** تغيير كلمة مرور الحساب الشخصي.
- **أين:** Supabase Dashboard → Authentication → Users → Reset password.
- **لماذا:** القيمة القديمة كانت في ملف SQL مرفوع، وما زالت في تاريخ Git.
- **تحقق:** سجّل خروجاً ودخولاً بالكلمة الجديدة.
- **خطر:** لا شيء. **مرة واحدة.**

**٢) تدوير `SUPABASE_SECRET_KEY` المسرّب تاريخياً**
- **أين:** Project Settings → API keys.
- **لماذا:** يتجاوز RLS بالكامل، وتاريخ Git يبقيه قابلاً للوصول.
- **تحقق:** حدّث `.env` و Vercel، أعد النشر، تأكد أن الـEdge Functions تعمل.
- **مرة واحدة.**

### 🟠 يحتاج قرارك

**٣) الترحيلان المتبقيان بدون حارس**
`20260911150300` و `20260912172000`. أستطيع إضافة نفس الحارس لهما — قل لي فقط.

**٤) مراجعة `platform_admins` بعد تطبيق `20260929000100`**
الترحيل سيمنح superadmin لكل مالك فعلي بلا صف. على نشر بعميل واحد هذا شخص واحد.
**تحقق:**
```sql
SELECT pa.user_id, pa.role, pa.is_active, u.email
FROM public.platform_admins pa
LEFT JOIN auth.users u ON u.id = pa.user_id
ORDER BY pa.created_at;
```
اسحب أي صف لا يجب أن يحمل صلاحية منصة: `DELETE FROM platform_admins WHERE user_id = '...'`.
**الآن وهذا ممكن بأمان — وهو الفرق الجوهري عن السابق.**

**٥) التحقق من RLS على جدولي الصلاحيات**
```sql
SELECT tablename, policyname, cmd, roles, qual, with_check
FROM pg_policies
WHERE tablename IN ('platform_admins', 'user_roles')
ORDER BY tablename, cmd;
```
تأكد أن أي `INSERT`/`UPDATE` مقيَّد بـ`with_check` لمديري المنصة فقط. **قراءة فقط.**

**٦)** Vercel → Settings → Environment Variables: مفاتيح المشروع الجديد.
**٧)** إنشاء أول مستخدم + منح دور المنصة (الخطوات ٥-٦ في §ك).

npx supabase migration list --linked      # قارن المحلي بالبعيد

```bash

```

```bash
npx supabase db push
```

npx supabase db reset        # يُسقط القاعدة ويعيد بناءها. فقدان كل البيانات.
