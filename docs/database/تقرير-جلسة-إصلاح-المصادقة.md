## ملخّص تنفيذي

واجه المستخدم **عطلاً كاملاً في تسجيل الدخول**: كل محاولة دخول تُرجع `HTTP 500`،
وكل شاشة محجوبة بعد الدخول. بدأ التشخيص بافتراض أن السبب صلاحيات أو RLS،
وانتهى إلى **سبب واحد دقيق ومُثبت بالدليل**: أعمدة رموز نصية في `auth.users`
كانت `NULL`، وGoTrue (المكتوب بـGo) لا يستطيع تحويل `NULL` إلى `string`.

**النتيجة النهائية:** تسجيل الدخول يعمل، و**44 صفحة** مفتوحة، والسبب المُسبب
للعطل مُعالَج **بنيوياً** بحيث يستحيل تكراره على أي قاعدة بيانات جديدة.

| القياس | قبل | بعد |
|---|---|---|
| `POST /auth/v1/token` | 🔴 500 | ✅ 200 + توكن صالح |
| `GET /auth/v1/admin/users` | 🔴 500 | ✅ 200 |
| `DELETE /auth/v1/admin/users/...` | 🔴 500 | ✅ يعمل |
| `POST /auth/v1/recover` | 🔴 500 | ✅ يعمل |
| صفحات الواجهة المتاحة | 🔴 0 | ✅ 44 |
| المحجوبون في الشاشات | 🔴 كل المستخدمين | ✅ لا شيء |

## الجزء الأول — العطل الحقيقي: `confirmation_token` = `NULL`

### 1.1 الرسالة الحاسمة

من **Supabase Dashboard → Logs → Auth**، كان كل مسار يقرأ صف مستخدم يفشل بنفس
الخطأ:

```text
sql: Scan error on column index 3, name "confirmation_token":
converting NULL to string is unsupported
```

وشمل اللوق هذه المسارات:

| المسار | كان | السبب |
|---|---|---|
| `POST /token` | 500 `error finding user` | تسجيل الدخول |
| `POST /recover` | 500 `error finding user` | استعادة كلمة المرور |
| `GET /admin/users` | 500 `unable to fetch records` | قائمة المستخدمين |
| `DELETE /admin/users/<id>` | 500 `error finding user` | حذف مستخدم |
| `GET /settings` | **200** ✅ | لا يقرأ `auth.users` |

> **ملاحظة تشخيصية مهمة:** نجاح `/settings` مع فشل كل ما يقرأ `auth.users`
> أثبت أن الخدمة حيّة والاتصال سليم، وأن العطل محصور في **قراءة جدول المستخدمين**.

### 1.2 السبب الجذري

في مخطط Supabase، هذه الأعمدة على `auth.users` مُعرَّفة `NOT NULL DEFAULT ''`:

```
confirmation_token
recovery_token
email_change
email_change_token_new
email_change_token_current
```

GoTrue يقرأها في متغيّرات `string` بلغة Go — **وGo لا تمثّل `NULL` كنصّ**.
عمود واحد فارغ يُسقط الاستعلام كله، فيفشل كل ما يقرأ المستخدم.

### 1.3 لماذا كانت `NULL` — الدليل من نفس البيانات

كان الحسابان على القاعدة يتصرفان بشكل مختلف تماماً، وهذا كان مفتاح التشخيص:

| الحساب | كيف أُنشئ | الأعمدة | النتيجة |
|---|---|---|---|
| `m@gmail.com` | `auth.admin.createUser()` (Admin API) | `''` ✅ | **200 — نجح** |
| `mousa.mc13@gmail.com` | `INSERT` مباشر من ترحيل | `NULL` 🔴 | **500 — فشل** |

**الاستنتاج:** الطريقة المستخدمة لإنشاء الصف هي الفارق الوحيد.
- `20260916000000_reset_and_recreate_superadmin_user.sql`
- `20260917200000_link_superadmin_user_and_permissions.sql`
- `supabase/seeds/demo_users.sql`

كلها تُدرج في `auth.users` بـ`INSERT` مباشر **دون تمرير هذه الأعمدة**، فتأخذ `NULL`.

> **هذا يُطابق حرفياً ما وضعه `docs/database/migration-safety-notes.md §6.1`:**
> *«الكتابة مباشرة في `auth.users` / `auth.identities` تتجاوز دفتر حسابات
> GoTrue الداخلي — وهو أسلوب غير مدعوم رسمياً»*. التطبيق خالف ما وثّقه،
> والنتيجة كانت هذا العطل.

### 1.4 الإصلاح — ثلاث طبقات

**الطبقة ١: إصلاح البيانات الحالية** (`20260929000600`)

```sql
UPDATE auth.users SET confirmation_token = coalesce(confirmation_token, '')
WHERE confirmation_token IS NULL;
-- ومثله: recovery_token, email_change,
--        email_change_token_new, email_change_token_current
--        (reauthentication_token إن وُجد العمود)
```

خصائص هذا الإصلاح:
- **لا يفبرك رمزاً** — القيمة البديلة `''` وهي الافتراضي الموثّق.
- **لا يمسّ أي رمز تأكيد حقيقي معلّق** — لأنه يطابق `NULL` فقط.
- **لا يُنشئ ولا يحذف ولا يعدّل** أي مستخدم أو هوية أو ملف أو دور.

**الطبقة ٢: الحارس البنيوي — وهذا هو الإصلاح الدائم** (`20260929000600`)

```sql
CREATE TRIGGER normalize_auth_user_token_columns
  BEFORE INSERT OR UPDATE ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.normalize_auth_user_token_columns();
```

الدالة تستبدل `NULL` بـ`''` على كل كتابة مستقبلية. **الأثر:** أي إدراج في
`auth.users` — من ترحيل، أو سكربت، أو SQL Editor في الـDashboard —
**يستحيل بنيوياً** أن يُنتج `NULL` مرة أخرى.

> **لماذا trigger وليس توثيقاً؟** لأن الترحيل لا يستطيع أن «يتذكّر» ضبط خمسة
> أعمدة نصية في جدول لا يملكه. الاعتماد على انتباه الكاتب هو ما سبّب العطل
> أصلاً؛ الحارس البنيوي هو الضمانة الوحيدة الدائمة.

**الطبقة ٣: إصلاح المصدر**

| الملف | الإصلاح |
|---|---|
| `20260916000000_...` | الأعمدة الخمسة مذكورة صراحةً في `INSERT` + تعليق يشرح لماذا |
| `supabase/seeds/demo_users.sql` | نفس الإصلاح + إصلاح الصفوف القديمة الفاسدة في `ON CONFLICT` |

**تحقق مدمج:** الترحيل يرفع `RAISE EXCEPTION` إن بقي أي `NULL` — فلا يفشل
النظام صامتاً بعد الآن.

## الجزء الثاني — مشاكل أخرى اكتُشفت وأُصلحت في نفس الجلسة

### 2.1 🔴 دائرة مقفلة تُحجب كل الشاشات عن السوبر أدمن

**العَرَض:** حساب السوبر أدمن موجود وسليم في `platform_admins`، ومع ذلك كل
صفحة محجوبة.

**السبب:** دورة مفرغة بين سياسة RLS وطريقة قراءة الواجهة لصلاحياتها:

```
src/lib/auth.tsx → SELECT role FROM platform_admins WHERE user_id = أنا
                              ↓
platform_admins_select USING (public.is_platform_admin(auth.uid()))
                              ↓
is_platform_admin تقرأ platform_admins ← نفس الجدول
                              ↓
لا صف مرئي → auth.tsx يُرجع false بصمت
                              ↓
app-shell.tsx يرى isPlatformAdmin=false, isSuperadmin=false, owner=false
                              ↓
🚫 كل الصفحات محجوبة
```

**لماذا ظهر الآن:** الترحيل `20260929000100` أزال شرط `OR user_roles.role = 'owner'`
من `is_platform_admin` — وكان ذلك **إصلاحاً صحيحاً** (فصل صلاحيات المنصة عن
صلاحيات الشركة)، لكنه **كشف** هذه الدائرة التي كان الشرط يُخفيها.

**الإصلاح** (`20260929000500`): سياسة self-read — «لك أن تقرأ دائماً الصف الذي
يصفك أنت»:

```sql
CREATE POLICY platform_admins_self_read ON public.platform_admins
  FOR SELECT TO authenticated
  USING (user_id = auth.uid());
```

السياسات في RLS تُجمَع بـ`OR`، فهذه **تضيف صفاً واحداً لكل قارئ** (صفّه هو)
ولا تُوسّع `platform_admins_select`.

**تحقق مدمج:** الترحيل يرفع استثناءً إن لم تُنشأ السياسة.

### 2.2 🟠 قائمة منح الدوال كانت ناقصة — تكسر أي نشر جديد

`20260929000200` ينتهي بـ`REVOKE EXECUTE ON ALL FUNCTIONS ... FROM PUBLIC, anon`
ثم يُعيد المنح لقائمة أسماء **مكتوبة يدوياً**. القائمة أسقطت:

| الدالة | ما ينكسر |
|---|---|
| `search_products` | قائمة المنتجات (بحث/فرز/صفحات) |
| `customer_ledger_balance` | كشوفات حسابات العملاء |
| `has_role` / `is_staff` | **كل سياسات RLS على جداول المستأجر** |
| `warehouse_reference_counts` | حارس حذف المخازن |

ولا يمكن أن تشمل أي دالة تُضاف لاحقاً من الـDashboard.

**الأثر على القاعدة الحالية:** لا شيء (المنح القديمة باقية).
**الأثر على قاعدة جديدة:** التطبيق يُثبَّت ثم يفشل في التشغيل
بـ`permission denied for function`.

**الإصلاح** (`20260929000400`): منح `authenticated` **ديناميكياً لكل الدوال**،
فلا يمكن أن تصبح القائمة «ناقصة دالة» مرة أخرى.

### 2.3 🟠 `ALTER DEFAULT PRIVILEGES` كان يكسر تسجيل الدخول

`20260929000200` كان ينفّذ:

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon;
```

هذه الجملة **لا تنحصر** في دوال كاتبها — بل تُعيد كتابة صف الـdefault ACL
للمخطط كله، فيسقط `anon` من المنح الافتراضية ويفشل تسجيل الدخول:

```text
500 {"error_code":"unexpected_failure","msg":"Database error querying schema"}
```

و`REVOKE ... FROM PUBLIC` يُخفي كل دالة جديدة عن `service_role`
(يُعطّل Edge Functions).

**الإصلاح:** حُذفت الجملتان، والمنح أصبح صريحاً لكل دالة.
**القاعدة المستخلصة:** `ALTER DEFAULT PRIVILEGES` مفتاح على مستوى المخطط كله —
يُمنع استخدامه للتعبير عن «هذه الدالة خاصة». للتخصيص: `REVOKE` صريح.

### 2.4 🔴 `is_staff` كانت تفشل **مفتوحة** لا مغلقة

`20260918000200` سطر 41:

```sql
AND COALESCE((SELECT is_active FROM profiles WHERE id = _user_id), true)
                                                                    ↑
```

القيمة البديلة `true` تعني أن مستخدماً **بلا صف `profiles`** يُعتبر **نشطاً**.
وهذا **عكس نيّة الملف تماماً**: حذف الملف الشخصي كان **يزيد** الصلاحية لا ينقصها.
صُحّح إلى `false` في `20260929000400`.

### 2.5 🟠 الهوية الشخصية داخل مسار التسجيل

`20260915030000` كان يعيد كتابة `handle_new_user()` بقاعدة تصعيد حيّة:

```sql
IF LOWER(NEW.email) = '<بريد شخصي>' THEN
  INSERT INTO public.user_roles ... 'owner';
  INSERT INTO public.platform_admins ... 'superadmin';
END IF;
```

**الأثر:** على قاعدة عميل، ذلك البريد يخصّ شخصاً آخر — **شخص ثالث يصبح سوبر
أدمن لقاعدة العميل لحظة تسجيله**، ولا يمكن إبطاله لأن القاعدة في الـtrigger
لا في البيانات.

**الإصلاح** (`20260929000000`): `handle_new_user()` أُعيد إلى مسؤوليته الواحدة
(إنشاء صف `profiles` فقط) بلا أي معرفة بالبريد أو الأدوار.

### 2.6 🟠 `20260916000000` كانت تُرقّي **أي** حساب إلى سوبر أدمن

رأس الملف كان يقول إن جمعه «مطابِق لصفر صفوف على مشروع جديد فهو غير ضار».
**هذا كان خطأً:** عبارة `DELETE ... WHERE email = '...'` لا تطابق شيئاً، لكن
**`INSERT INTO auth.users` التي بعدها تُنشئ الحساب من الصفر على كل قاعدة
جديدة** — ثم تُمنح `superadmin`.

**الإصلاح:** على قاعدة أنشأها الترحيل نفسه يعمل كما كان (وهذا مطلوب — يُنشئ
حساب المالك). وعلى قاعدة فيها أي حساب حقيقي يخرج فوراً. الترقية صارت **مشروطة
بإثبات أن الحساب من صنع الترحيل** (`encrypted_password IS NULL` + بلا صف في
`auth.identities`)، فلا يمكن أن تُرقّي شخصاً ثالثاً أبداً.

### 2.7 🟠 سبع جمل `DO UPDATE` كانت تُحيي صلاحيات مسحوبة

في `20260915030000` و`20260917200000`:

```sql
ON CONFLICT (user_id) DO UPDATE SET role = 'superadmin', is_active = true;
```

الحمولة متطابقة في كل الحالات، فالـ`UPDATE` **لم يكن يشتري شيئاً** — إلا
**إلغاء سحبٍ متعمّد** (`is_active = false`) عند التشغيل التالي. أي أن سحب
صلاحية سوبر أدمن **لم يكن ممكناً**.

**الإصلاح:** كلها `DO NOTHING`. **تحقق:** لا يوجد في المستودع أي
`DO UPDATE SET role = 'superadmin'`.

### 2.8 🟠 ترتيب مدمّر داخل سلسلة قابلة لإعادة التشغيل

`20260912111000_reset_for_meters_shop.sql` يحتوي `TRUNCATE` لـ25 جدول أعمال
متبوعاً بـ`DELETE FROM auth.users`. **كان محروساً بالفعل** على
`sales_invoices`، وأُضيف حارس ثانٍ: منع حذف حسابات حقيقية بمطابقة البريد.

### 2.9 🟡 كلمة مرور في ملف QA متتبَّع

الملف `qa-login.mjs` في جذر المستودع يحتوي كلمة مرور حساب حقيقي بنصّها.
**أُضيف إلى `.gitignore`** (بقرار من المالك بالإبقاء على القيمة كما هي).

### 2.10 🟠 الـSeed كان يخلط ثلاث دورات حياة

`supabase/seeds/seed.sql` — موصول بـ`config.toml` كـ`db.seed.sql_paths` —
كان يحتوي في ملف واحد: صفوفاً مرجعية + **بيانات أعمال تجريبية** (56 صنفاً،
20 عميلاً، 10 فواتير، حركات مخزون) + **إدخالات في `auth.users`** + **هوية
الشركة** (`company_settings`).

**الأثر:** أي `db reset` على مشروع عميل يزرع فواتير وهمية و**يستبدل اسم شركته
وعملته وضريبه**.

**الإصلاح — فصل إلى ثلاث طبقات:**

| الملف | يُشغَّل تلقائياً | المحتوى |
|---|---|---|
| `seeds/reference.sql` 🆕 | ✅ نعم (في `config.toml`) | تصنيفات مصروفات + وحدات قياس فقط |
| `seeds/demo.sql` (نُقل من `seed.sql`) | ❌ لا | البيانات التجريبية |
| `seeds/demo_users.sql` | ❌ لا | الحسابات التجريبية |

## الجزء الثالث — لماذا واجهت مشاكل متكررة بعد كل migration؟

**الإجابة البنيوية:** كان في المستودع **أربع آليات بأربع دورات حياة مختلفة**،
ولا مستند يوضح أيّها يفعل ماذا. الآن الفصل صريح:

```
db push          → migrations/            المخطط فقط         ✅ يُنشئ البنية
db reset         → migrations/ + reference.sql               ⚠️ محلي فقط
يدوي             → demo_users.sql + demo.sql                 ❌ تجريبي
Edge Function    → admin-create-user → auth.admin.createUser ✅ الحسابات
شاشة الإعدادات   → company_settings                          ✅ هوية العميل
20260916000000   → حساب المالك على قاعدة فارغة               ✅ محروس ومشروط
```

> **الملاحظة الحاسمة:** `db push` يُشغّل `migrations/` **فقط** ولا يمسّ
> `seeds/` إطلاقاً. أما `db reset` فهو **الوحيد** الذي يُشغّل `reference.sql`.
> هذا كان أكبر مصدر للالتباس.

### 3.1 أين تُنشأ البيانات فعلاً؟

| الطبقة | المصدر | تُنشأ تلقائياً؟ |
|---|---|---|
| المخطط (جداول، enums، دوال، RLS) | `migrations/*.sql` (47 ملفاً) | ✅ نعم |
| مرجعي: دول، جودات، ماركات، موديلات | ترحيل `20260912130000` | ✅ نعم |
| مرجعي: تصنيفات مصروفات، وحدات | `seeds/reference.sql` | ✅ عند `db reset` |
| أعمال وهمية: أصناف، عملاء، فواتير | `seeds/demo.sql` | ❌ لا |
| حسابات | `admin-create-user` / `20260916000000` | ✅ مشروط |
| إعدادات الشركة | شاشة الإعدادات في التطبيق | ❌ إعداد لا ترحيل |

### 3.2 لماذا لا توجد شاشة تسجيل (Sign-Up)؟

`src/routes/auth.tsx` فيه **`signInWithPassword` فقط** — لا `signUp` في المشروع
كله. ولذلك `bootstrap_first_owner` (التي تُنشئ أول `owner` تلقائياً) **لا تُطلَق
أبداً على قاعدة جديدة فارغة**، لأن لا أحد يُدرج صفاً في `auth.users`.

**النتائج المترتبة:**

| المستخدم | كيف يُنشأ حالياً | يعمل؟ |
|---|---|---|
| الموظفون | Edge Function `admin-create-user` عبر `auth.admin.createUser` | ✅ نعم — **الطريقة المدعومة رسمياً** |
| المالك على قاعدة جديدة | `20260916000000` (مشروط) | ✅ نعم |
| تسجيل ذاتي | — | ❌ **غير موجود** |

**التوصية:** إضافة `signUp` أو Edge Function للـbootstrap — **قرار منفصل
لم يُنفَّذ** لأنه تغيير وظيفي لا إصلاح.

### 4.1 ترحيلات جديدة (5)

## الجزء الثامن — القواعد المستخلصة (للمستند الدائم)

| # | القاعدة |
|---|---|
| R15 | **لا تُدرج في `auth.users` بـ`INSERT` مباشر.** استخدم `auth.admin.createUser()` — أو مرّر أعمدة الرموز الخمسة صريحةً. الحارس `normalize_auth_user_token_columns` يمنع الحدوث، لكن السبب يبقى خاطئاً. |
| R16 | **`ALTER DEFAULT PRIVILEGES` مفتاح على مستوى المخطط كله.** يُمنع استخدامه لـ«هذه الدالة خاصة» — للتخصيص: `REVOKE` صريح. |
| R17 | **دوال RLS تُستدعى بدور المُقيِّم.** أي دالة داخل سياسة يجب أن تكون قابلة للتنفيذ من الدور الذي يُقيّمها (بما فيه `anon` قبل المصادقة)، وإلا انكسر تسجيل الدخول. |
| R18 | **الدوال التي تقرأ جدولاً يجب ألا تكون محجوبة بسياسة ذلك الجدول.** استخدم `SECURITY DEFINER` + سياسة self-read للـbootstrap. |
| R19 | **`ON CONFLICT DO UPDATE` يُحيي حالة مسحوبة.** إن كانت الحمولة متطابقة، استخدم `DO NOTHING` — وإلا صار السحب غير دائم. |
| R20 | **`COALESCE(..., true)` في دالة صلاحيات تفشل مفتوحة.** القيمة البديلة الافتراضية في أي ضابط وصول يجب أن تكون `false`. |
| R21 | **قائمة منح مكتوبة يدوياً تتقادم.** المنح تكون ديناميكية أو مُولَّدة، وإلا أسقطت دالة عند أول إضافة. |
