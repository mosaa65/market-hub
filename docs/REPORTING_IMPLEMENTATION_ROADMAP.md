## 1. الملخص التنفيذي (Executive Summary)

تهدف هذه الخطة الهندسية التنفيذية إلى بناء منظومة تقارير وكشوفات تجارية وتشغيلية احترافية وموحدة في نظام **Vortex ERP**، تلبي احتياجات المنشأة في إدارة المبيعات، المشتريات، المخزون، حركة الشركاء، والرقابة على العمليات، وتعمل بكفاءة استثنائية على بيئة التشغيل المحلية (Local Server / Docker PostgreSQL)، مع بقاء معماريتها قابلة للنقل السحابي المستقبلي دون إعادة تصميم.

**تحديث نطاق العمل (توجيه المطور وصاحب النظام):**  
تم **استبعاد وتأجيل** كافة تقارير الطحن (Milling)، والإنتاج الصناعي، وأمانات العملاء، وقالب الإنتاج والكفاءة الفني، وقالب PDF الصناعي من نطاق التنفيذ الحالي؛ للتركيز أولاً على استقرار وقوة العمليات التجارية الأساسية (المبيعات، المشتريات، المخزون التجاري، الشركاء، والرقابة). سيتم بناء هذه المنظومة في مرحلة صناعية مستقلة لاحقاً دون الحاجة لإعادة تصميم المحرك الأساسي.

تقوم الفلسفة الهندسية لهذه الخطة على **الفصل المعماري الصارم بين أربعة أركان أساسية**:
1. **قالب الشاشة (Domain Screen — 6 شاشات مجال):** يحدد مجال الأعمال (مبيعات، مشتريات، مخزون ومستودعات، عملاء، موردون، رقابة وعمليات)، ويدير التبويبات وحالة الفلاتر وتفويض الصلاحيات.
2. **قالب عرض التقرير (Report View Template — 6 قوالب عرض):** يحدد النمط البصري والحسابي لعرض البيانات (تقرير ملخص، جدول تفصيلي، كشف حركة برصيد متسلسل، تجميع وترتيب، مقارنة وتحليل، حالات واستثناءات).
3. **تعريف التقرير ومزود بياناته (Report Definition & Data Provider):** يحدد العقد البرمجي المستقل (Schema) للفلاتر والأعمدة والمقاييس، بينما يتولى "مزود البيانات" جلب النتائج بكفاءة من PostgreSQL عبر عروض عادية (Views) أو استعلامات محكمة مع الترقيم بالخادم دون كتابة SQL حر داخل الواجهة.
4. **قالب التصدير والطباعة (Export & Print Template):** يضمن إخراج التقارير بصيغ PDF فاخرة (3 قوالب أساسية)، وجداول Excel وCSV، وطباعة إيصالات حرارية متطابقة حسابياً 100% مع أرقام الشاشة وتدعم اللغة العربية واتجاه RTL.

تم تنظيم خارطة الطريق في **13 مرحلة متسلسلة منطقياً (من المرحلة 0 إلى المرحلة 12)** تتضمن **47 مهمة تفصيلية** بمعرفات تتبع ثابتة (`REP-001` إلى `REP-047`).

## 5. المعمارية المستهدفة والفصل الرباعي (The 4-Way Architecture)

```
┌────────────────────────────────────────────────────────────────────────┐
│                   VORTEX COMMERCIAL REPORTING ENGINE                   │
└────────────────────────────────────────────────────────────────────────┘
                                   │
 ┌─────────────────────────────────┼─────────────────────────────────┐
 ▼                                 ▼                                 ▼
[1. شاشات المجالات الـ 6]     [2. قوالب العرض الـ 6]     [3. قوالب التصدير والطباعة]
- Sales Screen               - Summary Template         - Summary PDF
- Purchases Screen           - Detailed Table           - Tabular Detailed PDF
- Inventory Screen           - Movement Statement       - Movement Statement PDF
- Customers Screen           - Grouped & Ranking        - Excel Multi-Sheet
- Suppliers Screen           - Comparison Template      - Safe CSV Export
- Audit Screen               - Status & Exceptions      - Direct Slip Print (80mm)
 └─────────────────────────────────┬─────────────────────────────────┘
                                   │
                                   ▼
          [4. عقود تعريف التقارير ومزودات البيانات المشتركة]
          - ReportDefinition (Typed Schema)
          - Filter & Column Registries
          - Commercial Data Providers (PostgreSQL Views Pushdown)
```

### أ. قوالب الشاشات حسب المجال (Domain Screens — 6 شاشات)
تختص كل شاشة بقطاع تجاري أو تشغيلي محدد، وتحتوي على مسار مستقل (Route) في التنقل الجانبي:
1. `/_app/reports/sales`: تقارير المبيعات ونقطة البيع.
2. `/_app/reports/purchases`: تقارير المشتريات والتوريد.
3. `/_app/reports/inventory`: تقارير المخزون التجاري والمستودعات والتسويات والتحويلات.
4. `/_app/reports/customers`: تقارير العملاء التشغيلية وتكرار الشراء والعملاء الراكدين.
5. `/_app/reports/suppliers`: تقارير الموردين وتكرار التوريد ومقارنة أسعار الشراء.
6. `/_app/reports/operations-audit`: تقارير العمليات وسجل التدقيق والفواتير الملغاة والاستثناءات.

*(ملاحظة: شاشة تقارير الطحن والإنتاج `/_app/reports/milling` أرجئت للطور الصناعي القادم).*

### ب. قوالب عرض التقارير الأساسية (Report View Templates — 6 قوالب)
تحدد طريقة تمثيل ومعالجة البيانات على الشاشة:
1. **التقرير الملخص (Summary Report Template):** يبرز بطاقات مؤشرات الأداء (KPIs) ونسب التوزيع وجدولاً ملخصاً موجزاً (مثل: المبيعات اليومية، ملخص حركات المستودع).
2. **التقرير التفصيلي (Detailed Table Template):** يعرض سجلات العمليات سطراً بسطر مع الترقيم والفرز والبحث وتفاصيل المستند عند النقر (مثل: فواتير المبيعات، تفاصيل المشتريات، الخصومات).
3. **كشف الحركات والرصيد المتسلسل (Movement Statement Template):** يحسب الرصيد الافتتاحي والحركات بالترتيب الحتمي والوارد والصادر والرصيد بعد كل حركة (مثل: كشف حركة صنف في مستودع، كشف حركات الخزينة).
4. **التقرير التجميعي والترتيبي (Grouped & Ranking Template):** يجمع البيانات حسب كيان معين (الصنف، العميل، المورد، الفرع) ويرتبها تنازلياً أو تصاعدياً (مثل: المنتجات الأكثر مبيعاً، الموردون الأكثر توريداً).
5. **تقرير المقارنة والتحليل (Comparison Template):** يقارن بين فترتين زمنيتين أو فرعين أو تصنيفين ويعرض الفارق المطلق ونسبة التغير `%` (مثل: مقارنة المبيعات الشهرية، مقارنة أسعار التوريد).
6. **تقرير الحالات والاستثناءات (Status & Exceptions Template):** يفرز العمليات غير الطبيعية أو التي تتطلب تدخلاً عاجلاً (مثل: الأصناف تحت حد الطلب، المنتجات الراكدة، العمليات الملغاة، فجوات التصنيف).

*(ملاحظة: قالب الإنتاج والكفاءة الفني أرجئ للطور الصناعي القادم).*

### ج. عقود تعريف التقارير ومزودات البيانات (Definitions & Data Providers)
فصل تعريف الحقول والأعمدة عن طريقة جلب البيانات:
- **تعريف التقرير (Report Definition):** هيكل وصفي (Declarative Metadata) يحدد هوية التقرير، الفلاتر المطلوبة، الأعمدة المتاحة، المقاييس، والصلاحيات.
- **مزود البيانات (Data Provider):** دالة خادم متخصصة تنفذ الاستعلام الأمثل في PostgreSQL (عبر View أو استعلام محكم مع الترقيم وحساب الإجماليات)، دون تعريض الواجهة لكتابة استعلامات SQL حرة.

### د. قوالب التصدير والطباعة (Export & Print Templates)
1. **قوالب PDF المتخصصة (3 قوالب أساسية):**
   - *قالب الملخص:* ترويسة المنشأة، بطاقات المؤشرات، ورسم بياني/جدول ملخص.
   - *قالب الجداول التفصيلية:* متعدد الصفحات مع تكرار ترويسة الجدول وضبط التفاف النص العربي والهوامش.
   - *قالب كشوف الحركة:* يبرز الرصيد الافتتاحي وسطور الوارد والصادر والرصيد التراكمي وتذييل التوقيعات.
2. **قوالب Excel وCSV:**
   - *CSV Export:* بيانات مسطحة مع ترميز UTF-8 مع BOM لمنع تشوه النصوص العربية.
   - *Excel Detail Export:* ملف Excel منسق مع أعمدة ملونة وخلايا رقمية حقيقية (غير نصية).
   - *Excel Multi-Sheet Export:* مصنف متعدد الأوراق (ورقة للملخص وورقة للسجلات التفصيلية).
   - *Direct Thermal Slip Print:* طباعة إيصالات حرارية سريعة (80mm) للملخصات اليومية للكاشير.

## 6. مسؤوليات طبقات النظام (Architecture Tier Responsibilities)

| الطبقة | المسؤوليات المنوطة بها حصراً | الممارسات الممنوعة في هذه الطبقة |
|---|---|---|
| **قاعدة البيانات (PostgreSQL / Supabase)** | - احتساب المجاميع الثقيلة (`SUM`, `COUNT`, `AVG`).<br>- تجميع البيانات وحساب تكلفة البضاعة المنصرفة عبر الدوال والعروض.<br>- فرض سياسات الأمان والعزل على مستوى الصفوف (RLS).<br>- الترقيم الفعال (`LIMIT` / `OFFSET`) وفرز المؤشرات. | - منع استخدام `Materialized Views`.<br>- منع الحسابات العائمة غير المقربة.<br>- منع فتح صلاحيات غير مقيدة للمستخدم المجهول (Anon). |
| **طبقة الخادم (Server Layer / RPC & Functions)** | - التحقق الصارم من مدخلات الفلاتر عبر Zod.<br>- تدقيق صلاحيات المستخدم ومطابقتها لدور المنشأة.<br>- تنسيق استدعاء مزودات البيانات وتوليد مفاتيح الكاش الموحدة.<br>- تحويل نطاقات التواريخ بما يضمن شمولية نهاية اليوم `T23:59:59.999Z`. | - منع تمرير أسماء أعمدة حرة غير معتمدة إلى الاستعلام.<br>- منع تنفيذ حلقات N+1 RPC لجلب السجلات.<br>- منع إرسال بيانات غير مفلترة بالكامل إلى العميل. |
| **واجهة المستخدم (Frontend / React & TanStack)** | - عرض شاشات المجالات الستة وإدارة اختيار التقرير.<br>- إتاحة فلاتر ديناميكية تتكيف مع التقرير المختار.<br>- إدارة إخفاء/إظهار الأعمدة وحفظ التفضيلات محلياً.<br>- عرض بطاقات المؤشرات وجداول البيانات بنمط القالب المعتمد.<br>- فتح نوافذ تفاصيل المستندات الأصلية عند النقر على السجل. | - منع حساب الأرصدة التراكمية في الواجهة بطريقة عشوائية.<br>- منع التصفية بالذاكرة عبر `JSON.stringify` للمجموعات الكبيرة.<br>- منع استدعاء استعلامات مباشرة تتجاوز مزود البيانات. |
| **محرك التصدير والطباعة (Export & Print Engine)** | - إنتاج ملفات PDF مطابقة لأرقام الشاشة.<br>- توليد ملفات Excel وCSV بترميز عربي سليم.<br>- دعم الطباعة الحرارية والمستندات متعددة الصفحات مع الترويسات. | - منع إعادة حساب المبالغ أو الأرصدة في محرك التصدير بمعادلات تختلف عن الشاشة.<br>- منع الاعتماد على مكتبات غير مجربة مع الحروف العربية المتصلة. |

## 7. التصميم البرمجي للعقود المشتركة (TypeScript Core Schema)

```typescript
/**
 * Vortex ERP — عقود محرك التقارير التجارية الموحدة

export type ReportDomain =
  | "sales"
  | "purchases"
  | "inventory"

  | "suppliers"
  | "operations_audit";

  | "summary"

  | "movement_statement"
  | "grouped_ranking"
  | "comparison"
  | "status_exceptions";

export type ColumnDataType =
  | "text"
  | "code"
  | "money"
  | "quantity"
  | "percentage"
  | "date"
  | "datetime"
  | "status_badge"
  | "action_link";

export type FilterControlType =
  | "date_range"

  | "supplier_select"
  | "product_select"
  | "category_select"
```

## 9. الخطة الترتيبية للمراحل (Sequential Phases Overview)

تم تنظيم المشروع في **13 مرحلة متتابعة** بعد تركيز النطاق:
- **المرحلة 0:** تثبيت أساس العمل واعتماد قرارات الاكتشاف.
- **المرحلة 1:** حسم وتوثيق عقود البيانات وقواعد الحساب وحالات الاختبار التجارية.
- **المرحلة 2:** تصميم وتنفيذ طبقة مزودات البيانات التجارية في الخادم (Data Providers).
- **المرحلة 3:** بناء سجل تعريفات التقارير والفلاتر والأعمدة (Schema Registry).
- **المرحلة 4:** تنفيذ الحزمة التجريبية المزدوجة (Pilot: تجميعي مبيعات + كشف حركة مخزون).
- **المرحلة 5:** بناء قوالب عرض التقارير الستة والمكونات المشتركة.
- **المرحلة 6:** بناء محرك وقوالب PDF الثلاثة والطباعة الحرارية المعتمدة.
- **المرحلة 7:** بناء محرك وقوالب تصدير Excel وCSV المتقدمة.
- **المرحلة 8:** بناء شاشات المجالات الستة وربط التبويبات المتخصصة.
- **المرحلة 9:** التوسع في إطلاق تقارير المبيعات ونقاط البيع والمشتريات.
- **المرحلة 10:** التوسع في إطلاق تقارير المخزون التجاري والعملاء والموردين والرقابة.
- **المرحلة 11:** تدقيق الأمان وسياسات RLS واختبارات الأداء العالي.
- **المرحلة 12:** الإغلاق النهائي، التوثيق، والتسليم للمراحل اللاحقة.

### المرحلة 11: تدقيق الأمان وسياسات RLS واختبارات الأداء العالي (Security, RLS & High Performance)

1. **الهدف:** التأكد من إحكام الأمان، وتطبيق سياسات RLS، وحماية صلاحيات الفروع والشركاء، وضمان استجابة الاستعلامات في أقل من 200ms تحت أحجام البيانات الكبيرة دون Materialized Views.
2. **سبب الترتيب:** تأتي هذه المرحلة قبل الإغلاق النهائي لاختبار النظام تحت أقصى ظروف التشغيل والتحقق الأمني الشامل.
3. **المتطلبات السابقة:** اكتمال المرحلة 10.
4. **المهام الفرعية:**
   - `REP-043`: مراجعة سياسات RLS على جميع الجداول والعروض المستخدمة والتأكد من عدم قدرة الكاشير أو مدير الفرع على استعراض تقارير فروع أخرى غير مصرح له بها.
   - `REP-044`: مراجعة صلاحيات التصدير ومنع تنزيل بيانات العملاء وأرقام هواتفهم لمن لا يملكون دور `manager` أو `owner`.
   - `REP-045`: إجراء تحليلات الأداء باستخدام `EXPLAIN ANALYZE` على الاستعلامات في بيئة اختبار محلية محملة بـ 50,000 فاتورة وحركة مخزنية تجريبية.
   - `REP-046`: توثيق واعتماد الفهارس المركبة الناقصة المقترحة في ترحيل SQL معتمد:
     - فهرس `sales_invoices(status, created_at DESC)`.
     - فهرس `sales_invoices(customer_id, created_at DESC)`.
     - فهرس `purchase_invoices(supplier_id, created_at DESC)`.
     - فهرس `stock_movements(product_id, created_at DESC)`.
   - `REP-047`: ضبط استراتيجيات التخزين المؤقت في React Query (`staleTime: 60_000`, `gcTime: 300_000`) مع آليات الإبطال الذكي (Granular Invalidation) عند حدوث عمليات بيع أو نقل مخزني جديدة.
5. **الأجزاء المتأثرة:** سياسات RLS، ملفات الترحيل في `supabase/migrations/`، ومصانع الكاش في `src/lib/query-keys.ts`.
6. **الأجزاء القابلة لإعادة الاستخدام:** دوال التحقق من الأدوار `has_role`, `is_staff` في `02_core_identity_and_settings.sql`.
7. **تغييرات قاعدة البيانات:** إضافة الفهارس المركبة الموجهة لتسريع الاستعلامات دون Materialized Views.
8. **تغييرات الخادم:** تفعيل الكاش الآمن ومراجعة الصلاحيات.
9. **تغييرات الواجهة:** إظهار شارات تحذيرية للمستخدمين غير المخولين بدلاً من انهيار الشاشة.
10. **الاختبارات:** اختبارات أمنية لاختراق الصلاحيات (RBAC Tests)، واختبارات قياس سرعة الاستجابة (Performance Benchmarking).
11. **معايير القبول:** استجابة كافة استعلامات التقارير المرقمنة في أقل من 200ms، وثبات حماية RLS بنسبة 100%.

## 14. خطة قاعدة البيانات واستراتيجية الأداء دون Materialized Views

تعتمد استراتيجية الأداء الصارمة على المبادئ التالية:
1. **الاعتماد على عروض SQL العادية (Standard Views):** الاستفادة الكاملة من عروض SQL التجارية المعتمدة في `12_reporting_views.sql`، حيث تقوم قاعدة البيانات بتحسين الاستعلام تلقائياً بناءً على شروط الـ `WHERE` الممررة دون تخزين بيانات مكررة.
2. **الترقيم الإلزامي على مستوى الخادم (Server-side Pagination):** كل استعلام جدول تفصيلي يقيد بـ `LIMIT` و `OFFSET` محددين مسبقاً (افتراضياً 25 إلى 50 سجلاً) عبر دالة `.range()` في Supabase.
3. **التجميع اللحظي للخادم (Server-side Pushdown Aggregation):** لا يتم جلب السجلات لحساب المجاميع في المتصفح؛ بل ترسل استعلامات تجميعية خفيفة متزامنة (`SELECT COUNT(*), SUM(total)...`) موازية لطلب الصفحة الحالية.
4. **الفهارس الموجهة (Targeted Composite Indexes):** في المرحلة 11، يتم إدخال الفهارس المركبة لتسريع البحث الزمني وفرز الحالات دون التأثير على عمليات الكتابة.
5. **منع تشبع الذاكرة (Memory Safety):** في تقارير التصدير الكبيرة، يتم سحب البيانات بنظام الدفعات (Batches of 1,000 rows) وتجميعها تدريجياً في الذاكرة لتفادي خروج المتصفح أو الخادم عن الخدمة (Out of Memory).

## 15. خطة الأمان والصلاحيات وسياسات RLS

تلتزم الخطة بأعلى معايير حماية البيانات التجارية:
1. **الأمان على مستوى الصفوف (Row Level Security):** جميع الجداول والعروض تخضع لسياسات RLS المعتمدة في النظام. لا يمكن لأي مستخدم استعراض بيانات لا تخص منشأته أو متجره.
2. **عزل الصلاحيات حسب الأدوار (Role-Based Access Control):**
   - دور `cashier`: يقتصر على تقارير مبيعات اليوم الخاصة به وإيصالات الإغلاق.
   - دور `warehouse`: يقتصر على تقارير أرصدة وحركات ونواقص المخزون التجاري دون الإطلاع على مبالغ الأرباح أو تكاليف الشراء الحساسة.
   - دور `accountant` و `manager` و `owner`: الوصول لكافة التقارير التشغيلية المشمولة.
3. **حماية التصدير والتنزيل:** لا يُتاح تنزيل ملفات Excel أو CSV التي تتضمن بيانات اتصال العملاء وأرقام هواتفهم إلا للمستخدمين ذوي الرتب الإدارية العليا (`manager`, `owner`).
4. **حماية استعلامات الخادم:** منع تمرير أسماء جداول أو أعمدة متغيرة من الواجهة لمنع ثغرات SQL Injection، والاعتماد الحصري على أسماء معتمدة مسبقاً في سجل التعريفات.

## 16. خطة التشغيل المحلي داخل Docker والنسخ الاحتياطي

1. **البيئة المستهدفة:** خادم محلي أو جهاز مكتبي يعمل بنظام Windows / Linux، يحتوي على بيئة Docker لـ PostgreSQL وقاعدة بيانات Supabase المحلية.
2. **استقلالية المعمارية:** جميع الاستعلامات والعروض ومزودات البيانات مكتوبة بمعايير PostgreSQL القياسية (ANSI SQL)، مما يضمن عملها بنفس الكفاءة سواء على Docker محلي أو على خادم Supabase السحابي عند النقل مستقبلاً.
3. **النسخ الاحتياطي الدوري:** دمج جداول وسجلات التقارير ضمن خطة النسخ الاحتياطي الحالية للنظام (`backup_logs` و `scripts/push-cloud.ps1`)، مع ضمان أن استعادة النسخة الاحتياطية تعيد كافة العروض والفهارس دون الحاجة لإعادة بنائها يدوياً.

## 20. معايير القبول وشروط الانتقال للمراحل اللاحقة (Acceptance & Handoff Criteria)

### معايير قبول منظومة التقارير التجارية والتشغيلية (Definition of Done - DoD):
1. اكتمال تشغيل شاشات المجالات الست بنجاح ودون أي أخطاء برمجية أو تحذيرات في الواجهة.
2. عمل قوالب العرض الست بسلاسة وتكيفها التام مع الهواتف والشاشات المكتبية.
3. مطابقة الأرقام المعروضة في تقارير المبيعات والمشتريات والمخزون مع السجلات الأصلية بنسبة 100%.
4. عمل أزرار تصدير PDF وExcel وCSV والطباعة الحرارية بكفاءة، مع دعم كامل للغة العربية واتجاه RTL.
5. استجابة جميع التقارير المرقمنة في أقل من 200ms تحت بيئة Docker المحلية.
6. اجتياز اختبارات الأمان وسياسات RLS والتأكد من عزل بيانات الفروع والشركاء.
7. اجتياز فحص البناء النهائي بنجاح تام (`npm run build`).

### شروط إعلان اكتمال المشروع والانتقال للطور الصناعي أو المالي اللاحق:
- تسليم المنظومة التجارية بكامل مجالاتها الست وعملها في بيئة التشغيل لمدة أسبوعين دون أي بلاغات عن فروقات حسابية.
- قيام صاحب النظام باعتماد وإغلاق مرحلة التقارير التجارية رسمياً.
- فتح مرحلة التخطيط لتقارير الطحن والإنتاج والأمانات، أو مرحلة التخطيط المالي والمحاسبي للقوائم الختامية.
