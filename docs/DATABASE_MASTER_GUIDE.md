## 1. الفلسفة المعمارية: السحابي والمحلي

في نظام **Market Hub**، **Docker المحلي** و **Supabase Cloud** كلاهما صالح ليكون:
* **بيئة إنتاج (Production):** 
  * بعض العملاء (مثل مطحنة أو متجر في منطقة نائية بدون إنترنت مستقر) يشغلون النظام محلياً داخل شبكتهم الداخلية عبر خادم Docker (On-Premise) كبيئة إنتاج حقيقية وحية.
  * بعض العملاء الآخرين يفضلون الوصول السحابي من أي مكان وفروع متعددة، فيكون إنتاجهم على Supabase Cloud.
* **بيئة تطوير واختبار (Development / Staging):**
  * يمكنك استخدام Docker محلياً كبيئة تجارب ومختبر، أو إنشاء مشروع سحابي تجريبي مجاني لاختبار الميزات قبل إرسالها لعميل الإنتاج.

```
                    ┌─────────────────────────────────────────┐
                    │            كود النظام الموحد            │
                    │   (Vite + React 19 + TanStack Start)    │
                    └───────────────────┬─────────────────────┘
                                        │ يقرأ الاتصال من .env
                    ┌───────────────────┴─────────────────────┐
                    ▼                                         ▼
   ┌─────────────────────────────────┐       ┌─────────────────────────────────┐
   │         خادم محلي (Docker)       │       │       خادم سحابي (Cloud)        │
   │  - قد يكون إنتاج لعميل محلي     │       │  - قد يكون إنتاج لعميل سحابي    │
   │  - أو بيئة تطوير وتجارب للمبرمج │       │  - أو بيئة اختبارات سحابية      │
   │  - الاستوديو: 127.0.0.1:54323   │       │  - لوحة تحكم supabase.com       │
   └─────────────────────────────────┘       └─────────────────────────────────┘
```

## 2. مدير الحزم وبيئة العمل

* **الأداة المعتمدة حصراً:** **`Node.js` (v22+)** و **`npm`**.
* **تنبيه حاسم:** تم إلغاء أي ملفات تخص `bun` لعدم تشتيتك. لا تستخدم أمر `bun` أبداً.
* **أدوات المطور المطلوبة على جهازك:**
  1. `node` و `npm` (مثبتة وتعمل).
  2. `docker` (برنامج Docker Desktop — يجب فتحه عند الرغبة في تشغيل أو فحص السيرفر المحلي).
  3. `supabase` CLI (مثبت لديك ويعمل مباشرة أو عبر `npx supabase`).

## 3. المرجع السريع للأوامر اليومية

جميع الأوامر تُنفذ من جذر المشروع عبر **`npm`**:

| الهدف المطلوب | الأمر المعتمد | نوع العملية وأثرها |
| :--- | :--- | :--- |
| **تشغيل واجهة التطبيق** | `npm run dev` | يفتح موقع التطبيق على المنفذ `3000` |
| **تشغيل خدمات Docker** | `npm run db:local:start` | يشغل حاويات Supabase دون لمس أي بيانات |
| **إيقاف خدمات Docker** | `npm run db:local:stop` | يوقف حاويات Supabase لتوفير موارد الجهاز |
| **معرفة الروابط والمفاتيح** | `npm run db:local:status` | يعرض روابط Studio وAPI ومفاتيح الاتصال |
| **تحديث ترحيلات قاعدة قائمة** | `npm run db:local:migrate` | **آمن جداً:** يطبق التعديلات الجديدة فقط دون مسح بيانات العميل |
| **إعادة بناء محلي من الصفر** | `npm run db:local:rebuild` | **هدام (يحتاج تأكيد):** يمسح القاعدة المحلية ويعيد بناءها مع عينة المطحنة |
| **أخذ نسخة احتياطية محلية** | `npm run db:backup` | يأخذ dump كامل لقاعدة البيانات في مجلد `backups/` |
| **رفع التعديلات إلى السحابة** | `npm run db:cloud:push` | **آمن للإنتاج:** يرفع ملفات الترحيل والبذور النظامية دون مسح بيانات العميل |

## 5. شرح أوامر Docker المحلي

### 5.1 تشغيل وإيقاف السيرفر المحلي
* **التشغيل:**
  ```powershell
  npm run db:local:start
  ```
  *ماذا يفعل؟* يقوم باستدعاء Docker لتشغيل حاويات: PostgreSQL، GoTrue (المصادقة)، PostgREST، لوحة تحكم Studio، وخادم البريد Mailpit. لا يغير أي بيانات مخزنة مسبقاً.
* **الإيقاف:**
  ```powershell
  npm run db:local:stop
  ```
  يوقف الحاويات لحفظ بطارية وموارد جهازك عند عدم الحاجة.

### 5.2 التحقق من الحالة والروابط (Status)
```powershell
npm run db:local:status
```
*ماذا يطبع؟*
* **Studio URL:** `http://127.0.0.1:54323` (لوحة إدارة الجداول والبيانات الشبيهة بلوحة السحابة).
* **API URL:** `http://127.0.0.1:54321` (رابط الخادم الذي يتصل به المتصفح).
* **DB URL:** `postgresql://postgres:postgres@127.0.0.1:5432/postgres`.

### 5.3 التحديث الآمن لقاعدة بيانات عميل محلي موجود (Safe Migrate)
```powershell
npm run db:local:migrate
```
* **متى تستخدمه؟** عندما يكون لديك أو لدى عميل قاعدة بيانات شغالة وفيها فواتير ومنتجات حقيقية، وأنت قمت ببرمجة ميزة جديدة وأضفت ملف migration جديد، وتريد تطبيق هذا التعديل **بدون مسح أو تصفير أي سجل!**
* **كيف يعمل؟** يستدعي `supabase migration up --local` ليقارن الترحيلات المطبقة في جدول `schema_migrations` ويطبق الناقص فقط.

### 5.4 إعادة البناء التأسيسية الشاملة (Rebuild)
```powershell
npm run db:local:rebuild
```
* **تنبيه:** هذا الأمر مخصص لبيئة التطوير أو لتأسيس قاعدة بيانات فارغة جديدة كلياً.
* **ماذا يفعل؟**
  1. يطلب منك كتابة: `RESET LOCAL kwzqvgdyadylwnvjghqn`.
  2. يقوم بتصفير قاعدة Docker تماماً (`supabase db reset --local`).
  3. يطبق الترحيلات الـ 60 بالترتيب.
  4. يزرع بذور النظام (01_system) وعينة نشاط المطحنة (03_samples/sample-mill.sql).
  5. ينشئ حسابات المسؤول التجريبية بكلمة المرور `Super#2004`.
  6. يفحص ويؤكد نجاح كل الجداول وعدد المنتجات والحسابات.

## 6. شرح أوامر سوبابيز السحابي (Cloud)

### 6.1 تسجيل الدخول لأول مرة
```powershell
npx supabase login
```
سيفتح لك المتصفح لتسجيل الدخول بحساب Supabase وتفويض الـ CLI على جهازك (مرة واحدة فقط).

### 6.2 ربط مجلد المشروع بمشروع سحابي محدد
إذا أنشأت مشروعاً سحابياً جديداً لعميل، يمكنك ربطه بالأمر:
```powershell
npx supabase link --project-ref <PROJECT_ID>
```
حيث `<PROJECT_ID>` هو الرمز المميز لمشروع العميل (مثل `kwzqvgdyadylwnvjghqn`).

### 6.3 دفع الترحيلات بأمان إلى السحابة (Cloud Push)
```powershell
npm run db:cloud:push
```
* **هل يمسح بيانات العميل السحابية؟** **مستحيل!**
* **كيف يعمل؟**
  1. يتأكد من مطابقة الرمز في `.env` مع المشروع المرتبط.
  2. يطلب منك كتابة تأكيد بالاسم: `CLOUD <PROJECT_ID>`.
  3. ينفذ `supabase db push --linked` والذي يرسل فقط الترحيلات الجديدة التي لم تطبق بعد.
  4. يطبق فقط البذور المرجعية النظامية الصامتة (`01_system`) دون لمس سجلات وفواتير العميل.
  5. لا يرسل عينات المطحنة أو الحسابات التجريبية نهائياً إلا إذا طلبت صراحة `-- -IncludeDemoData`.

## 7. هيكل الترحيلات (Migrations)

جميع الترحيلات موجودة في المجلد:
`supabase/migrations/`

وهي مرقمة من `01_` وحتى `60_`.

### القواعد الذهبية للترحيلات:
1. **ممنوع تعديل أي ملف migration قديم:** التعديل على ملف قديم تم تطبيقه عند عميل أو على السحابة يكسر سلسلة التحقق (Checksum Mismatch).
2. **لأي تعديل أو إضافة، أنشئ ملفاً جديداً برقم تسلسلي تالٍ:**
   * مثلاً التعديل القادم يحمل اسم: `61_add_new_feature.sql`.
3. **استخدم أوامر SQL آمنة وقابلة للتكرار (Idempotent):**
   * استخدام `CREATE TABLE IF NOT EXISTS ...`
   * استخدام `ADD COLUMN IF NOT EXISTS ...`
   * استخدام `CREATE OR REPLACE FUNCTION ...`

## 8. نظام البذور (Seeds)

المسار: `supabase/seeds/`

تم فصل البيانات إلى مستويات واضحة لمنع تلوث بيانات العملاء:

| المجلد | محتواه | متى يُطبّق؟ | هل يدخل لعميل حقيقي؟ |
| :--- | :--- | :--- | :--- |
| **`01_system/`** | الوحدات الأساسية، الباقات، دليل الحسابات القياسي، تصنيفات المصروفات، ترقيم المستندات، طرق الدفع الأساسية | تلقائياً عند التأسيس | **نعم — النظام لا يعمل بدونها** |
| **`02_company/`** | إعدادات وهوية المنشأة الخاصة بالعميل (الاسم التجاري، الرقم الضريبي، الأرصدة الافتتاحية) | يدوي لكل عميل | **نعم — تخص هذا العميل فقط** |
| **`03_samples/`** | بيانات تجريبية وهمية (مثل منتجات مطحنة، عملاء وموردين وهميين) | فقط للتطوير والتجارب | **ممنوع لعميل إنتاج** |
| **`04_tests/`** | بيانات تثبيت الاختبارات البرمجية التلقائية | أثناء تشغيل الاختبارات | **ممنوع للإنتاج** |

## 9. إدارة العملاء وتبديل المشاريع

يتم التحكم بالبيئة المستهدفة بالكامل من خلال ملف **`.env`** في جذر المشروع.

### للعمل على السيرفر المحلي (Docker):
تأكد أن القسم (أ) في `.env` مفعل:
```env
VITE_SUPABASE_PROJECT_ID="local"
VITE_SUPABASE_URL="http://127.0.0.1:54321"
VITE_SUPABASE_PUBLISHABLE_KEY="sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH"
SUPABASE_DB_URL="postgresql://postgres:postgres@127.0.0.1:5432/postgres"
```

### للتبديل إلى عميل سحابي (Cloud Client):
1. قم بوضع علامة `#` أمام أسطر المحلي (القسم أ).
2. فعّل أسطر السحابة (القسم ب) وضع معرف مشروع العميل الجديد:
```env
VITE_SUPABASE_PROJECT_ID="معرف_مشروع_العميل"
VITE_SUPABASE_URL="https://معرف_مشروع_العميل.supabase.co"
VITE_SUPABASE_PUBLISHABLE_KEY="مفتاح_anon_للعميل"
SUPABASE_DB_URL="postgresql://postgres:كلمة_المرور@db.معرف_مشروع_العميل.supabase.co:5432/postgres"
```

## 10. سيناريوهات العمل الشائعة

### السيناريو 1: مبرمج يعمل محلياً ويجرب ميزات جديدة
1. يفتح **Docker Desktop**.
2. يفتح **`db-control.bat`** ويختار `[1]` لتشغيل السيرفر المحلي.
3. يختار `[8]` أو يشغل `npm run dev` للبدء في البرمجة.

### السيناريو 2: إضافة ميزة جديدة وتعميمها على قاعدة عميل (محلي أو سحابي)
1. كتابة التعديل في ملف migration جديد: `supabase/migrations/61_my_new_feature.sql`.
2. اختباره محلياً بتنفيذ خيار `[4]` في القائمة (`npm run db:local:migrate`).
3. بعد التأكد من نجاحه، دفع التعديل لقاعدة العميل السحابية بخيار `[6]` في القائمة (`npm run db:cloud:push`).
4. التعديل يطبق عند العميل في ثوانٍ مع بقاء كل فواتيره وحساباته بأمان تام.

### السيناريو 3: تسليم عميل جديد يعمل محلياً على سيرفر في محله (On-Premise Production)
1. تثبيت Docker Desktop على خادم العميل.
2. وضع كود المشروع وضبط `.env` ليعمل محلياً.
3. تشغيل `npm run db:local:start`.
4. تطبيق الترحيلات وبذور النظام الأساسية (`01_system`) بدون عينات المطحنة.
5. إدخال هوية شركة العميل في `02_company`.
6. ضبط تشغيل المشروع التلقائي عبر `start-market-hup.bat`.

## 11. دليل حل المشكلات الشائعة (Troubleshooting)

### المشكلة 1: `failed to connect to the docker API`
* **السبب:** برنامج Docker Desktop مغلق أو لم يكتمل إقلاعه بعد.
* **الحل:** افتح برنامج Docker Desktop من قائمة ابدأ في ويندوز، وانتظر حتى تظهر النقطة الخضراء في أسفل البرنامج (Engine running)، ثم أعد تشغيل الأمر.

### المشكلة 2: رسالة تضارب في الترحيلات `Checksum mismatch`
* **السبب:** تم تعديل ملف migration قديم سبق تطبيقه على القاعدة.
* **الحل:** لا تعدل ملفات قديمة أبداً. تراجع عن التعديل في الملف القديم وأضف التعديل كملف migration جديد برقم أحدث.

### المشكلة 3: المتصفح يظهر صفحة بيضاء أو خطأ مصادقة
* **السبب:** عدم تطابق المفاتيح في `.env` أو أن سيرفر Supabase مغلق.
* **الحل:** شغل `npm run db:local:status` وتأكد أن القيم المطبوعة تطابق الموجود في `.env`.
