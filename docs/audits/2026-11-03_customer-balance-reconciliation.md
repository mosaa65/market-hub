# تدقيق وإصلاح منظومة أرصدة العملاء والمطابقة المحاسبية

**التاريخ:** 2026-11-03
**الفرع:** `feature/customer-balance-reconciliation-audit` (منشأ من `origin/main`)
**النطاق:** أرصدة العملاء — دفتر العميل، الرصيد المخزَّن، آثار المرتجعات والتحصيل والأرصدة الافتتاحية والقيود.

## A. نتائج التحليل — كيف يعمل النظام حالياً

### أين يُخزَّن الرصيد

| الكيان                        | الجدول/العرض                                                                                               | الدور                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------- |
| رصيد العميل المخزَّن          | `public.customers.balance`                                                                                 | cache للقراءة السريعة  |
| دفتر العميل (المصدر المحاسبي) | `public.customer_ledger` (`debit`, `credit`, `entry_type`, `reference_id`, `reference_type`, `source_key`) | المصدر الحقيقي         |
| مطابقة قراءة فقط              | `customer_ledger_balances` / `customer_balance_reconciliation`                                             | تكشف الفرق بين الاثنين |
| دفتر الأستاذ العام            | `journal_entries` / `journal_lines` (حساب 1211 للحساب الوسيط للعميل)                                       | القيد المزدوج          |

### كيف كان يُحتسب

الرصيد المخزَّن كان **يُحدَّث يدوياً** في كل دالة RPC على حدة:

| المسار               | الدالة                                | كيف حدّثت `customers.balance`      |
| -------------------- | ------------------------------------- | ---------------------------------- |
| فاتورة بيع آجلة      | `create_sale` (9903)                  | `balance + v_outstanding`          |
| تحصيل مفرد           | `record_customer_payment` (76)        | `greatest(balance − amount, 0)`    |
| تحصيل مجزأ           | `record_customer_payment_splits` (76) | `greatest(balance − total, 0)`     |
| مرتجع بيع            | `create_sales_return` (9903)          | `balance − v_tot` **دائماً**       |
| رصيد افتتاحي (مدين)  | `post_opening_balance` (49)           | **لا شيء** — يُقيَّد في الدفتر فقط |
| عكس رصيد افتتاحي     | `reverse_opening_balance` (49)        | **لا شيء** — يُقيَّد في الدفتر فقط |
| تسويات/استيراد مباشر | `customer_ledger` INSERT مباشر        | **لا شيء**                         |

### خريطة تدفّق البيانات

```
فاتورة بيع ──► sales_invoices.paid/total ──► customer_ledger('sale', debit)  ──► customerS.balance (يدوي)
تحصيل      ──► customer_payments       ──► customer_ledger('payment', credit) ──► customers.balance (greatest, يدوي)
مرتجع      ──► sales_returns           ──► customer_ledger('return', credit)  ──► customers.balance (يدوي)
                                              │
                                              └─► journal_entries (1211 نصفي/نقدي) — منفصل تماماً عن مسار الرصيد
```

**الخلاصة:** مساران متوازيان — دفتر العميل وقيد الأستاذ — لا يلتقيان بضمان، والعمود المخزَّن ثالث لا يتبعه أي حارس. هذا أصل الاختلاف.

### C.2 المُشغّل — نقطة التحول البنيوية

```sql
CREATE TRIGGER tg_customer_ledger_sync_balance
  AFTER INSERT OR UPDATE OR DELETE ON public.customer_ledger
  FOR EACH ROW EXECUTE FUNCTION public.tg_customer_ledger_sync_balance();
```

كل حركة في دفتر العميل — من أي مسار، بما فيها التسويات والاستيراد وقيود الأدوات الإدارية — تُعيد احتساب الرصيد المخزَّن **داخل نفس المعاملة**. هذا يُغلق المشكلة الرابعة بنيوياً لا بترقيع.

### C.3 المعادلة الموحّدة

```
customerStoredBalance = Σ(customer_ledger.debit − customer_ledger.credit)
```

مطابقة تماماً لـ `customer_ledger_balances.ledger_balance` ولـ `balanceAsOf()` في `src/lib/statements/engine.ts`، فلا يوجد رقمان لرصيد واحد.

### C.5 الواجهة

- `statement-integrity-badge.tsx`: زر **«إعادة احتساب من دفتر العميل»** يستدعي `recalculate_customer_balance` ثم يُعيد قراءة الكشف. التحذير **لا يختفي** ما دام الفرق موجوداً؛ ورسالة خاصة عند `broken_documents`.
- `_app.statements.$entityType.tsx`: تمرير `customerId` و`onReconciled`.
- `_app.payments.tsx`: إزالة `Math.max(balance, 0)` من فحص المبلغ ومن عرض الرصيد.

## F. ضمانات سلامة النظام

1. **المصدر واحد:** `customers.balance` لم يعد يُكتب يدوياً في أي مسار جديد — الدفتر هو المرجع والمُشغّل هو المنفّذ.
2. **الذرّية:** كل عملية مالية (مستند + دفتر + قيد + رصيد) تتم في معاملة واحدة داخل `SECURITY DEFINER`، وأي خطأ يُلغي الكل.
3. **التزامن:** `customer_balance_lock(uid)` يقفل صف العميل أولاً في التحصيل والمرتجعات، فلا تعمل عمليتان متنافستان على رصيد واحد.
4. **التكرار:** `source_key` فريد + `uq_customer_ledger_opening_source` يمنعان تكرار الحركات عند إعادة الطلب أو إعادة الترحيل.
5. **التدقيق:** كل تغيير للرصيد المخزَّن يحمل «من كم → إلى كم» والسبب والمستخدم والمستندات المشوبة.
6. **لا إخفاء:** الأرقام في كشف الحساب تُقرأ من الدفتر، والتحذير يبقى ظاهراً، والفرق لا يُقصُّ بأي `greatest`.
7. **حماية RLS:** `customer_balance_adjustments` قراءة مالية فقط، والكتابة عبر `SECURITY DEFINER` حصراً.
8. **لا حذف:** لم تُحذف أي حركة محاسبية؛ سجل التصحيحات يُوثّق ولا يُصحّح الأرقام مباشرة.

## G. ما يحتاج تنفيذاً على قاعدة حقيقية

1. `npx supabase db push` (أو `npm run db:cloud:push`) لتطبيق 9913–9916 — **بعد** نسخة احتياطية.
2. `npm run audit:customer-balances` لمعاينة الفروق قبل أي إصلاح.
3. مراجعة الحالات `broken_documents` يدوياً قبل التصحيح الجماعي.
4. `select recalculate_all_customer_balances('مطابقة ما قبل التسليم');` ثم إعادة `customer_balance_reconciliation_report()` للتأكد أن كل الحالات `matched`.
5. `npm run test:customer-balances` لتشغيل اختبارات القبول.

## H. إصلاح احتساب الوقت في التحصيل (لاحق لنفس المهمة)

### الخلل 1 — تاريخ التحصيل يزحف يومًا (الواجهة)

```ts
const [date, setDate] = useState(new Date().toISOString().slice(0, 10)); // ❌
```

`toISOString()` يحوّل إلى UTC. المنشأة تعمل بتوقيت **Asia/Aden (UTC+3)**، فبين
منتصف الليل والثالثة صباحًا يعيد UTC تاريخ **الأمس**.

تحقّق فعلي داخل المشروع (TZ=Asia/Aden، الساعة 00:30 من 2026-11-03):

```
old: 2026-11-02   ← الأمس
new: 2026-11-03   ← الصحيح
```

### الخلل 2 — عرض تاريخ السند بوقت وهمي

`payment_date` عمود `date` بلا وقت، وكان يُمرَّر إلى `VortexDateBadge` كطابع
زمني. المكوّن يقرأه بـ `getHours()/getMinutes()` المحليين، فيظهر **ساعة
مستنبتة** قد تكون 03:00 صباحًا، وقد ينزاح اليوم في بعض المناطق. الحل:
`showTime={false}` + `dateOnlyIso()` لتثبيت منتصف ليل UTC عند العرض.
نفس المعالجة طُبّقت على عمود تاريخ فتح الفترة في كشف الحساب.

### الخلل 3 — منطقة الخادم الزمنية تحكم الدفتر (قاعدة البيانات)

```sql
occurred_at = coalesce(_payment_date, current_date)::timestamptz  -- ❌
```

`date::timestamptz` يُفسَّر بمنطقة الجلسة (عادة UTC). فتحصيل بتاريخ اليوم
ينزل في `customer_ledger.occurred_at` بمنتصف ليل **UTC**، أي 03:00 بتوقيت
عدن — وقد يقع في اليوم السابق عند الطرف الآخر من الاختلاف. النتيجة: ترتيب
حركات كشف الحساب لا يطابق وقوعها، والحركة قد تسقط في فترة مالية أخرى.

### ما تبقّى خارج نطاق هذه المهمة

`toISOString().slice(0,10)` ما زال مستخدمًا في **48 موضعًا** آخر في `src/`
(المصروفات، التقارير، الأصول…). هي نفس الفئة من الخلل لكنها خارج نطاق أرصدة
العملاء. الوحدة `@/lib/time/business-date` جاهزة لتكون المرجع، والترحيل إليها
ميكانيكي.
