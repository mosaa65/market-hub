# مراجعة أمان البيئات والصلاحيات — 2026-11-03 إلى 2026-11-04

## النطاق

مراجعة مصدر التطبيق وهجرات PostgreSQL ومسارات Edge Functions التي تتعلق باختيار Docker أو السحابة، والتحقق من الجلسات، وتفويض أدوار المتجر والمنصة. لم تُقرأ قيم المفاتيح أو تُعدّل بيانات قاعدة بيانات.

## عيوب مؤكدة عولجت في المصدر

1. كان عميل المتصفح ووسيط وظائف الخادم ينتقلان إلى عنوان ومفتاح سحابي ثابتين عند غياب الإعدادات. وكان الوسيط يسمح بتنفيذ الوظيفة مع مستخدم `anonymous` عند غياب الرمز أو فشل التحقق.
2. وسيط `raw-rest` كان يتحقق من جلسة المستخدم ثم يرسل طلب PostgREST بمفتاح الخدمة؛ وهذا يتجاوز RLS. كما كان السماح بالمسار يعتمد على أول مقطع فقط.
3. كانت الواجهة تقبل أدواراً من `localStorage` لمدة خمس دقائق، وتعتبر خطأ قراءة `profiles.is_active` أو غياب صف الملف الشخصي حالة نشطة.
4. كانت صلاحيات الشريط الجانبي وحارس الرابط المباشر متكررة وغير متطابقة؛ المسار غير المعروف كان يُسمح به، ودعم المنصة كان يرث صلاحيات المتجر في الواجهة وبعض سياسات RLS.
5. كان وسيط إنشاء المستخدمين يسمح للمدير رغم أن شاشة المستخدمين مقصورة على المالك.
6. كانت هجرة RBAC رقم 77 تمنح كل الجداول ودوال المستقبل صلاحيات واسعة بعد أن قيّدت هجرة 36 تلك الصلاحيات. كما سمحت سياسة قاعدة البيانات لدعم المنصة بتعديل الاشتراكات، ولأي مستخدم مسجل بكتابة سجل أحداث المنصة.
7. كان تعطيل ملف المستخدم لا يمنع جميع فحوص `has_role`، وكان المستخدم يستطيع تغيير `profiles.is_active` مباشرة. وكانت دالة حراسة حذف الصنف محجوبة عن الواجهة رغم استدعائها من التطبيق.
8. كانت سياسات سجل النسخ الاحتياطي تسمح لجميع المستخدمين المسجلين بقراءته وكتابته دون تحقق من الدور.
9. كانت نقاط خادم لوحة البنية التحتية ودالة Edge لإنشاء المستخدمين تعيد قراءة دور المالك بمفتاح الخدمة، لكنها لا تتحقق من أن ملف المالك نشط.
10. كانت لوحة البنية التحتية تستنتج السحابة من ملف CLI المرتبط وتعرض عمليات ترحيل قد تستهدف قاعدة غير مقصودة؛ كما كانت صلاحية مالك المتجر تمنح وصولاً لأوامر Docker على الجهاز.

## ما تغيّر

- أُزيلت عناوين ومفاتيح Supabase المضمّنة والبدائل الصامتة. يلزم الآن اختيار `VITE_SUPABASE_TARGET` و`SUPABASE_TARGET` صراحةً كـ `docker` أو `cloud` مع عنوان ومفتاح صالحين. Docker لا يقبل نطاق مشروع Supabase المستضاف، وهدف السحابة يرفض المضيف المحلي أو الداخلي. إعداد Compose يطلب الهدفين ويمنع اختلافهما.
- يحمّل `vite.config.ts` قائمة متغيرات الخادم المطلوبة من ملفات `.env` في وضع التطوير فقط؛ إذ إن Vite لا يضعها تلقائياً في `process.env`. الإنتاج يأخذ الأسرار من متغيرات runtime في Compose، ولا تُعرّف مفاتيح الخادم ضمن متغيرات المتصفح.
- صار وسيط الخادم يرفض غياب الرمز أو الرمز غير الصالح، ويتحقق من دور JWT، ويفشل بخطأ إعداد/تحقق بدل إنشاء جلسة مجهولة. مُنع استخدام مفتاح سري مكان المفتاح العام، ومفتاح الخادم السري يبقى في الخادم فقط.
- صار `raw-rest` يستخدم مفتاحاً عاماً ورمز المستخدم نفسه لطلب REST، مع السماح بأسماء الجداول المحددة كاملةً فقط؛ فتظل RLS سارية.
- أزيل تخزين صلاحيات الأدوار في المتصفح. تُعاد قراءة الصلاحيات عند التركيز وكل خمس دقائق، ويُحجب التطبيق أثناء التحديث. فشل فحص نشاط ملف المتجر أو غياب صفه يُرفض، بينما حالة مسؤول المنصة مصدرها سجل `platform_admins`.
- صار سجل التنقل مرجع صلاحيات المسارات المسجلة، وتُفحص معاملات الإعدادات، ويُرفض المسار غير المعروف. سوبر أدمن المنصة وحده يتجاوز صلاحيات المتجر؛ دعم المنصة لا يرث الأدوار.
- صار `is_staff` في قاعدة البيانات لا يحتسب دور دعم المنصة موظفاً في المتجر، وبذلك تتوافق سياسات RLS مع حارس الواجهة ونقاط RPC؛ سوبر أدمن المنصة النشط فقط يحتفظ بالتجاوز العام.
- جرى توحيد صلاحيات إنشاء الموظفين مع شاشة المستخدمين: المالك أو سوبر أدمن المنصة فقط.
- عُدلت هجرات 36 و38 و43 و77 لإعادة البناء، وأضيفت الهجرة الأمامية `9915_security_permissions_fail_closed.sql` لإصلاح قواعد البيانات الموجودة: تسحب منح الكتابة الواسعة وتعيد القائمة المراجعة، وتغلق منح المستقبل الافتراضية، وتعيد سياسات النسخ الاحتياطي والاشتراكات وسجل المنصة، وتجعل `has_role` و`has_any_role` و`is_staff` تراعي حالة النشاط.
- جرى قصر تحديث ملف المستخدم على الاسم والهاتف واللغة. تغيير حالة النشاط يمر عبر RPC يفحص دور المالك/سوبر أدمن، يمنع تعطيل الحساب الذاتي والمالك الأخير، ولا يغيّر حالة مستخدمي المنصة من سجل المتجر.
- صار فحص تعطيل آخر مالك متسلسلاً بقفل معاملاتي لمنع طلبين متزامنين من تعطيل آخر مالكين، وأصبحت نقاط الخادم التي تستخدم مفتاح الخدمة تشترط ملف مالك نشط قبل السماح بإدارة البنية أو إنشاء مستخدم.
- لا تمنح الهجرة الجديدة صلاحية تنفيذ كل دوال `public` للمستخدم المسجل؛ تحتفظ فقط بالمنح الصريحة الموجودة، وتضيف منحاً صريحاً لإجراء تغيير حالة الحساب، وتترك دوال الخادم محصورة بـ `service_role`.
- أُعيد السماح باستدعاء `product_delete_guard` من الواجهة بعد أن تأكدت صلاحياته الداخلية، وقُصر تجاوز الحارس على سوبر أدمن المنصة لا دور الدعم.
- فُصل اختيار البيئة عن ارتباط Supabase CLI: أدوات البنية التحتية لا تقرأ `.temp/project-ref` لتقرر الوجهة. أوامر الحالة والترحيل وإعادة البناء تستخدم `--local`، ولا تعرض الواجهة دفعاً أو سحباً أو إصلاحاً للسحابة. عند اختيار السحابة تُرفض إدارة Docker المحلية، وفشل Docker لا يغيّر الوجهة. كذلك حُصر تحكم المضيف بسوبر أدمن المنصة النشط، وأصبحت عمليات التنظيف المدمرة تتطلب عبارة تأكيد محددة.
- أُصلح التباس حالة السحابة بحيث لا تظهر «مرتبطة» إلا عند وجود معرّف مشروع صريح؛ اختيار `cloud` وحده لا يثبت الارتباط أو الاتصال.

## التحقق والحدود

- اختبار حارس المسارات: **377 تحققاً ناجحاً، دون إخفاق**، بما فيها منع مالك المتجر من فتح إدارة المضيف.
- اختبار اختيار البيئة ونوع المفتاح: **9 حالات ناجحة، دون إخفاق**.
- تغطية المسارات: كل مسار ضمن `_app` يطابق سجلاً أو قاعدة احتياطية مراجعة.
- فحوص ESLint وPrettier للملفات المتأثرة بأدوات البنية التحتية: **دون أخطاء**. فحص `git diff --check` ناجح.
- `npm run build`: اكتمل بنجاح بعد تفريغ مساحة القرص، بما في ذلك SSR وNitro.
- `npx tsc --noEmit --pretty false`: اكتمل دون أخطاء TypeScript.
- اختبار إعداد التطوير دون طباعة القيم: هدفا العميل والخادم متطابقان (`docker`)، عنوانا الاتصال صالحان، مفتاح المتصفح غير مميّز، والمفتاح السري محصور بإعداد الخادم.
- شُغّل خادم التطوير على `http://localhost:3000` وأعاد المسار الرئيسي HTTP 200 بعد تحميل إعدادات الخادم.
- فُحصت ملفات العميل المبنية مقابل ثلاثة مفاتيح خادم مضبوطة محلياً؛ لم يظهر أي منها في `.output/public`.
- `git diff --check`: لم يجد أخطاء مسافات/تباعد.
- فحص صياغة Compose نجح باستخدام نطاقين مؤقتين للفحص فقط؛ ملف `deploy/.env.production` الفعلي يفتقد `APP_DOMAIN` و`SUPABASE_DOMAIN`، لذلك إعداد النشر الحالي غير مكتمل ولا يبدأ كما هو. قيم الأهداف موجودة في إعدادات البيئة المحلية والإنتاجية، ولم تُطبع أي مفاتيح.
- لم تُطبّق الهجرة `9915` على Docker أو السحابة، ولم يُنفذ `db reset` أو تغيير بيانات. لذلك صلاحيات قاعدة البيانات الحية لا تُعد مُصلحة حتى تطبيق هذه الهجرة بنجاح. كما لم يُجر اختبار قبول متصل بقاعدة البيانات أو Edge Functions.
- لم تُشغّل الحاويات ولم تُنشر Edge Function المحدّثة. يجب أن تتطابق قيمتا `VITE_SUPABASE_TARGET` و`SUPABASE_TARGET` عند البناء والتشغيل. نشر التطبيق قبل الهجرة 9915 قد يعطّل تغيير حالات الموظفين لأن الواجهة تستخدم RPC الجديد.
- أدوات البنية التحتية المنشأة داخل التطبيق تعمل محلياً فقط عند تحديد Docker؛ عمليات السحابة تبقى منفصلة عبر إجراءات نشر مسماة بوضوح. لم يُنفذ أي أمر دفع سحابي في هذه المراجعة. ترحيل Docker يستخدم `supabase migration up --local` وفق دعم CLI المحلي، وليس وجهة الارتباط الضمني.
