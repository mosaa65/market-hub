# ملخص طريقة العمل المقترحة — Vortex ERP Offline-First

> هذا الملف ملخص تنفيذي للدراسة المعمارية، وليس Implementation. لا توجد فيه تغييرات منفذة على التطبيق أو قاعدة البيانات.

## القرار المختصر

سيتم تحويل النظام مستقبلًا إلى تطبيق Windows Desktop باستخدام:

```text
Tauri
  + React / TanStack UI
  + SQLite محلية
  + طبقة معاملات محلية
  + Outbox / Inbox Sync Engine
  + Supabase PostgreSQL / RPC / RLS
```

سيعمل التطبيق من قاعدة البيانات المحلية أولًا، ثم يزامن العمليات مع Supabase عند عودة الإنترنت. ستكون Supabase المرجع المشترك النهائي للعمليات المقبولة، بينما تكون SQLite نسخة محلية معاملاتية تسمح باستمرار العمل دون اتصال.

## كيف سيعمل النظام؟

### عند توفر الإنترنت

```text
المستخدم
  ↓
واجهة React
  ↓
المعاملة المحلية
  ↓
SQLite + Outbox
  ↓
Sync Engine
  ↓
Supabase RPC / API
  ↓
PostgreSQL + RLS
```

حتى أثناء الاتصال، تُحفظ العملية محليًا أولًا داخل transaction واحدة. بعدها يرسلها محرك المزامنة إلى Supabase. هذا يمنع ضياع العملية إذا انقطع الاتصال مباشرة بعد ضغط زر الحفظ.

### عند انقطاع الإنترنت

```text
المستخدم
  ↓
واجهة React
  ↓
SQLite المحلية
  ├── الفاتورة أو العملية
  ├── أثر المخزون أو الحساب
  ├── سجل التدقيق
  └── Outbox: عملية تنتظر المزامنة
```

يستمر المستخدم في إدارة المنتجات والعملاء والموردين والمخزون والمبيعات والمشتريات والمصروفات والتقارير، بحسب البيانات الموجودة محليًا والسياسات المسموح بها. تظهر العمليات التي لم تصل إلى السحابة بوضوح على أنها `Pending Sync`.

### عند عودة الإنترنت

1. يقرأ Sync Engine العمليات المعلقة بترتيبها.
2. يرسل كل عملية باستخدام `operation_id` و`idempotency_key`.
3. يتحقق الخادم من الصلاحيات والمخزون والأرصدة.
4. يقبل العملية كاملة أو يرفضها كاملة.
5. يسحب تغييرات Supabase التي حدثت منذ آخر `sync_cursor`.
6. يحدّث SQLite ويسجل النتيجة أو التعارض.

إذا توقف التطبيق بعد وصول العملية إلى الخادم، تعاد المحاولة بنفس المعرف. لن تُنشأ فاتورة أو دفعة ثانية؛ يعيد الخادم نتيجة العملية السابقة.

## ما الذي سيعمل Offline؟

- المنتجات والتصنيفات والعلامات والوحدات.
- العملاء والموردون.
- المستودعات والدفعات وتواريخ الانتهاء.
- المبيعات ونقاط البيع.
- المشتريات والمرتجعات.
- التحويلات والتسويات المخزنية.
- المدفوعات والتحصيلات والمصروفات.
- أرصدة العملاء والموردين والتقارير.
- الطباعة وPDF والباركود.
- سجل التدقيق والنسخ الاحتياطي المحلي.

بعض العمليات ستعمل محليًا لكنها تظل `Pending` حتى يعتمدها الخادم، خصوصًا العمليات التي قد تتعارض مع جهاز أو مستخدم آخر.

## كيف نحمي المخزون والمالية؟

### المخزون

- لا يتم تعديل `inventory` مباشرة من الواجهة.
- كل بيع أو شراء أو مرتجع أو تحويل هو عملية ذرية.
- تُحفظ وثيقة العملية وحركة المخزون وسجل التدقيق معًا.
- يمنع النظام المخزون السالب للأصناف المتتبعة بحسب سياسة العمل.
- عند وجود تعارض، لا نستخدم `Last Write Wins`.
- يسجل النظام تعارضًا يحتاج إلى رفض أو مراجعة أو عملية تعويضية.

مثال: إذا كان المخزون 100، وتم بيع 70 Offline بينما بيع 60 في السحابة، فلن يتم تغيير الكمية بصمت. سيتحقق الخادم من ترتيب العمليات، ثم يقبل إحداها أو يرفضها أو يطلب تسوية موثقة.

### المالية

- المبيعات والمدفوعات والمصروفات والمرتجعات تسجل كعمليات غير قابلة للتكرار.
- لا يتم تعديل الرصيد النهائي مباشرة عند المزامنة.
- يعاد بناء الأرصدة من الحركات المالية ومصادرها.
- تصحيح عملية مالية يكون بعكس موثق أو عملية تعويضية، وليس بحذف السجل.
- كل عملية تحمل معرفًا ثابتًا يمنع تكرارها عند إعادة الإرسال.

## كيف ستتم المزامنة؟

ستعتمد المزامنة على أربعة عناصر:

| العنصر | وظيفته |
|---|---|
| `Outbox` | حفظ العمليات المحلية التي تنتظر الإرسال |
| `Inbox` | منع تطبيق تغيير سحابي أكثر من مرة |
| `operation_id` | تعريف ثابت للعملية حتى بعد إعادة المحاولة |
| `sync_cursor` | معرفة آخر تغيير سحابي تم تطبيقه |

سيتم استخدام retry وexponential backoff عند انقطاع الشبكة. أما Realtime فسيستخدم كإشارة لتنبيه المحرك بوجود تغييرات، وليس كمصدر وحيد للبيانات؛ لأن أي إشعار قد يفوت أثناء انقطاع الإنترنت.

## تسجيل الدخول والصلاحيات

- أول تهيئة وربط الجهاز بـSupabase تحتاج إلى اتصال.
- بعد ذلك يستطيع مستخدم معروف محليًا الدخول Offline.
- تحفظ صلاحيات المستخدم محليًا كنسخة موقعة/موثقة، ويعاد التحقق منها عند الاتصال.
- Supabase Auth وRLS يظلان مسؤولين عن التحقق السحابي.
- لا يتم وضع `service-role key` أو `SUPABASE_SECRET_KEY` داخل التطبيق المثبت.
- إذا تغيرت صلاحية مستخدم أثناء Offline، فلن يعرف الجهاز بذلك إلا عند المزامنة؛ وهذه مخاطرة لا يمكن إلغاؤها دون اتصال.

## Windows والحماية

- يثبت البرنامج كتطبيق Windows عبر Tauri.
- تحفظ قاعدة البيانات خارج مجلد البرنامج حتى لا تضيع عند التحديث.
- تستخدم SQLite مع WAL ونسخ احتياطية تلقائية ومشفرة.
- يوقع المثبت والتحديثات رقميًا.
- يمكن استخدام ترخيص موقّع وربط اختياري بالجهاز.

لا يمكن حماية الكود حماية مطلقة من مستخدم يملك Administrator على جهازه. الهدف الواقعي هو حماية الأسرار والبيانات، ورفع تكلفة النسخ، وإبقاء القواعد الحساسة والتحقق النهائي في Supabase.

## ما الذي لن نفعله؟

- لن نعتمد على Cache أو `localStorage` كقاعدة ERP.
- لن نكتب عمليات المخزون والمالية مباشرة من الواجهة.
- لن نستخدم `Last Write Wins` للأرصدة أو الحركات المالية أو المخزون.
- لن نضع مفتاح Supabase السري داخل Desktop client.
- لن نعيد تشغيل migrations التي تحتوي reset أو demo seed لإنشاء قاعدة العميل المحلية.
- لن نعتبر Realtime بديلًا عن Outbox/Inbox وcursor دائم.
- لن نبدأ بتحويل كل النظام قبل عزل طبقة الوصول إلى البيانات واختبار العمليات المحلية.

## ترتيب التنفيذ المستقبلي

1. تثبيت قواعد المخزون والمالية وأشكال العمليات.
2. بناء SQLite وlocal migrations والنسخ الاحتياطي.
3. فصل routes/components عن Supabase عبر Data Access Layer.
4. نقل master data والتقارير إلى القراءة المحلية.
5. نقل المبيعات والمشتريات والمخزون والمالية إلى local transactions.
6. إضافة Outbox وAudit محلي.
7. إضافة Supabase Sync وidempotency وchange cursor.
8. إضافة conflict resolution والمراجعة والتسويات.
9. إضافة Offline authentication والترخيص.
10. تغليف Windows واختبار crash وpower loss وrestore والبيانات الكبيرة.

**الخلاصة:** التطبيق المستقبلي لن يكون موقعًا يخزن آخر نسخة من البيانات، بل نظام ERP محليًا كاملًا يعمل دون إنترنت، يحتفظ بكل عملية بشكل ذري وقابل للتتبع، ثم يزامنها مع Supabase بأمان عند عودة الاتصال.
