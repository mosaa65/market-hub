# Market-Hub ERP — تقرير تدقيق واقتراح معمارية Offline-First

> **حالة الوثيقة:** تحليل وخطة فقط. لم يتم في هذه المرحلة تعديل كود التطبيق، أو إنشاء Migration، أو تغيير Supabase/Vercel/RLS، أو نشر أي شيء.
>
> **تاريخ التحليل:** 2026-09-30

## 1. الملخص التنفيذي

القرار المقترح هو اعتماد معمارية **Hybrid Offline-First** يكون فيها تطبيق سطح المكتب هو قناة التشغيل الأساسية في حالات انقطاع الإنترنت الطويلة:

```text
Tauri Desktop Application
  + React / TanStack UI الحالية
  + SQLite محلية ومشفرة
  + Local Transaction + Outbox
  + Sync Engine
  + Supabase RPC / Sync API
  + PostgreSQL + RLS (المصدر المركزي المعتمد)
```

يبقى تطبيق الويب المنشور على Vercel متاحاً للعمل المتصل بالإنترنت، مع PWA لتخزين واجهة التطبيق والملفات الثابتة فقط. ولا ينبغي اعتباره قاعدة بيانات ERP محلية كاملة.

هذا الاختيار لا يطلب من العميل تثبيت Docker أو Node.js أو PostgreSQL أو تشغيل أي خادم محلي؛ بل يثبت تطبيق Windows عادي، وتُدار قاعدة بياناته محلياً داخل مجلد بيانات التطبيق.

## 2. ما تم إنجازه في هذه المرحلة

تم تنفيذ تحليل قراءة فقط للمستودع، وشمل:

- مراجعة التقنية المستخدمة: React 19 وTypeScript وTanStack Start/Router/Query وVite وSupabase وPostgreSQL وVercel.
- مراجعة بنية المسارات والمكونات والمكتبات وعميل Supabase والمصادقة والتخزين المحلي.
- تتبع المسارات التشغيلية للمبيعات والمشتريات والتحويلات والمرتجعات والمدفوعات والمصروفات والمخزون.
- مراجعة الـ migrations الحديثة الخاصة بمحرك المخزون وسياسات الأصناف والمبيعات والمشتريات والتقارير والصلاحيات.
- مراجعة وضع PWA والنسخ الاحتياطي والـ realtime والتخزين المحلي الحالي.
- تحديد الفجوات التي تمنع العمل الحقيقي دون إنترنت، ووضع تصميم للمخزن المحلي والمزامنة وحل التعارضات وخارطة تنفيذ تدريجية.

لم يتم تعديل أي ملف. يوجد ملف `plan.md` غير متتبع في المستودع قبل هذا العمل ولم يتم لمسه.

## 3. الوضع الحالي للمشروع

المشروع حالياً تطبيق ERP ويب متصل بالإنترنت. بنيته منظمة وظيفياً، لكن أغلب شاشات العمل تتصل مباشرة بعميل Supabase بدلاً من المرور عبر طبقة وصول بيانات موحدة.

```text
واجهة React
  → استعلام أو RPC من Supabase داخل Route
  → PostgreSQL / RLS / دوال RPC
  → نتيجة العملية وتحديث React Query أو Realtime
```

### نقاط جيدة موجودة بالفعل

- توجد دوال PostgreSQL ذرية للعمليات الحساسة، مثل البيع والشراء والمرتجعات والتحويل والتحصيل.
- محرك المخزون الحديث يستخدم قفل صف المخزون والتحقق من عدم نزول الكمية تحت الصفر في نفس المعاملة.
- العمليات المحمية تتحقق من المستخدم والدور قبل التنفيذ، والدوال الداخلية الحساسة ليست متاحة مباشرة للمتصفح.
- التقارير الحديثة تفرق بين الخدمات والمواد المخزنية وغير المخزنية، ولا تفترض دائماً أن تكلفة الصنف هي التكلفة الفعلية.
- يوجد Supabase Auth وRLS وأدوار تشغيلية: owner وmanager وaccountant وcashier وwarehouse.

### الفجوات الحالية

1. لا توجد قاعدة بيانات محلية للمعاملات.
2. لا يوجد Service Worker مسجل؛ يوجد Manifest فقط، وهذا لا يحقق Offline.
3. إعداد React Query يفرض `networkMode: "online"` للـ mutations؛ لذلك لا يمكن تنفيذ العمليات عند انقطاع الشبكة.
4. لا يوجد Outbox أو Inbox أو Sync Cursor أو معالجة تعارضات.
5. استدعاءات Supabase منتشرة مباشرة داخل الـ routes، ما يجعل التحويل إلى Local-first خطراً إن تم دفعة واحدة.
6. لا يوجد عقد Idempotency في الدوال التشغيلية الحالية؛ إعادة إرسال طلب غير مؤكد النتيجة قد تسبب تكرار العملية مستقبلاً.
7. أرقام الفواتير تصدر من الخادم، وبالتالي تحتاج المعاملة Offline إلى مرجع محلي مؤقت منفصل عن الرقم الرسمي.
8. التخزين المحلي الحالي هو تفضيلات وجلسة وكاش صلاحيات وسجل نسخ احتياطي، وليس قاعدة ERP.
9. توجد كتابة مباشرة للمصروفات في شاشة المالية؛ يجب تحويلها لاحقاً إلى عملية أعمال موحدة وقابلة للمزامنة، بدلاً من CRUD مباشر.

## 4. القرار المعماري

### لماذا Tauri + SQLite؟

| الخيار | النتيجة |
| --- | --- |
| Cache أو `localStorage` | غير مناسب لحفظ سجلات مالية أو مخزنية أو طوابير عمليات. |
| PWA + IndexedDB فقط | مناسب لتجربة ويب محدودة، لكن أقل قوة في التشفير والنسخ والاستعادة والتحديثات الطويلة. |
| Tauri + SQLite | الخيار الموصى به للـ POS والمخزون والعمل أياماً دون إنترنت؛ قاعدة معاملات محلية مستقرة وتطبيق مثبّت عادي. |
| Electron | صالح تقنياً لكنه أكبر حجماً واستهلاكاً؛ لا توجد حاجة مبدئية له مع Tauri. |

تطبيق الويب لا يُلغى. لكن التطبيق المكتبي يصبح هو المسار الموثوق للمتجر أو المستودع الذي يحتاج أن يستمر عند انقطاع الإنترنت.

| المشتريات والمرتجعات | عمليات محلية مؤقتة | الخادم يعتمد القيود النهائية |

## 6. قاعدة البيانات المحلية المقترحة

لا يتم نسخ كل جداول Supabase بصورة عمياء. تنشأ نسخة تشغيلية محلية من البيانات اللازمة فقط: إعدادات الشركة اللازمة للتشغيل، البيانات المرجعية، الأصناف، العملاء، الموردون، المستودعات، الدفعات، مواضع المخزون، المستندات وبنودها، المدفوعات، المصروفات، حركات المخزون، والتوقعات المحلية للتقارير.

كل صف قابل للمزامنة يحمل، حيث ينطبق:

```text
id                 UUID ثابت عالمياً
server_version     إصدار الصف على الخادم
updated_at         تاريخ آخر تعديل
deleted_at         Tombstone للحذف المنطقي
sync_state         synced | pending | rejected | conflicted
last_synced_at     آخر مزامنة
origin_device_id   الجهاز الذي أنشأ السجل
```

جداول النظام المحلية المطلوبة:

- `local_schema_migrations`
- `device_registration`
- `offline_authority_grants`
- `auth_snapshot`
- `sync_state`
- `sync_outbox`
- `sync_inbox`
- `sync_conflicts`
- `id_mapping`
- `local_audit_events`
- `local_backups`

تستخدم SQLite في وضع WAL، مع تفعيل Foreign Keys وفهارس للـ barcode وSKU والاسم، ولعمليات الطابور، وتاريخ المستندات، وموضع المخزون `(product_id, warehouse_id, owner)`.

## 7. الهوية والترقيم وعدم التكرار

كل عملية محلية جديدة تستخدم UUIDv7 أو UUID عشوائي آمن. لا يتم توليد الرقم الرسمي للفواتير Offline.

كل مستند يتضمن:

- `id`: معرف ثابت عالمياً.
- `local_document_ref`: مرجع قابل للطباعة محلياً، مثل `POS-DEVICE7-20260930-0041`.
- `server_document_number`: الرقم الرسمي، يعيّنه الخادم عند قبول العملية.
- `operation_id`: معرف ثابت لعملية المزامنة.
- `idempotency_key`: مفتاح فريد يمنع تكرار التنفيذ على الخادم.

على الخادم، أي إعادة إرسال بالمفتاح نفسه تعيد النتيجة الأصلية ولا تنشئ فاتورة أو دفعة أو حركة مخزون جديدة.

## 8. تصميم محرك المزامنة

```text
عملية المستخدم
  ├─ حفظ المستند والبنود محلياً
  ├─ تحديث الإسقاط المحلي للمخزون/المال
  ├─ كتابة حدث تدقيق محلي
  └─ إضافة Envelope غير قابل للتعديل إلى Outbox
          ↓
عند عودة الاتصال
  ├─ مصادقة والتحقق من الجهاز والصلاحية
  ├─ إرسال العمليات الجاهزة حسب التبعيات
  ├─ اعتماد أو رفض ذري من PostgreSQL
  ├─ حفظ النتيجة والرقم الرسمي
  ├─ سحب تغييرات الخادم منذ Cursor ثابت
  └─ تحديث قاعدة SQLite وواجهة المستخدم
```

القواعد الأساسية:

- حفظ المستند وحركة المخزون/المال المحلية وسجل التدقيق وOutbox يكون داخل **SQLite transaction واحدة**.
- لا يعاد تلقائياً تنفيذ خطأ صلاحية أو تحقق أو تعارض.
- الأخطاء المؤقتة تستخدم Exponential Backoff مع Jitter.
- الـ Realtime إشعار مساعد فقط؛ مصدر الحقيقة للمزامنة هو Pull بواسطة Cursor دائم.
- تبعيات الإرسال: البيانات المرجعية ← المستندات ← الحركات ← المدفوعات/المرتجعات ← كاش التقارير.
- لا تحذف عمليات Outbox الناجحة إلا بعد سياسة احتفاظ ونسخة احتياطية قابلة للتحقق.

يُفضّل أن يستقبل الخادم لاحقاً `sync_apply_operation` كعقد عمليات نوعي، ثم يستدعي محركات الأعمال الحالية داخلياً، بدلاً من السماح بـ CRUD عام من عميل Offline.

## 9. حل التعارضات

| النوع | السياسة |
| --- | --- |
| وصف الصنف وبيانات غير حرجة | تحقق إصدار ودمج أو مراجعة يدوية عند التداخل |
| السعر وسياسة الصنف | لا كتابة صامتة؛ تحقق الخادم ومراجعة التعارض |
| العملاء والموردون | دمج الحقول المستقلة فقط؛ التكرار يحتاج قرار مستخدم |
| الفواتير والمدفوعات وحركات المخزون | غير قابلة للدمج؛ تصحيحها بعكس/تعويض موثق |
| كمية المخزون | يمنع Last Write Wins؛ الخادم يتحقق من دفتر الحركات والرصد |
| حد ائتماني أو دور مستخدم | سلطة الخادم؛ العملية المرفوضة تبقى ظاهرة محلياً كـ Rejected |
| رقم فاتورة | رقم الخادم هو الرسمي مع الاحتفاظ بالمرجع المحلي للتتبع |

عند وجود عدة أجهزة تعمل Offline على المستودع نفسه، يجب اعتماد واحدة من سياستين: جهاز Offline مسؤول واحد لكل مستودع، أو حصص مخزون/تصاريح مؤقتة يصدرها الخادم للأجهزة قبل الانقطاع. غير ذلك قد ينتج رفض صحيح لعملية عند المصالحة، ولا يجوز إخفاؤه.

## 10. سلامة المحاسبة والمخزون

- القيود المالية وحركات المخزون تعامل كأحداث Append-only.
- التصحيح يتم بعكس أو مستند تعويضي، لا بتعديل التاريخ مباشرة.
- الرصيد والتقرير المحليان يحملا حالة **مؤقت / بانتظار اعتماد الخادم** حتى نجاح المزامنة.
- لا يسمح للمخزون المحلي بالنزول تحت الصفر ضمن حدود الجهاز الواحد.
- تبقى الخدمات والأصناف غير المتتبعة بلا حركة مخزون كما تفرضه السياسة الحالية.
- يجب الحفاظ على الفصل الموجود حالياً بين التكلفة الفعلية وتكلفة المعيار/المرجع.

## 11. المصادقة والأمن

- أول تسجيل دخول وربط جهاز واسترداد كلمة مرور وتغيير الأدوار تتطلب اتصالاً.
- يسمح Offline فقط لمستخدم سبق توثيقه على الجهاز، ضمن صلاحية موقعة/متحقق منها ومدة انتهاء واضحة.
- تشفر SQLite محلياً، وتحفظ مفاتيحها في مخزن أسرار نظام التشغيل، وتشفّر النسخ الاحتياطية بشكل مستقل.
- يربط التصريح بالمستخدم والجهاز والشركة والمستودعات المسموحة وانتهاء الصلاحية وإصدار التطبيق.
- لا يوضع `service_role` أو أي مفتاح Supabase سري داخل التطبيق المكتبي.
- صلاحية العميل المحلية تحدد ما يمكن تسجيله مؤقتاً فقط؛ لا تلغي RLS أو تحقق الخادم.
- يلزم إظهار أثر إلغاء المستخدم أو الجهاز عند أول اتصال لاحق، مع حظر المزامنة وإعادة طلب الدخول.

## 12. PWA والتحديثات والنسخ الاحتياطي

### PWA

يضاف Service Worker لاحقاً لتخزين App Shell والملفات الثابتة والخطوط والإصدارات فقط. لا تعتمد استجابات API الموثقة كقاعدة حقيقة في Cache.

### التحديثات

- التحديث لا يفعّل تلقائياً إن وجدت عمليات غير مزامنة.
- قبل Migration محلية: نسخة احتياطية، فحص توافق، وSnapshot قابل للاستعادة.
- قاعدة البيانات تبقى خارج مجلد تثبيت التطبيق.
- يوقع المثبت والتحديثات رقمياً.

### النسخ الاحتياطي

نسخة SQLite محلية مشفرة ومتسقة هي النسخة الأساسية للاستعادة Offline. النسخ التصديري الحالي من المتصفح لا يكفي وحده كضمان تشغيلي؛ لأنه يعتمد على سحب بيانات من السحابة إلى ذاكرة المتصفح.

## 15. معايير القبول

لا تعتبر المنظومة جاهزة قبل إثبات ما يلي:

1. عملية بيع لا تضيع عند إغلاق التطبيق أو انقطاع الكهرباء قبل المزامنة.
2. إعادة إرسال العملية نفسها لا تنشئ فاتورة أو دفعة أو حركة مخزون إضافية.
3. لا يصبح المخزون المحلي سالباً ضمن سياسة جهاز Offline واحد.
4. تعارض جهازين في المخزون يكتشف ويعرض للمراجعة، ولا يكتب بصمت.
5. تطابق دفاتر المخزون والمال المحلية مع الخادم بعد المزامنة.
6. المستخدم أو الجهاز الملغى لا يحصل على تصريح جديد ويمنع عند أول اتصال.
7. التحديث لا يفقد قاعدة البيانات أو Outbox أو النسخة الاحتياطية.
8. استعادة فعلية من نسخة SQLite مشفرة تنجح في اختبار مستقل.
9. الواجهة توضح دائماً حالة المزامنة والعمليات المعلقة والفاشلة والتعارضات.
10. التقارير تميز بوضوح بين البيانات المعتمدة من الخادم والعمليات المحلية المؤقتة.

## 16. التوصية التالية

لا تبدأ بإضافة Service Worker أو Cache أو تحويل كل الشاشات. الخطوة الصحيحة بعد الموافقة هي **المرحلة 0**: اعتماد سياسة الأجهزة والمستودعات والتشغيل المتزامن، ثم تنفيذ طبقة الوصول للبيانات وعقد Idempotency والمزامنة قبل نقل أي عملية مالية أو مخزنية إلى الوضع Offline.
